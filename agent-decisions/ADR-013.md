# ADR-013: 双通道工具调用采用「原生 function calling 优先 + ReAct 提示词降级」，以统一 IR 隔离差异

## Status: Accepted (2026-10-21)

## Background
用户已拍板：工具调用走双通道——优先 LLM 原生 function calling，模型不支持时自动降级 ReAct 提示词解析。需要决定两通道的关系、切换时机、以及上层如何不感知差异。

联网核实（2026-10-21，官方文档）发现各 provider 对 function calling 的支持**差异远大于预期**，无法假定「5 家都支持、都一样」：

- DeepSeek：`parallel_tool_calls` 被忽略（并行始终开启）；思考模式下必须在每轮 assistant 消息保留 `reasoning_content`，否则 400；strict 模式需换 `base_url` 到 `/beta`；**`deepseek-reasoner`（旧推理模型）完全不支持 Function Call**。
- GLM：**必须显式传 `tool_stream: true`**，否则模型不返回 `tool_calls`（`glm-5.3` 起默认 true）；思考模式下 `tool_choice` 不支持 `required` 与指定函数。
- Qwen：**不支持 `tool_choice: "required"`**（思考模式下尤其）；`parallel_tool_calls` 需显式 `true`；`qwen-omni-realtime` 系列两者都不支持。
- Kimi：`tool_choice: "required"` 仅 `kimi-k3` 支持；思考模式必须保留 `reasoning_content`；`finish_reason=tool_calls` 时 `content` 偶尔非空。
- OpenAI：全支持，但 strict 模式要求 `parallel_tool_calls: false`。

## Decision
采用**双通道 + 统一中间表示（IR）**架构：

1. **两条通道产出完全相同的 `TurnIR` / `ToolCallIR`**。上层（AgentLoopService、ToolExecutor、SSE 写出）只消费 IR，**物理上**不感知通道差异。IR 归一化点是：原生通道的 `tool-call-normalizer.ts` 与 ReAct 通道的 `react-parser.ts`，二者输出同一组类型。
2. **通道 A（原生）**：请求体下发 `tools` + `tool_choice: "auto"`；**工具名必须是消毒后的线上名**（下划线形式，`^[a-zA-Z0-9_-]{1,64}$`——点号会让整个请求 400，详见 ADR-014）；流式响应按 `delta.tool_calls[].index` 累积（`id`/`name` 取首个非空值，`arguments` 片段按序拼接）；结果按 OpenAI 兼容格式回填——先追加带 `tool_calls` 的 assistant 消息，再追加**数量与 `tool_calls` 一一对应**的 `role:"tool"` 消息（带 `tool_call_id`）。
3. **通道 B（ReAct 降级）**：提示词模板要求模型输出 ```` ```tool_call ```` 围栏内的 JSON；解析器三级降级——L1 提取围栏块 → L2 扫描首个平衡 `{...}` → L3 正则抽取工具名与参数。三级全失败时视为普通回答（不崩循环）；解析出但参数非法时交由 ToolExecutor 校验后以 `tool_error` 回喂。observation 通过 user 消息里的 ```` ```tool_result ```` 块回填。
4. **能力表按「模型」粒度配置**（`providers/capabilities.ts`）：`nativeTools` / `toolChoiceValues` / `explicitParallelToolCalls` / `retainReasoningContent` / `requireToolStreamFlag` / `onToolCallFailure`。因为 `deepseek-reasoner` 不支持而 `deepseek-chat` 支持，粒度必须到模型而非 provider。
5. **能力探测三级**：
   - L0 静态：请求前查表，`nativeTools=false` 直接走 ReAct，不浪费一次上游调用。
   - L1 运行时：收到上游 4xx 且信息匹配 tool 相关 → 标记该 `(provider, model)` 会话级降级 → 切换 ReAct 重试**本轮**。
   - L2 回切：新会话开始时对 L1 降级过的模型重试一次原生通道，成功则清除降级标记。**同一轮内不自动回切**（避免两通道 observation 格式不一致导致上游 400）。
6. **降级对前端可见但不打断**：`meta` 事件携带 `mode`（`function_calling` / `react`，与 UIUX §8 对齐）/ `degraded` / `degradedReason`，前端显示一条静态提示条。用户可在设置页锁定通道（`auto`/`native`/`react`），锁定时跳过探测。
7. **保守参数下发**：`tool_choice` 只发 `auto`（5 家唯一公共安全值）；`parallel_tool_calls` 默认发 `false`（保守，避免并行与审批交互复杂化）；`tool_stream` 仅在能力表要求时下发。
8. **ReAct 通道同样使用线上名**：提示词中的工具清单用线上名（保证模型产出的名字能被反查），但**同时给出规范名**供人读。

## Consequences
正面：模型选择自由，不因 provider 能力差异而无法使用工具；上层代码单一路径，ReAct 与原生共用全部工具/安全/审批逻辑；降级对用户透明且可观测；能力表把 provider 差异集中到一处，新增 provider 只需加一行配置。
负面：ReAct 通道准确性显著低于原生（ADR-014 承认此差距）；需要维护两套提示词与两套解析逻辑；原生通道的流式 `tool_calls` 归一化是易错点（现有 adapter 就是在这里把 tool_calls 降级成了纯文本，必须重写）；同一请求内可能发出两次 `meta` 事件，需在前端明确「后到者覆盖」的约定。
