# ADR-011: 上下文记忆存储选用 Node 22 内置 node:sqlite，不引入 better-sqlite3

## Status: Accepted (2026-10-21)

## Background
Agent 平台要求服务端持久化上下文记忆（会话、消息、工具调用记录），需要一个嵌入式数据库。候选：`node:sqlite`（Node 22 内置，实验性）、`better-sqlite3`（原生模块）、`node-sqlite3-wasm`、纯 JSON 文件、外部 DB 服务。

任务书给出的初始假设是「better-sqlite3 需 node-gyp 编译，Windows/沙箱易失败」。该假设需要实测验证——版本演进可能已改变这一事实，架构决策不能基于过时前提。

## Decision
使用 Node 22 内置 `node:sqlite` 的 `DatabaseSync` API，通过 `server/src/repositories/db.ts` 封装访问，不引入任何 SQLite npm 依赖。

理由（本机 Windows + Node 22.22.2 实测）：

1. **安装风险与耗时**：`npm install better-sqlite3@13.0.3` 实测耗时 **2 分 30 秒**（同机纯 JS 包对照 10-25 秒，差值为大体积预编译产物下载）。`node:sqlite` 零安装零编译，直接消除交付链路上的一个阻塞点。
2. **原假设已被证伪但风险仍在**：实测 better-sqlite3 13.0.3 **已内置 `prebuilds/win32-x64.node` 且 `scripts` 中无 `install`/`postinstall`**，本机**未触发** node-gyp 编译，加载运行正常。因此「必然需 node-gyp 编译」不成立。但其 `engines.node >= 22` 与预编译产物与 Node 版本强绑定，跨版本/跨平台仍可能退化为源码编译（需 Python + MSVC），风险不能视为零。
3. **功能完备**：实测 `DatabaseSync` 提供 `open/close/prepare/exec/function/location/aggregate/createSession/applyChangeset/enableLoadExtension/loadExtension`，`StatementSync` 提供 `iterate/all/get/run/columns/setAllowBareNamedParameters/setAllowUnknownNamedParameters/setReadBigInts/setReturnArrays`；`PRAGMA journal_mode=WAL` 生效；手写 `BEGIN/COMMIT` 事务正常；`backup` 导出可用。覆盖本项目全部需求。
4. **迁移成本已被吸收**：全部 SQL 收敛在 `repositories/` 下，若未来必须换驱动，改动面 = 一个 adapter 文件 + 一条新 ADR，不是重写。

已知代价与处置：
- **ExperimentalWarning 噪音**（Node 22 上 Stability 1.1）：启动脚本加 `--disable-warning=ExperimentalWarning`（实测生效），并登记为已知接受的权衡。
- **无 `transaction()` 辅助函数**：`repositories/db.ts` 提供 `withTransaction(fn)` 封装（手写 BEGIN/COMMIT/ROLLBACK，嵌套用 SAVEPOINT）补齐。
- **同步 API 阻塞事件循环**：全部查询强制走索引，禁止分析型 SQL；长耗时分析查询如需支持，另行迁移 `worker_thread`。
- **API 稳定性**：CI 与 Docker 锁定 Node 22.22.2 精确版本，不做跨大版本自动升级；升级 Node 时跑 DB 冒烟测试。

## Consequences
正面：零依赖零编译，安装与部署风险最低；WAL + prepared statement 性能足够支撑单机 Agent 负载；与 Node 运行时版本天然一致。
负面：Node 22 上属实验特性，次版本间 API 可能变动；无 `transaction()`/`pragma` 便利方法需自行封装；同步 API 在错误使用下会阻塞事件循环；无法使用 better-sqlite3 的部分扩展能力。
