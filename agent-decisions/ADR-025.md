# ADR-025: 重写 adapter 的 tool_calls 处理为「按 index 累积 + 流末 finalize」的纯函数归一化

## Status: Accepted (2026-10-22)

## Background

现有 `server/src/providers/openai-compatible.adapter.ts` 第 144-151 行把 `delta.tool_calls` 的 arguments 片段拼成普通文本 `delta` 发出：

```ts
const fragments = toolCalls
  .map((call) => (typeof call.function?.arguments === 'string' ? call.function.arguments : ''))
  .join('');
if (fragments.length > 0) return { type: 'delta', text: fragments };
```

纯问答场景无害（tool_calls 不出现），Agent 场景致命——丢三样东西：

- `id` → 回程 `role:"tool"` 消息无法匹配 `tool_call_id`，上游直接 400；
- `name` → 不知道调哪个工具，只能报 `TOOL_NOT_FOUND`；
- `index` → 并行调用无法归并，结果与调用错位。

这不是「可以后将就」的性能问题，是**协议层信息丢失**：丢的是调用的身份，而不是格式。

## Decision

新增 `server/src/providers/tool-call-normalizer.ts`，**纯函数、无 IO、可单测**：

```ts
export interface RawToolCallDelta { index?: number; id?: string; type?: string;
                                    function?: { name?: string; arguments?: string }; }
export interface NormalizedToolCall { index: number; id: string; name: string;
                                      rawArguments: string; arguments: Record<string, unknown>;
                                      parseError?: 'EMPTY_ARGS'|'INVALID_JSON'|'MISSING_ID'|'MISSING_NAME'; }

export function createToolCallAccumulator(): ToolCallAccumulator;
export function accumulate(acc, deltas: readonly RawToolCallDelta[]): void;
export function finalize(acc): NormalizedToolCall[];
```

算法：
1. 按 `index` 建 `Map`（缺失 `index` 的分片按 `0` 处理）。
2. `id` / `name` **取首个非空并锁定**，后续分片的空串或 null 不得覆盖。
3. `arguments` 片段**只 append 不解析**，直到 `finish_reason === 'tool_calls'` 或流结束才 `JSON.parse`。
4. parse 失败 → `parseError='INVALID_JSON'`，**产出失败结果 `TOOL_ARGS_INVALID` 并以 `tool_result{status:'failed'}` 回喂 LLM，不中断整轮**。
5. `id` 缺失 → 服务端生成 `call_<uuid>` 兜底（`role:"tool"` 必须带 `tool_call_id`）。
6. **空 `arguments`（无参工具）合法** → `arguments={}`，不算 `INVALID_JSON`。
7. 归一化结果**不立刻下发前端**——`tool_call` 事件要求参数是完整对象，故在 `finalize()` 之后才发。

adapter 侧改造：删除 L144-151；`UpstreamEvent` 扩展 `tool_calls` 与 `reasoning`；`[DONE]` 分支与**无 `[DONE]` 的异常收尾路径**都必须先 `finalize()` 再 yield `done`；`buildBody` 按能力表条件下发 `tools` / `tool_choice` / `parallel_tool_calls` / `tool_stream`。

**必测点**（`__tests__/tool-call-normalizer.test.ts`，10 条）：单调用三片拼接 / 后续分片空 `id`·`name` 不覆盖 / `index:0` 与 `index:1` 交错不串味 / 缺 `index` / arguments 截断 / 无参工具 / `id` 全程缺失 / `content` 与 `tool_calls` 同时出现（Kimi 已知行为）/ 无 `[DONE]` 异常收尾 / 上游 `arguments` 为对象而非字符串。

## Consequences

**正面**
- 调用身份（`id`/`name`/`index`）不再丢失，回程 `role:"tool"` 能严格一一对应，消除上游 400 与结果错位。
- 纯函数隔离可变状态，10 条测试点全部可在毫秒级跑完，不依赖网络与 provider。
- 与「`tool_call` 事件只在参数完整后才下发」的既有裁决天然吻合（架构 §8.1.1：不采用 `tool_call_delta` 三段式）。

**负面 / 代价**
- 新增一个文件 + 一个类型分支，adapter 行数上升（需按 ≤300 行门禁拆分，超出部分移入 `tool-call-normalizer.ts`）。
- 并行调用归并逻辑是本文件唯一有状态复杂度的部分，靠 T3/T4 两条测试守住。
- 若某 provider 的 `index` 语义非标（如始终为 0 但实际是多调用），仍会归并错；缓解是 T4 与 T7 的兜底 + 观察期日志告警。
