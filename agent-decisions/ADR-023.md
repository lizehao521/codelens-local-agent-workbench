# ADR-023: SQLite Schema 锁定 7 张表——补 `approvals` / `provider_capabilities` / `tool_results`，去 `artifacts` / `local_events`

## Status: Accepted (2026-10-22)

## Background

架构文档 §7.2 初版建 6 张表：`sessions` / `messages` / `tool_calls` / `artifacts` / `local_events` / `schema_migrations`。该版与架构文档自身的 API 清单（§11.1）和 PRD 验收标准存在三处硬冲突，本项目总监在 Phase 2 启动前实测发现：

1. **缺 `approvals`**：API 有 `POST /api/v1/approvals/:id`，AC-06 要求「服务端保存待执行调用、决定与参数绑定、不可篡改」，AC-04 第三条攻击场景要求「令牌不匹配 → 409 + 异常审计」。无表可落 → **直接违反两条 P0 验收**。
2. **缺 `provider_capabilities`**：API 有 `GET /api/v1/providers/capabilities`，AC-01 要求探测结果「不每轮试探」。无表可落 → 探测结果只在内存，进程重启即丢，AC-01 落空。
3. **缺 `tool_results`**：`tool_calls.result_ref` 指向它；L1 工具结果外置依赖 `artifact_path` / `inline_preview` / `sha256` / `bytes`。无表可落 → 长结果无处回查。
4. **多建 `artifacts`**：PRD v1.1 与 Spec §3 已判定「artifacts 面板」是 P1 Backlog，且长结果指针可由 `tool_results` 承载，单独建表是冗余 JOIN。
5. **多建 `local_events`**：PRD §14.5 与 Spec §3 已判定埋点沿用前端本地事件日志，服务端不落库；对应 `POST/GET /api/v1/events` 两个端点本期不实现。

## Decision

锁定 **7 张表**：

| 表 | 主键 | 承载 |
|----|------|------|
| `sessions` | `id` | 会话元信息 + `recovery_code_hash` + `device_token_hash` + 失败计数/锁定 |
| `messages` | `id` | 消息；`content` 纯文本 + `segments_json` 分段结构（C-6） |
| `tool_calls` | `id` | 工具调用审计（**规范名**落库 + `args_digest` + `result_ref` + 七态 `status`） |
| `tool_results` | `id` | 结果外置：`inline_preview` / `artifact_path` / `bytes` / `truncated` / `sha256` |
| `approvals` | `id` | 审批挑战 + 决定 + 异常审计计数；**决定一次性写入** |
| `provider_capabilities` | `(provider, model)` | 能力探测三态 `supported` / `unsupported` / `failed` |
| `schema_migrations` | `version` | 迁移版本 |

配套三条硬规则：

1. **审计不可篡改**：`approvals.decision` 只在 `decision IS NULL` 时写入（repository 层 `UPDATE ... WHERE decision IS NULL` 断言影响行数 = 1），数据库层由触发器 `trg_approvals_decision_once` 兜底（`RAISE(ABORT,'APPROVAL_DECISION_IMMUTABLE')`）。`tool_calls` / `approvals` **只追加**，不提供 UPDATE/DELETE 端点。
2. **凭证只存哈希**：恢复码 `sha256(code + sessionId)`、设备令牌 SHA-256、审批令牌 SHA-256。DB 文件泄露也伪造不出一次批准。
3. **artifact 文件仍落盘**（`SANDBOX_ROOT/.artifacts/<toolCallId>.json`），但**不建 `artifacts` 表**——指针放 `tool_results.artifact_path`，`fs.read` 可直接按路径回查（与 ADR-014 一致，零新增能力面）。

落盘 SQL：`docs/agent/schema.sql`（幂等，可直接 `db.exec()`）。叙述版：架构文档 §7.2。

## Consequences

**正面**
- AC-04 第三条攻击场景与 AC-06 有了物理落点，`POST /approvals/:id` 的 409 + 异常审计可验收。
- AC-01 的探测结果跨进程持久化，「不每轮试探」成立。
- `tool_calls.result_ref` 不再悬空；长结果可回查、可校验 `sha256`。
- 表数从 9（含两张已判不建的）收敛到 7，与 Spec §6 完全一致。

**负面 / 代价**
- `provider_capabilities` 从 Spec 给的 5 列扩到 12 列（承载 `GET /providers/capabilities` 响应契约与 OD-A3 的 `lightweightModel`）。若坚持只留 5 列，则该端点只能回内存静态表，AC-01 的持久化落空。
- `approvals` 从 7 列扩到 13 列（承载 `mismatch_count` / `last_mismatch_at` / `last_mismatch_detail` 异常审计）。7 张是 Spec 锁定的硬上限，故**不新增第 8 张审计表**。
- `sessions` 增加 `recovery_failed_count` / `recovery_locked_until`——AC-05「连错 5 次锁 15 分钟」不能只存内存（重启即失效）。
- 触发器引入 DB 层约束：`node:sqlite` 需 `db.exec()` 支持 `CREATE TRIGGER`（已可，无需扩展加载）。
