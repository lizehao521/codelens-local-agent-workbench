# ADR-012: Agent 循环采用单 Agent 状态机 + 工具编排，不引入多 Agent 协作与事件溯源

## Status: Accepted (2026-10-21)

## Background
通用 Agent 工具调用平台需要决定 Agent 循环的形态。可选：
- A. 单 Agent 循环（LLM ↔ 工具 ↔ LLM），循环逻辑显式状态机
- B. ReAct / Plan-and-Execute 等提示词范式作为唯一执行形态
- C. LangGraph / AutoGen / CrewAI 等框架托管的多 Agent 图
- D. 事件溯源（Event Sourcing）+ 完整状态回放

知识库 `references/architecture/ai-agent-patterns.md` 给出的成熟结论是「同模型+同需求，没有 Harness 只有 60% 完成率，有 Harness 达 98%」——即价值在 Harness（工程约束层），不在框架层。

## Decision
采用 **A：显式状态机的单 Agent 循环**，自研，不引入 Agent 框架。

状态机：`idle → thinking → (tool_call → awaiting_approval? → executing_tool → tool_result/tool_error → thinking)* → final → done`，终止态含 `done` / `error` / `aborted` / `budget_exhausted` / `max_iterations` / `circuit_open`。

理由：
1. **不选 C（框架）**：LangGraph/AutoGen 等框架会引入新的依赖树、自己的状态模型与事件循环，与本项目已有的 Express 分层、TypeScript 类型体系、SSE 契约全部冲突。核心诉求（工具注册表、双通道、审批、熔断）都要自己写，框架省不下多少代码却增加大量耦合。本项目的复杂度在**工具与安全**，不在编排拓扑。
2. **不选 B（纯提示词范式）**：ReAct 只作为**降级通道**存在（见 ADR-014），不能作为主形态——提示词解析的准确性不可控，无法保证工具名与参数的正确性。
3. **不选 D（事件溯源）**：完整状态回放需要持久化每一次中间状态并支持重放，对单机 MVP 是过度设计。本项目只持久化**消息与工具调用结果**（可审计、可回查长结果），不追求可重放执行。
4. **显式状态机的价值**：五个终止条件（T-1 正常 / T-2 超迭代 / T-3 超预算 / T-4 用户中止 / T-5 熔断）必须逐一可测、行为确定。状态机让「循环何时停、为什么停、停时留了什么」成为代码结构而非涌现行为。
5. **Harness 思路落地**：把「模型不可靠」的部分（工具名解析、参数校验、超时、重试、审批、失败回喂、熔断、预算）全部收进工程层，让 LLM 只负责「决定调哪个工具、传什么参数」。

硬约束：
- 最大迭代 12 轮、单次提问总超时 180s、同一轮工具串行执行（不并行）。
- 工具失败**不是**终止条件，而是一次负向 observation 回喂 LLM。
- 编排层不感知 HTTP：只产出事件对象，SSE 写出在 controller 层。

## Consequences
正面：循环行为完全确定可测；无框架依赖，与现有分层一致；工具/安全逻辑集中在一处，未来维护者有明确的改动入口。
负面：自研编排意味着边界情况要自己覆盖（预算竞争、中止与落库的竞态、审批挂起与会话恢复的交互）；单 Agent 拓扑不适合需要角色分工的复杂任务，但本期不在范围内。
