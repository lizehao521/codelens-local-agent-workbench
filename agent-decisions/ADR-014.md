# ADR-014: 工具注册表以 ToolDefinition 为核心，规范名（点号）与线上名（下划线）双轨，冲突用 `mcp.<serverId>.<tool>` 前缀消解

## Status: Accepted (2026-10-21)

## Background
核心需求是「易于扩展新工具」。四类工具（HTTP / 文件 / 计算系统 / MCP）来源异构：内置工具写死在代码里，MCP 工具运行时从 `listTools()` 动态获得且名字不可控。同时需要一个机制让用户能启禁用工具、按风险分组展示、以及为高危操作加审批。

需要决定：注册表的接口形态、动态工具如何并入、名字冲突怎么办、新增工具的流程如何标准化。

**一个跨文档冲突必须先裁决**：PRD §5.1 与 UIUX §3.1 都要求工具标识符用点号命名空间（`http.request` / `fs.read` / `mcp.filesystem.read_file`），但**所有 OpenAI 兼容 provider 强制校验 `tools[].function.name` 必须匹配 `^[a-zA-Z0-9_-]{1,64}$`——点号不在允许字符集内**。

证据（联网核实 2026-10-21）：
- OpenAI 官方文档：`name` "Must be a-z, A-Z, 0-9, or contain underscores and dashes, with a maximum length of 64."
- 实测错误：`Invalid 'tools.function.name': string does not match pattern. Expected a string that matches the pattern '^[a-zA-Z0-9_-]+$'.` —— HTTP 400，**整个请求被拒**（不是跳过单个工具）。
- 已有生产事故两起：某 Agent 框架因 MCP 工具名带点号（`aippt.doc_beautify`）在 DeepSeek 上 100% 失败；某插件因工具名 `demo.time` 上线即 400。
- 根因：MCP 规范允许点号，但 OpenAI 兼容协议层不允许——**协议转换层必须做名字消毒**。

## Decision
### 1. ToolDefinition 接口（锁定字段）
`name`（规范名，点号）/ `wireName`（线上名，下划线）/ `displayName`（人话名）/ `category`（`http|file|compute|mcp`）/ `description`（给 LLM 看，写清「何时该用」）/ `inputSchema`（JSON Schema draft-07 子集）/ `handler` / `timeoutMs` / `risk`（`low|medium|high`）/ `approvalMode`（`none|soft|hard|two_step`）/ `enabled` / `source`（`builtin|mcp`）/ `idempotent` / `maxResultChars` / `mcpServerId?`。

设计要点：
- `description` 是**给 LLM 看的**（决定工具选择准确率），`displayName` 是**给人看的**（设置页/审批条/示例任务），两者不混用。
- `inputSchema` 用 draft-07 **子集**（`type`/`properties`/`required`/`enum`/`items`/`description`），禁用 `$ref`/`oneOf`/`patternProperties`/数组上下界——DeepSeek strict 模式明确不支持这些关键字，传了会 400。
- `idempotent` 决定失败时是否允许重试（非幂等工具重试可能造成重复副作用）。
- `maxResultChars` 让每个工具自己声明结果体量上限，注册表据此在入上下文前截断。

### 2. 双轨命名制（本次裁决的核心）
| 轨道 | 形式 | 用途 |
|------|------|------|
| 规范名 canonical | 点号，如 `http.request`、`mcp.filesystem.read_file` | 内部标识、数据库落库（`tool_calls.tool_name`）、前端卡片展示、审计检索 |
| 线上名 wire | 下划线，如 `http_request`、`mcp_filesystem_read_file` | **仅**用于下发 LLM 的 `tools[].function.name` |

消毒规则（`utils/tool-name.ts` 的 `sanitizeToolName`，纯函数必须单测）：点号与其余非 `[a-zA-Z0-9_-]` 字符 → `_`；压缩连续下划线、去首尾下划线；不以字母开头则前置 `t_`；截断至 64 字符；冲突追加 `_2`/`_3`（**规范名不变**）。注册期校验规范名格式，不匹配直接抛错（加载期拒绝，不上线后才炸）。

**回程映射**：LLM 返回的是线上名，执行前用 `wireName → canonical` 反查表还原规范名再落库；反查失败 → `TOOL_NOT_FOUND`。

### 3. 风险是两维的，且是「工具 + 操作」的二元判定
- `risk`（`low`/`medium`/`high`）描述操作的潜在影响面；`approvalMode`（`none`/`soft`/`hard`/`two_step`）描述交互强度。**两个独立维度**（PRD §5.2）。
- `ToolDefinition.risk`/`approvalMode` 是**基线**；实际值在**调用时**由「基线 + 本次参数」判定，随 `tool_call` 事件下发，**前端不推断**（UIUX §3.8：前端不能成为安全判定的第二来源）。
- 典型升级：`http.request` GET → low/none，POST/PUT/PATCH/DELETE → high/hard；`fs.write` 新建/追加 → medium/soft，覆盖已有文件 → high/hard；`fs.delete` 删工作区根 → two_step。
- `two_step` 仅在显式升级时使用，是逃生舱不是常态。

### 4. 注册表能力
`register` / `registerAll` / `get` / `list(filter)` / `setEnabled` / `groupedByRisk` / `toProviderTools(names?)`。

**禁用的语义**（借知识库 `ai-agent-patterns.md` 的「权限感知 Function Calling」原则）：禁用的工具**不进入 `toProviderTools()`**——LLM 根本不知道它存在，而不是知道却不能用。已被 LLM 请求但已禁用 → `TOOL_DISABLED`。

**安全默认**：MCP 工具整体默认 `enabled=false`（PRD §5.3）；`high` 风险工具默认关闭。

### 5. 名字冲突消解
- 注册表主键是**规范名**：内置用 `http.request`；MCP 一律加 `mcp.<serverId>.` 前缀，如 `mcp.filesystem.read_file`。
- 因此**内置工具永远不会被 MCP 覆盖**。
- 多个 MCP Server 之间同名 → `serverId` 必须唯一（配置时校验）；仍冲突则拒绝注册第二个并返回明确错误。
- 前端展示用规范名 + 来源标签（内置 / MCP Server 名）。

### 6. 新增工具的标准流程（交付给未来维护者的契约）
8 步：① 定义 ToolDefinition（单一导出，文件名=工具名）→ ② 写 draft-07 子集 JSON Schema → ③ 写 handler（**不做**超时/审批/SSE 写出）→ ④ 风险定级（`risk`/`approvalMode`/`idempotent`/`maxResultChars`）→ ⑤ 在 `tools/builtin/index.ts` 集中登记 → ⑥ 加测试（正常/参数非法/超时/越界）→ ⑦ 在架构文档 §6.6 登记 → ⑧ 过门禁（≤300 行 + typecheck + test 全绿）。

MCP 工具的例外：schema 来自 `listTools()` 原样透传，但适配层必须校验其为合法 draft-07 子集（不合法则标记为仅 ReAct 可用），补齐 `risk`（MCP 工具默认 `high`，用户可调低但**不得**自动调高为 `low`）、`approvalMode`（默认 `hard`）、`timeoutMs`（默认 15s）、`category='mcp'`，并按 §2 生成规范名与线上名。

### 7. 执行器统一施加约束
`ToolExecutor` 负责：查表 → 查启用 → 参数校验（**字段级错误信息**）→ 运行期风险与审批判定 → 超时包装 → 重试 → 结果截断 → 落库 → 产出事件。工具 handler 自身**不做**这些事，保证所有工具的安全基线一致。

## Consequences
正面：新增工具的成本被固化为可检查的 8 步；内置与 MCP 工具在上层完全同构；点号命名在展示与审计层保持人类可读，同时满足 provider 硬校验；禁用语义正确；MCP 工具无法覆盖内置工具。
负面：多了一组「规范名 ↔ 线上名」的映射，映射表必须与注册表同生命周期（工具动态增删时同步维护）；消毒规则是纯函数但必须被**端到端测试**覆盖（注册带点号的工具 → 断言下发的是下划线名 → 断言 LLM 返回该名能反查回规范名）——单测拦不住这类问题，因为单测里工具名只是个字符串 key，从不经过 LLM；`inputSchema` 被限制在 draft-07 子集，牺牲部分表达能力换取 5 家 provider 兼容。
