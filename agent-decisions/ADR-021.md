# ADR-021: 错误处理采用分类表驱动 + 每工具熔断 + 循环检测 + 供应商降级链，不使用全局重试计数

## Status: Accepted (2026-10-21)

## Background
初稿架构（ADR-018）定义了「工具级有限重试 + 失败即负向观察 + 连续失败熔断 + 分层故障隔离」。PRD §8.1 / §8.2 / §8.3 在此基础上补充了四项要求，且都指向同一个问题——**重试预算该花在哪**。

PRD §8.1 给出的行业依据：ReAct 式 Agent 的重试预算约 90% 花在「永远不可能成功」的错误上，最典型是模型幻觉出一个不存在的工具名，用指数退避去重试一个字典里根本没有的 key——指数退避救不了它。

PRD §8.2 补充：**循环检测**（以 `(工具名, 参数归一化哈希)` 为键）、**每工具熔断器**、**任务级重试总预算 5 次**。
PRD §8.3 与 AC-08 补充：**供应商降级链**（主供应商连续失败 → 自动切下一个，界面明示）。

## Decision
### 1. 错误分类表驱动（替代全局重试计数）
| 错误类型 | 可重试 | 消耗重试预算 |
|---------|--------|-------------|
| 参数非法 / 不符合 schema | 否 | **否** |
| 工具不存在（幻觉） | 否 | **否** |
| 权限 / 路径越界 / SSRF 拦截 | 否 | **否**（且**同一被拒目标在任务内封禁**） |
| 目标不存在（404） | 否 | 否 |
| 限流 429 / 上游 5xx / 网络超时 | 是（最多 2 次，指数退避 **+ jitter**） | 是 |
| 工具执行超时 | 由模型决定 | 否 |
| 熔断打开 | 否（**直接快速失败，不触发 LLM 调用**） | 否 |

**关键区分**：参数非法 / 工具不存在 / 安全拦截这三类**不消耗重试预算**——它们是「确定性校验失败」，重试 100 次也是同样结果。立即回喂模型让��换参数或换工具，是唯一正确处理。

**HTTP 工具的额外约束**：仅幂等方法（GET/HEAD）自动重试；非幂等方法超时**不自动重试**（需重新确认，否则可能重复副作用）。

### 2. 任务级重试总预算：5 次
单任务内所有工具重试**合计**上限 5 次，超出后不再自动重试，只允许用户手动触发。计数器随任务生命周期，不是全局。

### 3. 每工具熔断器
同一工具在**本次任务内**连续失败 3 次 → 打开熔断 → 后续调用**直接快速失败，不触发 LLM 调用**（省一次往返，模型也不必为已知不可用的工具浪费轮次）。熔断状态在会话内可见（卡片标「已熔断」）。MCP Server 熔断独立计数，只影响该 Server 的工具。

### 4. 循环检测（`(工具名, 参数归一化哈希)`）
- 连续 **2** 次 → 注入 observation：「你正在重复同一个调用，请换参数或换工具」。
- 连续 **3** 次 → 判定死循环，**中止任务**，保留已完成结果，给出「检测到重复调用，已停止」+「从该步重跑 / 换路径 / 换工具」三个恢复入口。

参数归一化哈希：键排序 + **剔除易变字段**（`timeoutMs`/`maxBytes`/`maxEntries`/`contextLines`）后 JSON 序列化取 SHA-256。剔除是必要的——否则「同一调用只改了超时」会被误判为新调用，漏掉真正的循环。

### 5. 供应商降级链
- **触发**：同一供应商连续 **2** 次 5xx/429 且退避重试已耗尽（单次 5xx 不切——可能是瞬时抖动）。
- **范围**：仅在**用户已配置**的 provider 列表内，按设置页顺序；不自动切到未授权（无 Key）的 provider。
- **切换后**：换 provider+model，`meta` 事件重发（附 `switchedFrom`/`switchReason`）；**能力表按新 `(provider, model)` 重新判定**（不能假设新供应商也支持原生 function calling）；已产生的工具调用**不重放**，从当前轮继续。
- **上限**：单任务内最多切换 **2 次**，避免在多个坏供应商之间打转。

### 6. 工具失败仍是一次「负向观察」
分类表决定**是否重试**，但不改变「失败不终止循环」这一原则——失败被渲染成 observation 回喂 LLM，让模型决定换参数、换工具、走别的路径或向用户说明。安全拦截类错误的回喂信息**不含绕行建议**（防诱导模型反复撞墙）。

## Consequences
正面：重试预算花在真正可能成功的错误上；确定性失败立即回喂，模型能立刻改；熔断与循环检测防两类典型死循环（工具级与参数级）；供应商降级让上游抖动不中断任务；分层故障隔离保证 MCP/DB 故障不冒泡为循环终止。
负面：错误分类表是复杂度的来源，Phase 2 必须逐条覆盖测试（每类至少一例）；「不触发 LLM 调用」的熔断快速失败要求执行器与编排层解耦得更彻底；供应商降级会让 `meta` 事件在一个请求内多次重发，前端需处理；参数哈希的易变字段剔除规则需要可配置（不同工具的"易变"字段不同），但配置项过多本身是负担——故给出默认清单。
