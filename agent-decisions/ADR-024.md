# ADR-024: 审批令牌用 HMAC 绑定「会话 + 调用 + 工具名 + 参数摘要」，不匹配即 409 + 异常审计

## Status: Accepted (2026-10-22)

## Background

PRD §6.4 定下「服务端持有」原则：服务端保存待执行调用并签发令牌，客户端只回传决定。理由是一个已被公开指出的 human-in-the-loop 漏洞——**用户批准的内容与实际执行的内容不一致**。

Spec AC-04 把它写成可验收的第三条攻击场景：**若客户端提交的待执行内容与服务端令牌不匹配，服务端必须拒绝执行并返回 409 + 异常审计**。AC-06 同时要求审计「不可篡改」。

需要决策的是三件事：令牌绑定什么、如何校验、不匹配时留什么痕迹。

## Decision

**令牌结构**（`utils/hmac.ts` + `services/agent/approval.service.ts`）：

```
payload = `${sessionId}|${toolCallId}|${toolName}|${argsDigest}|${expiresAt}`
sig     = HMAC-SHA256(AGENT_APPROVAL_SECRET, payload) → base64url → 前 32 字符
token   = `t_${base64url(payload)}.${sig}`
```

- `argsDigest`：参数规范化哈希——键排序 + 剔除易变字段（`timeoutMs`/`maxBytes`/`maxEntries`/`contextLines`）→ `JSON.stringify` → SHA-256。与循环检测的键**共用 `utils/digest.ts` 同一函数**，保证「批准的参数」与「检测的键」口径一致。
- `expiresAt`：签发 + 300000（5 分钟）。
- 库里只存 `challenge_token_hash = sha256(token)`，**不存令牌明文**。

**校验链（顺序不可颠倒，任一失败即 409 + 异常审计）**：

1. `approvals` 查 `id` → 无 → `404 APPROVAL_NOT_FOUND`
2. `status != 'pending'` → `409 APPROVAL_ALREADY_DECIDED`
3. `now > expires_at` → 置 `status='expired'` → `410 APPROVAL_EXPIRED`
4. **令牌哈希恒定时间比较不匹配 → `409 APPROVAL_TOKEN_MISMATCH` + `mismatch_count+1`**
5. **服务端从 `tool_calls` 重算 `args_digest`，与 `approvals.args_digest` 不符 → `409 APPROVAL_ARGS_MISMATCH` + `mismatch_count+1`**
6. 通过 → 事务内写 `decision`/`reason`/`decided_at`/`status='decided'`（`WHERE decision IS NULL`，影响行数 ≠ 1 即抛 `APPROVAL_ALREADY_DECIDED`）

**请求体防线**：`POST /api/v1/approvals/:id` 的 zod schema 用 `.strict()`，body 只允许 `{ token, decision, reason? }`。出现 `arguments` / `toolName` 等任何其它键一律 `400 VALIDATION_ERROR`——**服务端绝不接受客户端提交的工具调用内容**。

**异常审计**：不匹配写入 `approvals.mismatch_count` / `last_mismatch_at` / `last_mismatch_detail`（`TOKEN_MISMATCH` / `ARGS_MISMATCH` / `EXPIRED` / `NOT_PENDING`）。累计 3 次 → 该挑战立即置 `status='aborted'`，不再接受任何决定。审计列只追加，不覆盖 `decision`（ADR-023 触发器兜底）。

**`allow_session` 作用域**：内存 `Map<sessionId, Set<"toolName:argsDigest">>`，仅本次会话进程内存活，不落库、不跨会话、不跨重启。

## Consequences

**正面**
- AC-04 第三条攻击场景有了确定的机器可判据与痕迹；AC-06「不可篡改」由「一次性写入 + 只存哈希 + 触发器」三重保证。
- 「批准的参数被改写」与「跨会话/跨调用批准」两类绕过被同一套 `argsDigest` 覆盖。
- `.strict()` 让「客户端塞内容」在第一道就 400，不进入业务校验。

**负面 / 代价**
- 需要 `AGENT_APPROVAL_SECRET`；缺省时进程启动生成随机密钥并告警，代价是**重启后所有挂起审批失效**（已接受：挂起审批本就只存内存句柄，重启即作废，会话恢复时标记 `aborted`）。
- 5 分钟过期对「用户思考很久」的场景偏紧；权衡是宁可让用户重新确认，也不让长有效期的令牌留在客户端。
- 每次提交都要重算 `argsDigest`（一次 JSON 规范化 + SHA-256），成本可忽略。
