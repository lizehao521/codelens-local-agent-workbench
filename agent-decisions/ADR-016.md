# ADR-016: SSE 事件协议在原 4 事件基础上扩展为 10 种，中划线命名，工具状态由 tool_result.status 承载

## Status: Accepted (2026-10-21)

## Background
CodeLens 现有 SSE 协议只有 4 种事件：`meta` / `delta` / `done` / `error`。Agent 平台需要向前端可视化工具调用过程（工具名、参数、进度、结果、耗时、错误、审批请求、上下文压缩），这超出了 4 事件的能力。

前后端必须共享同一份事件契约，否则必然漂移（这是知识库 `generated-code-failure-modes.md` 中「幻觉接口」的常见来源）。

UIUX §3.2 / §10.3 已按其自身假设写好了视觉状态机与渲染结构，并在附 D 中把 4 个问题交由架构裁决（A1 审批回执通道、A2 Message.content 粒度、A3 风险判定归属、A4 事件命名）。

## Decision
扩展为 **10 种事件**：`meta` / `delta` / `reasoning` / `tool_call` / `tool_progress` / `tool_result` / `tool_approval_required` / `context_notice` / `done` / `error`。

关键约定：
1. **帧格式不变**：`event: <name>\ndata: <json>\n\n`，沿用现有 `sendSSEEvent`。心跳沿用 15s `: ping` 注释帧。
2. **事件名用中划线（kebab-case）**，与 UIUX §3.2/§10.3 一致，不使用下划线（C-2）。
3. **文本增量事件保持 `delta` 不变**（C-3）。架构初稿曾提议改名 `token`，经对齐后**撤销**：现有前端 `stream.ts` 的 `case 'delta'` 已在消费该事件，改名收益为零、回归风险为正。UIUX §4.1 假设的 `text-delta` 一并对齐为 `delta`。
4. **不单设 `tool_rejected` / `tool_skipped` 事件**（C-7）：这类语义由 `tool_result` 的 `status` 字段承载。前端只需处理 4 个工具事件（`tool_call` / `tool_progress` / `tool_result` / `tool_approval_required`），不必为每个状态写分支。
5. **`tool_result.status` 锁定 7 值**，与 PRD §6.1 六态 + UIUX §3.2.1 衍生态一一对应：`pending` / `running` / `success` / `failed` / `timeout` / `rejected` / `skipped`。
6. **新增 `tool_approval_required`**：审批是安全机制的必要环节，若不显式建模，前端无法在流中挂起等待用户操作。事件携带 `approvalId` / `approvalToken` / `expiresAt`。
7. **新增 `context_notice`**：上下文压缩/截断必须对用户可见，否则用户会看到模型「忘记」了上下文却不知原因。
8. **审批回执走独立端点，不走 SSE 同流**（C-4）：`POST /api/v1/approvals/:id`，body 只含 `{token, decision, reason?}`。理由：审批可能跨数分钟，SSE 长连接不适合承载用户思考时长；且 PRD §6.4 的服务端持有原则要求——服务端把待执行调用持久化并签发 token，**绝不接受客户端提交的工具调用内容**（防「批准的与实际执行的不一致」漏洞）。决定后服务端在原 SSE 流上继续推送 `tool_result`。
9. **风险与确认档位由服务端判定并随 `tool_call` 下发**（C-5）：`risk` 与 `approvalMode` 两个字段，前端**不自行推断**——前端不能成为安全判定的第二来源。
10. **类型定义双向对齐**：`client/src/types/agent-events.ts` 与 `server/src/types/agent-events.ts` 必须是同一份内容（复制或代码生成），改一处必须改另一处。事件名 TS 联合类型是唯一事实源。
11. **降级时 `meta` 可发两次**：同一次请求内，后到的 `meta` 覆盖先到的（`mode` 变为 `react`）。该约定必须写进前端实现注释。
12. **事件 payload 全文见架构文档 §8.2**，每种事件给出 JSON 示例，作为前后端联调契约。

## Consequences
正面：工具调用全过程在前端完整可见（这是 Agent 产品的核心体验）；新增事件是纯增量，不破坏既有 4 事件的处理逻辑；类型文件双向对齐把契约漂移风险降到最低；7 个状态用 1 个事件承载，前端分支数最少；审批走独立端点使 SSE 流在长等待期间只需维持心跳。
负面：事件种类从 4 增至 10，前端分发逻辑变长（需按资源拆文件以守住 300 行门禁）；`tool_result` 的 `status` 是 7 值联合类型，前端 switch 需穷尽处理，漏一个会有静默渲染错误；「同一请求内可能两次 `meta`」是非直觉约定，必须有明确文档与测试。
