# ADR-018: 重试与降级采用「工具级有限重试 + 失败即负向观察 + 连续失败熔断 + 分层故障隔离」

## Status: **Extended by ADR-021 (2026-10-21)**

> **本 ADR 已被 ADR-021 扩展**：PRD §8.1/§8.2/§8.3 补充了①**错误分类表驱动**（替代全局重试计数，确定性校验失败不消耗重试预算）②**任务级重试总预算 5 次** ③**循环检测**（`(工具名, 参数归一化哈希)`，2 次注入 observation / 3 次中止）④**供应商降级链**（主供应商连续失败 → 自动切换，界面明示）。
> 本 ADR 仍然有效的部分：失败即负向观察（不崩循环）、错误信息可操作化、分层故障隔离（SQLite 内存降级 / MCP 隔离）、上游错误归一化与脱敏。**重试矩阵与熔断细节请以 ADR-021 为准。**

## Background
Agent 循环中任何一环都可能失败：工具超时、HTTP 5xx、上游限流、SQLite 锁冲突、MCP Server 崩溃。若任一失败都终止循环，Agent 几乎不可用；若无限重试，循环永不结束。必须定义失败的处理方式与终止边界。

## Decision
### 1. 核心原则：工具失败不是终止条件，而是一次「负向观察」
失败被渲染成 observation（原生通道用 `role:"tool"` 消息，ReAct 通道用 ```` ```tool_result ```` 块）回喂 LLM，让模型自己决定：换参数重试、换工具、走别的路径、或直接告知用户失败。同时向客户端发 `tool_error` 事件（前端展示错误，但对话流不中断）。

**错误信息给 LLM 时必须可操作**（含哪个参数不合法、期望类型、可用工具名），但**不得**包含内部堆栈、绝对路径、数据库结构、内网拓扑（防死循环与信息泄露）。

### 2. 工具级重试矩阵
| 错误 | 可重试 | 次数 | 退避 |
|------|--------|------|------|
| `TOOL_TIMEOUT` | 是 | 1 | 500ms（仅幂等工具） |
| `TOOL_NETWORK_ERROR` | 是 | 2 | 500ms → 1500ms（仅 GET/HEAD） |
| `TOOL_EXECUTION_ERROR` | 是 | 1 | 500ms（仅瞬时故障） |
| `MCP_CALL_FAILED` | 是 | 1 | 800ms |
| `TOOL_ARGS_INVALID` / `TOOL_NOT_FOUND` / `TOOL_DISABLED` / `TOOL_DENIED` / `SSRF_BLOCKED` / `PATH_JAIL_VIOLATION` | 否 | 0 | — |

**硬约束**：单次工具调用总耗时（含重试）不得超过其 `timeoutMs` 的 **2 倍**。

### 3. 连续失败熔断
- 同一轮迭代内连续工具失败达 3 次（`AGENT_CIRCUIT_THRESHOLD`）→ 停止执行工具，把失败摘要作为 observation 回喂让 LLM 收尾，终止原因 `finishReason=circuit_open`。成功一次即重置计数。
- **MCP Server 独立熔断**：单个 Server 连续失败 3 次 → 标记 unhealthy → 其工具从 `toProviderTools()` 移除。**不影响其他 MCP Server，不影响内置工具。**

### 4. 上游 LLM 错误归一化
| 上游情况 | 错误码 | 可重试 | 降级动作 |
|----------|--------|--------|----------|
| 连接失败 / 5xx | `UPSTREAM_ERROR` | 是 | 退避重试 2 次（500/1500ms） |
| 超时（>60s） | `UPSTREAM_TIMEOUT` | 是 | 重试 1 次；仍超时则让 LLM 收尾或报错 |
| 401 / 403 | `UPSTREAM_AUTH_ERROR` | 否 | 立即结束，统一文案（**不区分 Key 无效与欠费**） |
| 429 | `UPSTREAM_RATE_LIMITED` | 是 | 读 `Retry-After`（上限 10s）后重试 2 次 |
| 400 且匹配 tool 相关 | `UPSTREAM_TOOL_UNSUPPORTED` | 否 | **切换 ReAct 通道重试本轮**（L1 探测） |
| 400 其他 | `UPSTREAM_BAD_REQUEST` | 否 | 结束，不透传原始报文 |
| 流中断（已有部分内容） | `UPSTREAM_STREAM_INTERRUPTED` | 否 | 结束并**保留已产生内容** |

**强制脱敏**：所有上游错误信息经 `maskKey()` 处理后才可进日志与响应。绝不透传上游原始报文（可能含 Key 回显或内部端点）。

### 5. 通道降级
见 ADR-013。核心补充：降级切换发生在同一轮内是允许的（原生失败 → ReAct 重试本轮），此时需再发一次 `meta`（`channel=react`, `degraded=true`），**前端约定后到者覆盖**。

### 6. SQLite 故障降级
读失败 → 降级为**内存模式**，当前请求继续跑（工具执行与 LLM 调用不依赖 DB），明确告知用户「会话持久化不可用」。写失败 → 丢弃该条写入，不阻断循环，累计失败 >5 次则完全切内存模式。**启动时 DB 不可用不拒绝启动**：服务已上线过，DB 坏了直接不启动会导致整体不可用，降级可用性更重要（健康检查返回 `degraded: true`）。

### 7. MCP 故障隔离
MCP 的任何故障只影响 MCP 工具自身，通过「工具级错误 → observation 回喂 → 熔断移除」两条路径消化，**绝不冒泡为循环终止**。

## Consequences
正面：单点失败不会击溃整个 Agent 运行；每类错误都有明确的终止/重试/降级路径，可逐一测试；重试有上限与时间预算，不会无限循环；MCP 与数据库故障被隔离在各自边界内。
负面：错误矩阵本身是复杂度的来源，Phase 2 实现时必须逐条覆盖测试；「失败回喂 LLM」可能诱导模型反复重试同一失败工具（靠熔断 + 错误信息可操作化缓解）；上游错误分类依赖对 provider 错误格式的经验判断，可能需要按实测调整。
