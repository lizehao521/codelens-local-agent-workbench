# 性能优化

> 先测量、后优化、再复测——没基线的"优化"是碰运气。

## 何时使用

- 观察到响应慢、CPU/内存占用过高、超时。
- 上线前需要满足性能指标（延迟/吞吐/内存）。
- 需要定位并消除真正瓶颈而非"凭感觉改"。

## 执行流程

1. **建基线** —— 明确性能指标（时延/吞吐/内存），测得优化前数字。
2. **Profiling 定位** —— 用剖析工具/日志找出耗时与内存热点，锁定前 1~2 个真瓶颈。
3. **假设验证** —— 对瓶颈问 5Why 追根因，形成可检验的优化假设。
4. **优化** —— 做最小改动（算法/缓存/并发/IO/索引/数据结构），一次只改一个变量。
5. **复测** —— 与基线对比确认收益，无收益则回退；记录改动与数据。

## 输入 / 输出

| 输入 | 输出 |
| --- | --- |
| 程序 / 热点对象 | 瓶颈定位 + 根因 |
| 性能指标与目标 | 优化改动 + 前后对比 |
| 剖析结果 | 复测数据 |

## 关联思维策略

- **5Why** —— 从"慢"追到根因（算法差？重复 IO？锁竞争？）。
- **第一性原理** —— 回到计算量/IO 量的本质，而非堆硬件。
- **对比分析** —— 关键路径与最优实现/基线对比，找差距。

## 基因库记录

- **类型**：pattern
- **复用经验**：先测量后优化；一次只改一个变量便于归因；无收益应立即回退，避免为优化引入回归。
- **可复用性**：高 —— 通用。
- **入库自检**：用户选择 ✅ / 适应度前 100 ✅ / 可复用 ✅

## 示例

### 场景：接口耗时从 3s 降到 200ms

1. 基线：平均 3s、P95 5s。
2. Profiling：每请求 500 次冗余 DB 查询。
3. 根因：N+1 查询；假设：批量一次取出可降 IO。
4. 优化：改批量查询 + 结果缓存。
5. 复测：平均 200ms、P95 350ms，行为不变。

## 安全与回滚

- **透明**：基线、改动、复测数据全记录。
- **可控**：一次一处改动，可单独回退。
- **可逆**：改动前快照，无收益即回退。
- **渐进**：先解决最大瓶颈，再评估次要项。
- **用户主导**：是否接受"用缓存换一致性"等权衡由用户决定。

## 工具对齐（当前异结构工具面）

- perf-regression —— capture 采样算 p50/p95/mean；save 存基线；compare 按阈值报回归（缺基线=报错，绝不是"0 回归"）。
- cache-design —— simulate/compare：对时间线 workload 离散仿真命中率/羊群事件/缓存峰值，先仿真再落地。
- perf-regression compare 只吃落盘的基线文件路径：传内存对象报 EISDIR，路径不存在报 baseline file not found —— 要比对必须先把基线 save 到文件。
- perf-regression 冷/热基线差 7.4 倍（实测 194.8ms vs 26.3ms）：「优化前后对比」必须先确认两边同热度，否则会把冷启动差异当成巨大收益。
