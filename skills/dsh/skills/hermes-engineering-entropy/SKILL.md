# 🧹 工程熵治理（v2.0 进化版）

**第一性原理**：工程熵增来自四类根因——

1. **重复造轮子**（同构脚本几十个变体 / 平行传话层各长一套）；
2. **噪声膨胀**（缺 `.gitignore` 致 `node_modules`+`*.map` 占掉九成文件）；
3. **无导航文档**（多端项目无 README，等于 AGI 没有地图）；
4. **文档失真**（README 把「规划中」写成「已实现」，AGI 据错误世界模型决策）。

熵减的最高杠杆 = **归纳去重 → 软隔离（可逆）→ 根因 gitignore → 文档世界模型 → 机器可对账**，而不是直接硬删。
治理不是「删文件」，而是**先软化、再治根因、最后让文档能被机器复算**。

## 与 hermess / DSH Agent 的深度融合

熵治理不是拍脑袋删东西，每一步都落到**确定性工具**上，产物可复核：

| 治理动作 | hermess 引擎支撑 | DSH 工具面 | 产物 |
|---|---|---|---|
| 熵增扫描 | — | `code-audit`（scan/dup/stats/untested，按真实字节与内容哈希） | 总文件/按扩展名行数/god-files/重复组/无测试模块 |
| 软隔离与回滚 | write-guard 写闸 | `git-snapshot`（init/snapshot/diff/status/restore，fs SHA-256 manifest 后端） | pointId + undo 句柄 |
| 配置与边界 | — | `config-diff`（merge/diff/secret-scan，逐 key 溯源） | 漂移叶路径 + 密钥暴露状态 |
| 依赖去重 | — | `dependency-audit`（audit/lockcheck，静态无网络） | 浮动版本/dev-prod 重复/幽灵 import/许可证 |
| 文档锚点对账 | **bench-truth 台架数机器对账** | `test-runner`（run/tap/plan/runSuites） | 文档声明 vs 实测事实，漂移即红 |
| 能力变更留痕 | **capability 能力基线** | — | 工具/技能/组合/预设四面哈希 |

> 复制工具文档 = 又一次熵增（这正是 E1 要治的病）。

## 熵治模式库（E1–E6）

### E1 归纳去重（pattern-001/034）
- **场景**：同一类任务几十个变体脚本散落；两个库各实现一套传话层。
- **做法**：先用 `code-audit dup` 按**内容哈希**列出真实重复组（不靠肉眼），再归纳同构脚本 → 少量核心文件（公共库 + 工具集 + 策略匹配）。
- **经验**：去重前先确认「是否真同构」——靠文件结构 / 接口签名比对，不靠印象。**哈希相同是铁证，长得像不是。**

### E2 软隔离（pattern-034）
- **场景**：要删冗余备份 / 散落脚本 / 性能报告，直接删不可逆、风险高。
- **做法**：先 `git-snapshot` 留机械回滚点（拿 pointId + undo 句柄），再把待删物移入 `_rollback/` 子目录；确认无引用后再清；README 存档「被删清单」保可追溯。
- **经验**：① 不可逆操作必须**软隔离**，不是可选项；② 清空前必须记录被删清单，否则丧失可追溯性；③ 文档要区分「现状 vs 规划」，避免超前失真。

### E3 根因 gitignore（pattern-034）
- **场景**：一个仓几万文件，九成是 `node_modules`+`*.map` 噪声。
- **做法**：先 `code-audit stats` 按扩展名度量噪声占比（真实字节，不估算），再为对应目录生成 `.gitignore`（`node_modules/`、`dist/`、`*.map`、`.env`），从**度量上**消除噪声膨胀。
- **经验**：膨胀根因九成是**缺 `.gitignore`**，而非代码本身——先隔离噪声再评估本质（pattern-011：无度量无优化）。**只数噪声不补 gitignore，清完又涨。**

### E4 文档世界模型（pattern-034）
- **场景**：多端架构无统一入口，AGI / 新人无法导航。
- **做法**：根目录 `README.md` 用架构图 + 目录导航表串联各端，标注共享范式与快速开始；**并且**让关键数字（版本 / 台架数 / 能力面）成为可被机器复算的锚点。
- **经验**：文档即世界模型——无 README 等于无导航。但**地图也会漂移**：只写不验的文档，三个月后就是错的。

### E5 双库分叉识别与合并
- **场景**：两个平行代码库分叉，公共范式各自生长、基因库分裂。
- **做法**：识别为高价值长周期项，给可执行清单——① `code-audit` + `config-diff` 列两库重叠面；② 以「公共 helper」为迁移单元先抽公共层；③ 每迁移一个即跑两库单测 + import 闭合审计（pattern-019）；④ 保留薄封装向后兼容；⑤ 迁移进度 = 已统一 helper / 重叠面总数（可度量）。
- **经验**：双库分叉是进化熵增的隐蔽源头——必须识别并规划合并主干，否则平行生长永不停止。

### E6 机器可对账（本版新增 · 融合 hermess）
- **场景**：README 写着「全绿」，但没人知道这是跑出来的还是抄来的。
- **做法**：把文档里的关键事实分成**声明**与**事实**两类；事实必须有机器真相源（版本 = `package.json.version`；台架数 = 实测；能力面 = 能力基线哈希），并在校验脚本里比对声明与事实，**漂移即红**。
- **经验**：E4 的地图会漂移，E6 是钉住地图的钉子。**「文档写完就不管」是文档失真的唯一根因。**

## 通用执行协议（结晶 SOP）

```
1. 熵增扫描   → code-audit（stats/scan/dup/untested）        出量化基线
2. 归纳去重   → 同构判定 + 抽公共层（E1）
3. 软隔离     → git-snapshot 留点 + 移入 _rollback/（E2）     出 pointId
4. 根因治理   → 补 .gitignore / 依赖去重（E3 + dependency-audit）
5. 文档世界模型 → README 架构图 + 目录导航表（E4）
6. 机器可对账 → 锚点声明 vs 实测事实比对，漂移即红（E6）
7. 分叉合并   → 双库重叠面清单 + 迁移进度（E5，长周期）
```

- **可逆优先**：任何删除类操作先留回滚点再软隔离，确认无引用再清。
- **治根因不治现象**：噪声膨胀先补 `.gitignore`，别去数文件；重复代码先抽公共层，别逐文件改。
- **文档即地图，地图要钉住**：无 README 即无导航；有 README 无对账即会漂移。

## 安全原则（M 系四闸 · 对齐进化引擎）

1. **透明** — 清理清单在 README 可见，被删物留档可追溯。
2. **可控** — 软隔离可随时还原（`git-snapshot restore` 自带 undo 句柄）。
3. **可逆** — 回滚点 + 软隔离是必走步骤，非可选项。
4. **渐进** — 先快赢（清理 / gitignore / README），长周期项（双库合并）排期推进。
5. **导入一致性** — 合并双库时凡移动 / 重命名符号必做全仓 import 闭合审计（pattern-019）。
6. **不注水** — 度量一律来自真实字节与真实哈希；缺数据写「未执行」，不估算、不编造。

---

## 反模式（pitfall）

- **直接硬删**：跳过回滚点直接 `rm`，误删不可还原，违反可逆原则。
- **文档超前失真**：README 把「规划中」写成「已实现」，使 AGI 据错误世界模型决策。
- **只数噪声不补 gitignore**：清完又涨，根因未治。
- **靠肉眼判重复**：同构判定必须走内容哈希与接口签名，眼见不为实。
- **文档写完不钉**：没有机器对账的文档，三个月后必然失真。

## 与 v1.0 的差异（哪些内容不适合现在，已改）

v1.0（上传版）是一份**针对某次具体清理战役**写的结案报告式技能，其中若干事实已不适用于当前环境。本版按「方法可复用、事实不写死」原则进化：

| v1.0 内容 | 本版处理 | 理由 |
|---|---|---|
| 「某前端仓 4 万+ 文件中 95% 是 `node_modules`+`*.map`」 | **改为度量口径**（先 `code-audit stats` 再判占比） | 那是另一个仓的历史测量值，写死会误导；方法可复用，数字不可 |
| 「`hermess` 与 `hermess-agent` 双库分叉」 | **退成方法论**（E5 只讲识别与合并清单） | 本工作区为单库 `hermess/`，具体库名不再成立 |
| `_TRASH_/` 软隔离约定 | **改为 `git-snapshot` + `_rollback/`** | 与本宿主既有约定一致（`_rollback/` 是实际在用的回滚点目录） |
| E4 文档世界模型 | **增强为 E4 + E6 机器可对账** | 只写不验的文档必然漂移；hermess 的 bench-truth 实践正是解法 |
| 无度量环节 | **补熵增度量基线**（真实字节 / 内容哈希） | pattern-011：无度量无优化；E3 的「先度量后治理」需要它 |
| pattern-034 / 019 出处标注 | **保留**（provenance） | 来源是事实，不因环境变化而失效 |

> **保留的第一性原理不变**：熵增来自「重复造轮子 + 噪声膨胀 + 无导航文档」，治理要先软化再治根因。这条在任何仓库都成立。

## 前提与边界

- E3「膨胀根因九成是缺 `.gitignore`」：前提是**该仓受 git 管辖**。仓不在 git 下时补 `.gitignore` 对磁盘占用**零作用**，得改走「先量化占用来源再定处置」（实测：本仓 `git rev-parse --is-inside-work-tree` 报 not a git repository，`.gitignore` 只有 1 行 `/.hermess-snapshots`，而磁盘主占用是 6588 个 `.bak` / 458.8 MB，补 gitignore 一个字节都减不掉）。
