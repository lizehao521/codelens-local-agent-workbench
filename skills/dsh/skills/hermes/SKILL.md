# Hermes｜版本升级协议

> Hermes 是信使：把项目的契约完整带过版本边界，一条不丢。
> 旧版本冻结不动，新版本继承后增量演进；边界先写成标准，再写成代码。

## 何时使用

- 把 Vn 升级为 Vn+1，或新建下一版本文件夹
- 框架逻辑出现结构性问题：职责混同、边界不清、静态层与动态层不分
- 需要在不破坏旧版本冻结基线的前提下演进

## 第一步｜判定升级级别（先判定，再动手）

| 级别 | 判据 | 动作 |
|---|---|---|
| L1 认知层 | 只需新增文档 / skill / 契约，引擎不用改 | 旧版本内直接升级，跑全量回归即可 |
| L2 引擎层 | 需要新增模块或能力，旧模块不动 | 新建 Vn+1 文件夹，继承后增量实现 |
| L3 结构层 | 需要修改已冻结模块 | 在 Vn+1 中重命名版本号，改清单 `path` + 引用方 `import` 两处，旧→新对照登记进历史对照表 |

## 执行流程（八步）

1. **诊断**：用 grep / 测试 / 引用扫描把问题证据化列出，不凭感觉写"有问题"。
2. **边界标准先行**：先写标准文档与硬规则（违反即抛错），再写实现代码。没有标准的代码是又一次边界漂移。
3. **建新版文件夹**：复制上一版 → 删除上一版专属构建产物（构建产物永远由构建重新产出）。
4. **继承映射**：逐条登记「继承 / 修改 / 新增 / 删除」+ 理由，放进总控目录。
5. **增量实现**：新模块只依赖共享契约层，不偷改旧模块。
6. **闭集登记**：模块清单四处登记（`modules` / `testSuites` / `artifacts` / `publicApi`），漏登记 = 测试红。
7. **测试 → 构建**：先 `run_all` 后 `build`；顺序颠倒会让启动器显示旧计数。
8. **报告三类不外推**：静态检查 / 单元测试 / 浏览器点击分别登记；未执行必须写"未执行"。

## 边界问题专用判据（主线 / 支线、静态 / 动态类）

- **静态层 = 声明式骨架**：运行时只可推进 / 完成，不可新增或删改节点；运行时注入骨架节点 = 抛错。
- **动态层 = 运行时实例**：可开关，但每个实例必须有声明来源（def）与明确的闭合路径（完成 / 失败 / 到期）。
- **跨轨写状态 = 越界**：支线结算直接写主线状态（或反之）必须抛错，只允许通过世界状态间接影响资格与权重。
- **焦点唯一**：主线进行中节点数 = 1；支线并发数有上限。
- **每次路由可审计**：返回 track / layer / 依据 trace，供门禁与人工复核。

## 输入 / 输出

| 输入 | 输出 |
|---|---|
| Vn 项目 + 问题描述 | 升级级别判定 + 新版文件夹 |
| 框架问题（模糊） | 证据化诊断 + 边界标准文档 |
| Vn 基线 | 继承映射表 + 增量模块 + 测试报告 |

## 禁止事项

- 在 Vn 上直接修改已冻结引擎
- 删除、覆盖旧版本的任何文件
- 未登记就往 `40_程序标准` 或测试目录新增文件
- 跳过测试先构建
- 把"未执行"写成"通过"，把 BLOCKED 写成 FAIL
- 用 fallback 掩盖缺失（候选拦完返回空结果）

## 一句话口令

> 先诊断出证据，先定标准再写码；旧版冻结、新版继承、闭集登记、测试先于构建；
> 每次跨界，契约一条不丢。
