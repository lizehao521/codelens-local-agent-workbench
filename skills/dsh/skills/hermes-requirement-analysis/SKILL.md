# 需求分析

> 目标不是"记录他说了什么"，而是"搞清楚他真正要解决什么问题"。

## 何时使用

- 诉求模糊，只有一句想法或目标。
- 多人对"要做什么"理解不一致。
- 需要明确范围、边界与验收标准再动手。

## 执行流程

1. **复述诉求** —— 用自己的话把诉求讲一遍，确认理解一致。
2. **5Why 追问** —— 连问"为什么"，找到背后真正的目标。
3. **拆解条目** —— 拆成功能项 / 非功能项 / 约束项。
4. **划边界** —— 明确"做什么"与"不做什么"。
5. **定验收标准** —— 每条给出可检验的完成标准。
6. **输出需求清单** —— 逐条带优先级，交用户确认。

## 输入 / 输出

| 输入 | 输出 |
| --- | --- |
| 一句诉求 / 原始描述 | 需求清单（功能/非功能/约束） |
| 相关方与背景 | 边界与不在范围内说明 |
| 优先级信号 | 验收标准 |

## 关联思维策略

- **第一性原理** —— 剥离表面表述，回到本质目标。
- **5Why** —— 逐层追问定位真实意图。
- **归纳推理** —— 从碎片信息归纳出结构化需求。

## 基因库记录

- **类型**：strategy
- **复用经验**：先复述对齐，再拆解；每条需求都要可达"可检验的验收标准"。
- **入库自检**：用户选择 ✅ / 适应度前100 ✅ / 可复用 ✅

## 示例

废话需求「做个报表」→ 澄清：给谁看、看哪些指标、多久更新 → 拆成数据源/指标/视图/权限 4 项 + 验收标准。

## 安全与回滚

- **透明 / 可控 / 可逆 / 渐进 / 用户主导**：澄清只问不改，边界与验收由用户拍板。

## 工具对齐（当前异结构工具面）

弱对齐：ask_user_question 只用于"用户拥有、检查答不出"的取舍；边界与验收评审走计划模式/exit_plan_mode；核心是澄清推理。
