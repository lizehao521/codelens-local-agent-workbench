# 代码审查

> 审查的目标不是挑错，而是让问题在上线前以最低成本暴露。

## 动作核

**审完必须交出一份分级清单，每条含四件：定位（文件:行）· 根因 · 修复建议 · 级别。**

缺任何一件都不算完成：

- 只写"这里有 bug"、不写根因 —— 不算完成。
- 只写根因、不写定位 —— 不算完成。
- 只给级别、不给修复建议 —— 不算完成。
- **分不出级别时不许硬套** —— 写明"判不了"和缺什么才能判。

## 何时使用

- 代码提交前 / 合并前的评审。
- 接手他人代码，需要快速建立质量认知。
- 定位难以复现的缺陷，需要通盘排查。
- 上线 / 发版前的最后一道把关。

## 执行流程

1. **明确审查目标** —— 确认范围（提交 diff / 模块 / 全量）、关注点与放行标准。
   做不出这三样就别开始：范围不定则清单无法收敛，放行标准不定则分级无依据。
2. **通读结构** —— 先看目录与调用关系，再进入逐文件、逐函数细节。
   先建立"这个系统由几块组成、谁调谁"的框架，否则逐文件看会得出互相矛盾的结论。
3. **四象限核查** —— 对每个单元从四维度走一遍（清单见下一节）。
4. **5Why 追根因** —— 对每个问题问"为什么"，定位根因而非表象。
   停在"这行写错了"是表象；追到"这里没有校验的前提"才是根因。
5. **分级清单** —— 按「阻断 / 重要 / 建议 / 风格」输出问题清单 + 修复建议 + 定位。

## 判据：什么算审完

逐项勾，**任何一项为否，结论就只能写"未审完"**：

- [ ] 审查范围写明了（审了哪些文件 / 哪个 diff，没审什么也要写）。
- [ ] 四条判据都走过一遍（正确性 / 安全 / 性能 / 可维护性），**没查的那条要写明"未查"**。
- [ ] 每条问题都有 定位 + 根因 + 修复建议 + 级别。
- [ ] 分级有依据（见「分级标准」），不是"感觉像重要的"。
- [ ] 给出了放行结论：可以放行 / 修完哪些才能放行 / 不放行。
- [ ] 列出了**已知未覆盖的面**（哪些地方这次没看、为什么）。

> 最后一项最容易被省，但它决定了这份清单能不能被信任：**一份不说"我漏了什么"的清单，读者无法判断它的边界。**

## 四象限核查清单

### 正确性

- **边界**：空集合 / 单元素 / 最大 / 溢出 / 零 / 负数。
- **空值**：null / undefined / 空字符串 / 缺字段。
- **异常路径**：抛了谁接、接不住会怎样。
- **并发**：同一资源被两处同时改 / 读时被改。
- **类型**：隐式转换、精度、时区、编码。
- **排序与比较的隐含前提**：按字符串排还是按数值排？依赖"格式统一"的地方，那个前提被校验了吗？

### 安全

- **注入**：拼接出来的命令 / SQL / 路径 / 正则。
- **路径**：`..` 与符号链接能否越出预期目录。
- **越权**：身份从哪来、能不能伪造、有没有校验归属。
- **敏感信息**：密钥 / token 出现在日志、错误信息、返回值里。
- **依赖**：浮动版本、已知漏洞、来源是否可信。
- **求值**：`eval` / `new Function` / `vm` —— 以及**参数从哪来**（不可达的动态求值不是缺陷，要写明"当前不可达"）。

### 性能

- **复杂度**：嵌套循环、循环内查询、循环内 IO。
- **多余 IO**：同一文件重复读、同一次调用重复建连。
- **内存**：无界缓存、累积数组、大对象持有。
- **前提**：性能结论必须带**同热度**的对照 —— 冷态与热态可以差数倍，测错一头就是假收益。

### 可维护性

- **命名**：名字说的是不是它做的事。
- **重复**：同一逻辑几处实现；以及**它们是否真同构**（靠接口签名比对，不靠"长得像"）。
- **职责**：一个函数是否在做两件无关的事。
- **可测试性**：能不能在不启动整个系统的前提下测到它。
- **注释与代码是否一致**：注释说的和代码做的不一致时，**两者都可能错**，以实测为准。

## 分级标准

| 级别 | 判定边界 | 处理 |
| --- | --- | --- |
| **阻断** | 会造成数据损坏 / 安全越权 / 线上不可用；或有**当前可达**的确定性错误 | 不修完不放行 |
| **重要** | 条件成立时才触发，或触发后损失可恢复但代价大 | 本次修，最迟下个版本 |
| **建议** | 不影响正确性，但会增加后续成本（重复、难测、难读） | 排期 |
| **风格** | 纯粹一致性偏好，改了与不改都正确 | 可选 |

**两条不许含糊**：

- **"重要"不等于"看起来严重"** —— 判定要落在"什么条件下会触发、触发了损失多大"。
- **当前不可达的问题不得判阻断** —— 例如动态求值面存在但所有调用点都不传用户输入，此时应判"重要"并写明"当前不可达"。
  把它判成阻断，会让真正的阻断被淹没。

## 输入 / 输出

| 输入 | 输出 |
| --- | --- |
| 代码 / diff / 仓库路径 | 分级问题清单 |
| 审查标准 / 放行条件 | 逐条建议 + 根因 + 定位 |
| 安全/性能红线 | 是否放行的结论 |
| —— | 已知未覆盖的面（这次没看什么） |

## 关联思维策略

- **对比分析** —— 与规范、最佳实践、历史正确实现做对照。
- **5Why** —— 从症状追到根因，避免只改表象。
- **红队演练** —— 假设自己是攻击者/恶意输入，找漏洞。

## 基因库记录

- **类型**：pattern
- **复用经验**：先通读结构再抠细节；问题必须分级并给出根因，不能只报"有 bug"。
- **可复用性**：高 —— 任何语言、任何规模都适用。
- **入库自检**：用户选择 ✅ / 适应度前 100 ✅ / 可复用 ✅

## 示例

### 例一：假设场景（走一遍格式）

1. 目标：登录接口 + token 校验逻辑。
2. 正确性：空 token、过期、并发请求 → 发现一处空值未判。
3. 安全：token 用弱随机数生成 → 判「阻断」，建议改用安全随机源。
4. 成果：输出 1 阻断 + 2 重要 + 3 建议，附定位与修复方案。

### 例二：真实审查（含"根因靠硬读数确认"）

被审对象：一个证据链模块的入账与读取两个函数。

**找到的问题**：读取函数按 id 的**字典序**排序后取末 N 条，用来当"最近 N 条"。

**根因（5Why）**：

```
Why1 为什么可能取错？  它排的是 id，不是时间。
Why2 为什么用 id 排？  id 形如 dec-0001，零填充后字典序 == 数值序 == 时间序。
Why3 零填充谁保证？    创建 id 的那段代码 —— 这里没有校验，也没有断言。
根因：用"人可读的 id 顺序"当"时间顺序"的代理，而两者只在 id 格式统一时等价。
```

**根因不靠推理，靠一次硬读数确认**：

```
注入一个非零填充 id（时间上更早）:  dec-probe-0001
期望（按时间最近 2 条）:          [dec-0066, dec-0067]
实际:                            [dec-0067, dec-probe-0001]      <- 不一致，假设成立
```

**分级**：判「重要」不判「阻断」—— 因为核对了真实数据：67 个 id 全部形如 `dec-NNNN`，**当前不触发**。
分级按实际影响，不按理论严重度。

**这条例子的可复用点**：一个"依赖未校验前提"的缺陷，光看代码只能得到"可能有风险"；
**用一次注入把前提破掉，才能从"可能"变成"确实"。**

## 安全与回滚

- **透明**：列出审查范围与判定标准。
- **可控**：修复分批进行，阻断项优先。
- **可逆**：记录审查前版本，修复可回退。
- **渐进**：先修阻断，再清重要，最后风格。
- **用户主导**：是否放行由用户拍板。

## 前提与边界

- **"测试全绿"不能当审查依据**：前提是测试真有牙齿。实测本仓 `hermess/test/` 下的 `*.test.mjs` 在 `node --test` 下**全绿**（任取单文件实测 `tests 1 / pass 1 / fail 0`、exit 0），
  而**实际执行的断言数为 0** —— 这些文件全部 export `tests`，却**无一 import `node:test`**（真 import 数：**0**），
  `node --test` 对"可加载但零注册"的文件判绿。**回归前先确认测试真的执行了断言，不能只看颜色。**
- **"四象限都过了"不等于没有缺陷**：前提是这四类覆盖了该系统的风险面。
  对并发 / 权限 / 数据迁移类系统，"四象限"之外还有一类（时序与状态机的可达性）。
  遇到这类系统，在结论里写明"本次用四象限覆盖，未覆盖时序类"。

- **台架：574 通过 / 0 失败**（`run-all.mjs` 实测；本段已登记进 `hermess/lib/bench-truth.mjs` 的 `BENCH_ANCHORS`，
  由 run-all 尾部机器对账 —— 数字抄旧即红，不再靠人记）。

## 工具对齐（当前异结构工具面）

- code-audit —— scan/stats/god-files/dup/untested：先用真实字节算出总文件/行数/上帝文件/重复组/无测试模块，再人工审正确性/安全四象限。
- dependency-audit —— audit(manifest)：浮动版本/dev-prod 重复/幽灵 import/许可证；lockcheck 对 lock 文件。
- code-audit dup() 只做整文件哈希：函数级复制粘贴完全失明（实测 hermess/lib 里 7 份取整函数副本、3 个唯一实现体，dup() 报 0 组重复）。要查函数级重复得自己抽实现体比对。
- code-audit untested() 会全量误报：真有测试的文件（metrics.mjs）也报「无测试」——不能据此判某模块没测试，逐条复核。
- code-audit stats 对 .md 报 totalLines=0（真值 71 LF）：文档/非代码文件的统计值不可信，别写进审查结论。
