# 代码审查

> 审查的目标不是挑错，而是让问题在上线前以最低成本暴露。

## 何时使用

- 代码提交前 / 合并前的评审。
- 接手他人代码，需要快速建立质量认知。
- 定位难以复现的缺陷，需要通盘排查。
- 上线 / 发版前的最后一道把关。

## 执行流程

1. **明确审查目标** —— 确认范围（提交 diff / 模块 / 全量）、关注点与放行标准。
2. **通读结构** —— 先看目录与调用关系，再进入逐文件、逐函数细节。
3. **四象限核查** —— 对每个单元从四维度打分：
   - **正确性**：边界、空值、异常、并发、类型。
   - **安全**：注入、越权、敏感信息、依赖漏洞。
   - **性能**：复杂度、多余 IO、内存泄漏。
   - **可维护性**：命名、重复、职责、可测试性。
4. **5Why 追根因** —— 对每个问题问"为什么"，定位根因而非表象。
5. **分级清单** —— 按「阻断 / 重要 / 建议 / 风格」输出问题清单 + 修复建议 + 定位。

## 输入 / 输出

| 输入 | 输出 |
| --- | --- |
| 代码 / diff / 仓库路径 | 分级问题清单 |
| 审查标准 / 放行条件 | 逐条建议 + 根因 + 定位 |
| 安全/性能红线 | 是否放行的结论 |

## 关联思维策略

- **对比分析** —— 与规范、最佳实践、历史正确实现做对照。
- **5Why** —— 从症状追到根因，避免只改表象。
- **红队演练** —— 假设自己是攻击者/恶意输入，找漏洞。

## 基因库记录

- **类型**：pattern
- **复用经验**：先通读结构再抠细节；问题必须分级并给出根因，不能只报"有 bug"。
- **可复用性**：高 —— 任何语言、任何规模都适用。
- **入库自检**：用户选择 ✅ / 适应度前 100 ✅ / 可复用 ✅

## 示例

### 场景：审查一处登录鉴权

1. 目标：登录接口 + token 校验逻辑。
2. 正确性：空 token、过期、并发请求 → 发现一处空值未判。
3. 安全：token 用弱随机数生成 → 判「阻断」，建议改用安全随机源。
4. 成果：输出 1 阻断 + 2 重要 + 3 建议，附定位与修复方案。

## 安全与回滚

- **透明**：列出审查范围与判定标准。
- **可控**：修复分批进行，阻断项优先。
- **可逆**：记录审查前版本，修复可回退。
- **渐进**：先修阻断，再清重要，最后风格。
- **用户主导**：是否放行由用户拍板。
