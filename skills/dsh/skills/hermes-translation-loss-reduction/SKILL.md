# 🔁 传话层工程降损（v2.0）

**第一性原理**：Agent 是「模型 ↔ 环境」之间的传话层。最大损耗不在工具数量，而在
**回传原始载荷**（像素 / 扁平元素列表 / 原始 DOM / 300 行构建日志）+ **模型每轮重新解析环境** +
**失败只回 raw error 让模型猜** + **同轮重复调用浪费一次往返** + **检查命令自身出错伪装成被测物失败**。

降损的最高杠杆 = **把回传从原始载荷变成模型可消费的符号** + **把每步失败变成可纠正反馈** +
**消除重复推导/重复调用** + **让"完成"以产物为证而非以进程状态为证**。

## 降损模式库（结晶自基因库）

### P1 符号态提炼（pattern-005）
- **场景**：工具回传原始载荷（截图 / DOM / 目录列表），模型每轮重解析。
- **做法**：`_build_symbolic_state(raw)` 从结构化结果归纳高信号字段
  （`controls`/`interactive`/`focused_text_value`/`dialog_open`/`app`），注入回传。
- **经验**：提炼是归纳不是推理；解耦成通用 helper 后任何工具挂一个字段即得收益（pattern-010）。
- **实证（2026-10-06）**：构建日志 300+ 行原始依赖清单冲入 context 被 `<response clipped>` 截断——
  事后只需 6 行符号态（「electron 44.4.1 打包 → NSIS 目标生成中」）即可替代。见 P9。

### P2 调用前意图预检（pattern-006）
- **场景**：tool_call JSON 合法但语义荒谬（点不存在元素 / 空 path / 危险命令伪装），执行后才失败且带副作用。
- **做法**：纯函数 `precheck_tool_args(agent, name, args)` 在执行前拦截，返回 `(error, hint)` 转成普通 tool-error 让模型下一轮自纠。
- **经验**：必须 **fail-open**（返回错误结果而非硬中止），否则模型无法自纠；与 tool_guardrails 形成 defense-in-depth。

### P3 失败归因（pattern-007/013）
- **场景**：工具失败只回 raw error，模型靠猜"为什么败、下一步调什么"。
- **做法**：`classify_failure(tool, text)` 正则映射 → `(reason, suggestion)`；升级为卡片 `{failure_reason, suggested_next, recoverable, quick_action}`。
- **经验**：反馈最高形态不是"说清为什么"，而是"给一个能直接执行的下一步"（quick_action）。
- **实证（2026-10-06）**：edit old_string 失配 → 归因「锚点来自记忆而非 read」→ quick_action「先 read 再 edit」；
  pwsh 命令 `[exit code: 1]` 无输出 → 归因「检查命令自身语法错（数组 .Trim()）」而非被测物失败。见 P11/反模式。

### P4 跨 turn 意图栈（pattern-008/012）
- **场景**：模型每轮从头重推"我们要干啥"，易漂移。
- **做法**：`IntentStack` 线程安全栈（goal/subgoals/expected_tools），`align()` 软提示（非阻断）——失败计数做门限，3 连败触发 flailing 警告。
- **经验**：意图记忆须是"软对齐"而非"硬门禁"；用失败计数做触发门限比无条件拦截更稳。

### P5 执行轨迹可视化（pattern-009/015）
- **场景**：多步编排成一次 sequence 后用户/模型看不到"执行到哪一步、卡在哪"。
- **做法**：`TrailRecorder` 每步记 `{step, op, ok, summary, error}` + `failed_at_step` + 耗时，`save()` 落 JSON，`diff_trails(a,b)` 可复盘对比。
- **经验**：编排能力上线后必须配套"轨迹可视化 + 结构化沉淀"，否则能力越强黑盒越深。

### P6 符号态缓存（pattern-016）+ 失败归因记忆化（pattern-017）
- **场景**：屏幕/输入没变却每轮重复蒸馏、每次失败跑整套正则。
- **做法**：`screen_signature()` 对输入取 sha256 → 有界 FIFO 缓存复用结果；`classify_failure` 仅缓存**纯函数**结果（有界 FIFO）。
- **经验**：① 性能优化最高杠杆是消除重复推导；② **记忆化前必须先确认纯函数性**——
  `precheck_tool_args` 依赖运行时状态（当前截图索引）NOT 纯函数，记忆化会返回错误判定，**绝不可缓存**。

### P7 同轮只读调用去重（pattern-018）
- **场景**：模型一轮里重复发相同 `read_file`/`list_dir`，每次算一次"模型重推"。
- **做法**：`turn_cache` 每 turn 重置；仅 `_READONLY_CACHEABLE` 只读工具允许；派发前命中即复用。并发路径用**提交前预去重**（`_concurrent_dedup_plan` 纯函数）避免 worker 共享缓存竞态。
- **经验**：① 同轮去重必须"仅只读 + 按轮重置"才零陈旧；② 接多派发分支时**每个分支都要覆盖且逐字保留原异常/中断语义**；③ 去重决策抽成纯函数可单测。
- **实证（2026-10-06）**：同轮两次 `git-snapshot`/构建状态查询可合并为一次 Promise.all 只读并发——省一个往返。

### P8 损耗量化基线（pattern-011/042）
- **场景**：降损只是概念——没有度量就无法证明收益、无法定位下一优化点。
- **做法**：线程安全全局 `TranslationMeter`，在符号态注入点记"原始载荷 vs 符号态"体积、在 executor 记"每次工具调用=一次重推" + 各降损命中计数；`report()`/`to_json()` 暴露。
- **经验**：**没有度量就没有下一步优化**。先建基线再优化；度量必须零侵入、fail-open。

## v2.0 新增模式（工程会话结晶）

### P9 大载荷摘要闸（L1/S1——P1 在"执行日志"面的推广）
- **场景**：构建/测试/审计工具动辄回传数百行原始日志；`<response clipped>` 截断=信息既丢了又污染 context。
- **做法**：**任何工具回传 > 30 行，先归纳再消费**：长日志只取「头 3 + 尾 12 + 关键事件行（状态机迁移/错误/产物路径）」；
  归纳格式固定为符号态卡片 `{phase, done, doing, artifact, blockers}`。多个只读查询**并发合并**成一次 run_code 再摘要（与 P7 同构）。
- **经验**：截断不是"没看清"，是**结构化证据**——它证明该回传没做符号态。归纳是纯函数（日志→卡片），可缓存（P6）。

### P10 派发产物判据（P3 在"进程派发"面的特化）
- **场景**：后台起进程（构建/长任务）出现「静默无输出」：内联 `-Command` 重定向不生效、exit 文件不落盘、进程退出码与产物状态不一致。
- **做法**：三层判据，缺一即 UNVERIFIED：
  ① **产物文件为准**（finished-goods truth）：exe/安装包存在且时间戳新于任务起点才算成；
  ② **日志文件存在性**为派发成功判据（不看进程退出——进程 True/False 都可能骗人）；
  ③ 派发用**脚本文件**（`.cmd`/`.ps1` + `cmd /c` 重定向），不用内联命令串。
- **经验**：`Get-Content(...).Trim()` 链在数组上抛错 = 检查器自身故障；**先怀疑检查器，再怀疑被测物**。
  跑批任务里「running=True 但产物已生成」是常态——以产物时间戳为准。

### P11 锚点预检（P2 在"文本编辑"面的特化）
- **场景**：edit/write 靠"记忆中的代码"做 old_string 锚点，模块重构后必失配，每次失配浪费一整轮。
- **做法**：**edit 前必须 read 精确文本**（含行号），锚点带足上下文且全文件唯一；重构后的锚点一律视为**过期载荷**。
- **经验**：锚点失配是最容易清零的损耗——它 100% 由预检消除。与"先台架后装活"同构：改前先观测真值。

### P12 状态双信道去噪（P1/P3 在"状态判定"面的推广）
- **场景**：进程状态（running/exit code）与产物状态（文件存在/时间戳）是两个独立信道，互相不蕴含。
- **做法**：状态判定**以产物信道为准**，进程信道只做辅助；两个信道矛盾时，报矛盾本身（而不是选边相信）。
- **经验**：`exit code 0` ≠ 成功（可能什么都没做）；`running` ≠ 未完成（产物可能早已落盘）。与「不注水」纪律同构：拿不到产物证据=未执行。

## 通用执行协议（结晶 SOP）

```
1. 诊断损耗点 → 2. 选模式(P1~P12) → 3. 抽通用helper解耦 → 4. 注入回传/执行前
→ 5. 加度量基线 → 6. 单测固化 → 7. 大载荷过 P9 摘要闸
```

- **解耦优先**：提炼/预检/归因逻辑抽成与具体工具无关的 helper，新工具只需挂一个字段即获能力（pattern-010）。
- **fail-open 铁律**：任何拦截/缓存/度量异常都必须静默回退原行为，绝不能让治理层拖垮主流程。
- **纯函数审查**：凡要记忆化/复用的逻辑，先确认输入确定→输出确定，否则只能实时算。
- **产物判据**：任何"完成"声明须指向产物（文件/路径/哈希），无产物 = 未执行（P10/P12）。

## 损耗实测基线（2026-10-06 会话样本，TranslationMeter 口径）

| 损耗事件 | 次数 | 单次成本 | 清零手段 |
|---------|------|---------|---------|
| edit 锚点失配 | 2 | 整轮往返 | P11（read 后改） |
| 后台派发丢日志 | 3 | 2-3 轮排查 | P10（脚本文件+产物判据） |
| 大载荷截断 | 2 | 信息丢失+污染 | P9（摘要闸） |
| 检查命令自身报错 | 2 | 误判被测物 | P10③/反模式 |
| 同源状态矛盾 | 1 | 误判完成/未完 | P12（产物为准） |

**结论**：本会话 10 次可避免损耗中，P9+P11 覆盖 5 次（50%）——先落这两个杠杆收益最大。

## 安全原则（继承自进化引擎）

1. **透明** — 所有降损改动让用户知道（度量/面板暴露）
2. **可控** — 可随时关闭某模式
3. **可逆** — 每个改动独立可回滚
4. **渐进** — 小步迭代，先度量后优化
5. **fail-open 不可破** — 治理层永不作为主流程的单点故障

## 反模式（pitfall，pattern-019 + v2.0）

- **导入一致性陷阱**：跨模块 `import` 在**加载期**即解析，一个坏符号名会让整模块崩（比 lint 更前置）。凡重命名/移动符号，必须 grep 全仓同步所有引用方，落地后做"全量 import 闭合审计"。
- **锚点漂移陷阱**：把"记忆里的代码"当编辑锚点——模块一重构必失配。锚点是**快照过期载荷**，edit 前 read（P11）。
- **截断即信号**：响应出现 `<response clipped>` 不是"没看清"，是该回传没过 P9 摘要闸的直接证据——立刻归纳，不要盲目重读原文。
- **exit code 拜物教**：`[exit code: 1]` 可能来自检查命令自身语法错（如数组 `.Trim()`）。检查器与被测物分开验证：先用一条 trivially-safe 命令验证检查器，再解读结果。

## 工具对齐（当前异结构工具面）

- run_code —— 把多步读写压缩成一轮 PTC，降低跨轮传话损耗；grep/read/write/edit 直接用，不回传原样大文本。
- git-snapshot —— 传话层产物落地前留回滚点。
