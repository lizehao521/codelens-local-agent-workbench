# 安全测试

> 用攻击者的视角验证防线，而非只验证"正常路径能跑通"。

## 何时使用

- 目标（Web 应用 / API / 脚本）上线前或重大变更后。
- 发现疑似漏洞，需要 PoC 验证确认。
- 修复之后需要复测确认闭环。

## 执行流程

1. **资产与接口盘点** —— 列出域名、端点、参数、认证点、数据流。
2. **威胁建模** —— 明确"谁可能攻击、攻什么、后果多大"，划定测试边界（在授权范围内）。
3. **漏洞清单核查** —— 按 OWASP 等清单逐项验证（注入、XSS、越权、敏感信息泄露、弱认证等）。
4. **PoC 验证** —— 对疑似漏洞用最小可控输入复现，记录触发条件与影响。
5. **修复与复测** —— 给出加固建议，修复后复测，确认不再复现。

## 输入 / 输出

| 输入 | 输出 |
| --- | --- |
| 目标地址 / 接口定义 / 代码 | 漏洞清单（分级 + PoC） |
| 授权范围与红线 | 加固建议 |
| 历史漏洞记录 | 复测结论 |

## 关联思维策略

- **红队演练** —— 主动构造恶意输入与攻击路径。
- **预判验证** —— 先假设漏洞存在，再用最小输入验证。
- **5Why** —— 追溯漏洞成因（是缺过滤、缺权限、还是缺设计）。

## 基因库记录

- **类型**：pattern
- **复用经验**：先盘点接口再做威胁建模；每个漏洞必须给出"触发条件 + 影响 + 修复"三件套。
- **可复用性**：高 —— 适用于任何 Web 应用 / API 目标。
- **入库自检**：用户选择 ✅ / 适应度前 100 ✅ / 可复用 ✅

## 示例

### 场景：一处登录参数疑似注入

1. 盘点：登录接口 `POST /login`，参数 `user` / `pass`。
2. 威胁建模：外部未认证用户可访问 → 高风险。
3. 核查：`user` 拼接进 SQL → 尝试 `' OR '1'='1`。
4. PoC：绕过密码校验成功登录 → 判「阻断（SQL 注入）」。
5. 修复：参数化查询 + 输出转义 → 复测不复现。

## 安全与回滚

- **透明**：明确测试范围、payload 与影响。
- **可控**：所有动作限制在授权范围内，破坏性测试单独标记。
- **可逆**：测试前快照/备份，可还原。
- **渐进**：先无害探测，再低影响验证，最后确认性 PoC。
- **用户主导**：是否执行有风险的 PoC 由用户批准。

## 工具对齐（当前异结构工具面）

- dependency-audit —— audit(manifest, {ghostImports})：幽灵 import/浮动版本/许可证，纯静态无网络（真实字节，不跑 npm audit）。
- verify-url —— 外链逐条核验 state；SSRF/协议越界=denied 不冒充 broken。
- verify-url 的 broken 会把活端点判死：401（主机活着、要鉴权）也记 broken（实测真实 base URL 的 /v1 返回 404、/v1/models 返回 401，两者都记 broken）。见 broken 先确认不是鉴权/根路由问题，别把它当「目标不可达」写进结论。
