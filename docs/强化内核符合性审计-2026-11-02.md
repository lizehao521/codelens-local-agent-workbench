## 二、逐条验证

### §1 闭环：`Improve(π) = π --Act--> τ --Judge--> r --Update--> π'`

**结论：符合。环真的在转。**（unit）

| 环节 | 落点 | 证据 |
|---|---|---|
| π（策略） | `repositories/policy.repository.ts`（`policy_versions` 表） | static |
| Act | `services/agent/agent-loop.service.ts` | static |
| τ（轨迹与证据） | `tool_calls` / `tool_results` 表 | static |
| Judge | `services/judge/judge.service.ts` + L0–L3 | unit |
| r（判决） | `judge_runs` / `judge_verdicts` 表 | static |

| π' → 下一次 Act | `buildSystemPrompt(taskKind, policy)` 注入经验段 | unit |

**闭环被钉死的证据**：`tests/judge-policy-loop.test.ts`（12 用例）验证
「Judge 产 r → Update 消费 r 生 π' → 下一轮 Act 可读 → 有效性可被聚合」，
且断言**经验由具体 fail 判据决定**（pass/inconclusive 不产生噪声）。

**经验排序按证据而非年龄**：`services/agent/lesson-budget.ts` 用 Laplace 平滑通过率排序，
证据相同者按「被注入次数最少」优先（避免自证式饿死）。默认预算 8 条 / 480 字符，
使经验段常驻开销不超过「身份+规则」本身。

> 历史记录（`.workbuddy/memory/2026-10-31.md`）显示此环曾是「环有形状，从未转过」
> ——`buildSystemPrompt` 因 `lessons.length === 0` 永远走 `return base`，正好命中 §4
> 反面清单「加了模块但没人调用」。**现已修复并有回归测试守护。**

### §2 C2 闭环（没有被消费的分数/指标/日志 = 开环）

**结论：部分符合。发现 2 处开环。**（static）

#### 开环项 1：`maxResultChars` —— 声明 12 处，读取 0 处

| 位置 | 内容 |
|---|---|
| `types/tool.ts:75` | 接口字段声明 `maxResultChars: number` |
| 10 个内置工具 + 1 个 MCP 适配器 | 各自赋值（2000 / 4000 / EXEC_STDOUT_CAP+…） |
| **消费者** | **无** |

它在每个工具上都写了一个「结果字符上限」，但执行链路（`executor.service.ts`）从不读它。
实际生效的是另一个常量 `OBSERVATION_MAX_TOKENS`。按 C2 口径：**这 12 处赋值是纯装饰**。
（注：本轮之前的大输出治理已把实际裁剪改为 token 硬顶，但这个死字段仍在。）

#### 开环项 2：`messages.tokens` / `usage_json` 记账失真

- `messages.tokens` 用 `estimateTextTokens()` 估算，**不计 `reasoning_content`**。
  实测同一消息 reasoning 2149 字符却只记 7 token。
- `messages.usage_json` 列**全空**——上游真实账单从未落库。
- 后果：无法从 DB 还原真实 token 账单，只能靠 `usage.promptTokens`（跨轮累计）
  粗算。按 C2 口径，这两个字段目前**没有真实消费者能用它们做决策**。

#### 闭环正常的部分

- `ModelSync` → `provider_models` 表 → `providers/registry.ts` 合并 → 会话可选
  （宪法补丁 §2 的「sync 进 registry」门禁，有 `model-sync.integration.test.ts` 守护）
- `policy_injections` 记录每次注入（`recordInjections`），可与有效性聚合对账

### §2 C3 自证（判据要先被判据检验）

**结论：符合。破坏夹具真能打红。**（unit + mutation）

`tests/judge-canary.test.ts`（9 用例）实现宣言要求的四件套：

| 要求 | 实现 | 证据 |
|---|---|---|
| 正常例（该绿的绿） | 「金丝雀通过，且已知好/坏样本被分开」 | unit |
| 金丝雀（该红的红） | 「全部换成永真闸 → 变红」「全部换成永假闸 → 变红」 | unit |
| 破坏夹具（改坏必红） | **突变验证：见下** | mutation |
| 判别力自证（非永真闸） | 「只削弱一条 → 判别力下滑，金丝雀仍报警」 | unit |

**突变验证（本轮实做）**：把 `L0_CRITERIA` 整体换成永真闸（恒 `status: 'pass'`），
金丝雀 **3 条测试变红**：
1. `金丝雀通过，且已知好/坏样本被分开` —— 主判别力测试
2. `只削弱工具成功率这一条 → 判别力下滑，金丝雀仍然报警`
3. `金丝雀使用的阈值与生产判据同源`

还原后 md5 一致。**这证明金丝雀不是装饰，能抓住「假绿」。**

L3 红队（`tests/judge-red-team.test.ts`，14 用例）钉的是**判红边界**：
条件句/未来语气/代码示例不算声明（防误杀）；失败的调用不算证据；无声明判 `unexec`。

### §2 C4 不外推（UNEXEC ≠ PASS）

**结论：符合。纪律内建于判据本身。**（static + unit）

- `unexec` 是独立状态，与 `pass`/`fail` 并列（`types.ts`）。
- 金丝雀失效时**整体降级为 `unexec`**，不写 pass（`canary.ts`）。
- 「已知好样本出现 unexec」→ 金丝雀自身判 `unexec`（样本没覆盖到 = 自证无效）。
- 红队：无声明 → `unexec` 而非 `pass`（测试名明写「没声称 ≠ 已证实」）。
- L3 接入：纯解释型回答 ⇒ L3 为 `unexec`，**不因「没得校验」把任务拖成失败**。

未发现把 UNEXEC 说成 PASS 的代码路径。

### §6 工具纪律（三条机器闸）

**结论：不符合。整节未实现。**（static）

宣言 §6 要求的机器产物，**全库搜索（.ts/.mjs/.md/.txt/.json）仅在 `强化Agent.txt` 自身命中**：

| 要求 | 状态 |
|---|---|
| `tmp/tools/<taskId>/` 任务作用域 | **不存在** |
| `tool_created` / `tool_used` / `tool_failed` 三事件 | **不存在** |
| `tool_removed` 事件 | **不存在** |
| 孤儿工具闸（任务结束作用域必须为空） | **不存在** |
| 沉淀配对闸（`tool_removed` 必须配对 `lesson`） | **不存在** |
| 写闸复用（进主树必过自证与工程闸） | **不存在**（工具是静态内置，无动态创建路径） |

**注意**：现有代码里的 `lesson` 是 **π 经验注入**（§5 范畴），与 §6 的「沉淀三问→lesson」
不是一回事。两者名字撞了但口径不同——按 §5 自己的要求「口径必须分开，不能互相冒充」，
这里存在**术语混用风险**。

**判断**：§6 描述的是「任务期动态造工具」的纪律。当前 CodeLens 的工具是静态内置
（`tools/builtin/` 10 个），**没有动态创建工具的能力**，所以 §6 的闸暂时无对象可守。
但宣言把它写成硬要求，代码里却完全无对应——按 C1 口径，这是**文档与实现的不一致**。

## 五、全局一致性结论

**内核是真的在转**，不是「环有形状」：
- r 真的改 π'（经验由具体 fail 判据产生，非模板）
- π' 真的改下一次 Act（注入 system prompt，且按证据排序）
- 判据自己先被判据检验（金丝雀 + 破坏夹具，突变可打红）
- UNEXEC 纪律内建（不外推）

**不一致处集中在两点**：
1. **文档超前于实现**（§6）——宣言写了硬要求，代码无对应，且术语与 §5 撞名。
2. **装饰未清**（C2）——`maxResultChars` 与失真账本是「写了没人用」的典型。

按宣言自己的反面清单，这两类正是「不是强化，是忙碌」。**它们不影响当前功能正常性，
但影响「下一次自我修改仍可被证伪」的可信度。**
