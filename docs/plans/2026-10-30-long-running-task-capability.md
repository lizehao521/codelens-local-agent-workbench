# 长期任务能力（Long-Running Task）可行性与 PRD

> 日期：2026-10-30
> 状态：**草案，待产品总监确认后转 ADR**
> 上游依据：`docs/agent/spec.md`（v2.0 现行规格）、`docs/agent/phase2-architecture-detail.md`、ADR-017 / ADR-020 / ADR-024 / ADR-025、`产品宪法补丁.md`
> 关联未决项：OD-A5（单任务最大轮次默认 12 是否合适）

---

## 0. 结论先行

**结论：可行，但不能靠调参数实现，必须新增"任务编排层"，把 Agent 循环从 HTTP 请求生命周期里剥离出来。**

三条判断：

1. **当前架构在结构上排斥长任务，不只是参数偏紧。** 12 轮 / 180s / 5 分钟审批 / 进程内存授权，这四条不是"限制强度"问题，而是"任务身份绑定在请求生命周期上"的必然结果。`POST /api/v1/agent/stream` 一旦断开，任务就没有任何载体存续。
2. **真正的成本不在调度，在上下文。** 长任务的成败取决于"工作记忆外置"——真值放结构化任务状态，messages 只作叙事。这一条不做，轮次调到 300 也只是把崩溃点往后推。
3. **不要一步做到"自主长跑"。** 产品宪法 C1 要求新模块必须回答"强化了 Act / Judge / Update / Memory 哪一维"。L3 阶段的"定时自主唤醒"目前强化不了任何一维，只是把用户从"看着跑"变成"猜它跑成什么样"，属于装饰。**建议只做 L1+L2，L3 待 Judge 侧有可验证的判据后再议。**

## 1. 现状约束审计（对照代码，非文档口径）

| # | 约束 | 代码位置 | 现状值 | 长任务下的失效方式 |
|---|------|---------|--------|------------------|
| C-1 | 任务总时限 | `server/src/services/agent/loop-budget.ts:23` `TASK_BUDGET_MS` | **180_000 ms 硬编码常量** | 到点强制 `budget_exhausted`，无论任务是否接近完成 |
| C-2 | 最大轮次 | 同文件 `:21` `DEFAULT_MAX_ITERATIONS` | 12（可配 5–30） | 第 13 次 LLM 调用被拦，输出"未完成项"后终止（AC-02 明确此行为） |
| C-3 | 任务级重试预算 | 同文件 `:22` `DEFAULT_MAX_RETRIES` | 5 | 长任务必然耗尽，且耗尽后无恢复入口 |
| C-4 | token 硬顶 | 同文件 `:25` `TOKEN_BUDGET_CONTEXT_FACTOR` | 上下文窗口 × 2 | 长跑必然撞顶；且这个口径按"单任务"算，不按"任务全程"算 |
| C-5 | 审批令牌时效 | ADR-024（5 分钟过期）+ `approvals.expires_at` | 300s | 用户离开 5 分钟，待批调用作废，任务卡死 |
| C-6 | 会话级授权作用域 | ADR-024 `allow_session` = 进程内 `Map` | 不落库、不跨会话、不跨重启 | 长任务跨小时/跨天，授权必然丢 |
| C-7 | 重启即废弃 | ADR-024 负面清单 | 挂起审批重启后置 `aborted` | 桌面端休眠唤醒、服务重启 = 任务死 |
| C-8 | 上下文压缩回退 | ADR-020 降级链 ② | 自检缺项 → 回退并提示"上下文已满" | 设计上就接受"长任务可能因压缩失败中断" |
| C-9 | 任务身份载体 | spec §5 `POST /api/v1/agent/stream`（SSE） | 任务生命周期 = SSE 连接生命周期 | 客户端断开/刷新 → 任务无归属，无续跑入口 |
| C-10 | 数据库表边界 | spec §6 锁定 9 张表 | 无任何 task / checkpoint 实体 | 无断点可存，也无处可读 |

**关键洞察（C-9）**：其余 9 条都是"参数级"或"策略级"障碍，只有 C-9 是**结构性**的。只要任务身份仍然是"一条 SSE 请求"，L1 就没法做——因为没有任何对象能在请求结束后被"继续"。

## 2. 可行性判断（回应"要不要做"）

### 2.1 三个必须提前想清楚的技术难点

| 难点 | 本质 | 现在的机制为什么扛不住 | 应对方向 |
|------|------|---------------------|---------|
| **上下文腐化** | 长跑必然爆窗，压缩有损 | 压缩是"摘要 + 机械自检"，缺项就回退求人（ADR-020 ②）。20 轮能过，200 轮过不了 | 工作记忆外置：任务状态（已完成/待办/已改文件/关键约束）结构化存 SQLite，上下文只装"当前窗口 + 结构化状态摘要"，不再回放历史 |
| **审批延迟模型冲突** | 现在是"人等 5 分钟"，长任务是"任务等 5 小时" | 令牌 5 分钟过期；`allow_session` 在进程内存 | 令牌持久化 + 挂起态不消耗任务预算 + 续签机制。**这不是把 300s 改大**，是换一套"挂起/唤醒"语义 |
| **幂等** | 断点续跑必然重放工具调用 | `fs.write` / `http.request` 都无幂等键，重放即副作用 | 工具层加 `idempotencyKey`（= taskRunId + stepSeq），写操作前置"目标状态比对"而非"直接覆盖" |

### 2.2 与产品宪法判据的对照

| 判据 | 本方案的回答 |
|------|------------|
| **C1 中心性** | L1 强化 **Memory**（任务状态成为一等实体，可跨轮次复用）；L2 强化 **Act**（动作可续、副作用可追）。**L3（定时自主唤醒）四维都强化不了，故不建议做** |
| **C2 闭环** | 检查点必须有真实消费者：`task_runs` 的唯一消费者是"续跑端点"与"UI 进度面板"。若只写不读 = 开环，直接砍 |
| **C3 自证** | 每条验收标准都要有破坏夹具：杀掉进程 → 重启 → 断言任务从 checkpoint 续跑且副作用不重复 |
| **C4 不外推** | 阶段验收必须在"真实 Key + 真实中断"下跑，不接受"单元测试绿了就写 PASS" |

### 2.3 优先级判断（RICE，沿用 spec §2 口径）

| 能力 | Reach | Impact | Confidence | Effort | RICE | 建议 |
|------|-------|--------|-----------|--------|------|------|
| **L1 可中断续跑**（checkpoint + 任务实体化） | 4 | 3 | 0.8 | 4 | **7.2** | P0，先做 |
| **L2 可恢复**（审批持久化 + 幂等 + 重启续跑） | 3 | 3 | 0.75 | 4 | **5.1** | P0，紧随 L1 |
| **L3 可编排**（子任务状态机 + 定时唤醒） | 2 | 2 | 0.4 | 5 | **0.96** | **暂不做**，判据不足 |

对比 spec 中已排的 P0 项（AC-11 token 显示 7.0、AC-08 错误重试 7.2），**L1 的优先级与现有 P0 同档**，但不属于 v2.0 MVP 锁定范围——需要显式扩范围决策。

## 3. 方案设计

### 3.1 结构性变更：任务实体化

```
现在：  用户请求 ──→ SSE 连接 ──→ Agent 循环 ──→ 连接关闭 = 任务结束
                    （任务身份寄生在连接上）

目标：  用户请求 ──→ task_runs 记录 ──→ 调度器 ──→ Agent 分段循环 ──→ checkpoint
                            ↑                                          │
                            └────────── 续跑端点 / 重启恢复 ←──────────┘
                    （任务身份独立存续，SSE 只是「订阅视图」）
```

要点：
- `POST /api/v1/agent/stream` **不改语义**，但内部改为"创建或接管 task_run，然后边跑边推流"
- 断连不再等于中止；用户在 UI 上显式中止才中止（对应现有 `POST /api/v1/agent/abort`）
- 单个 `task_run` 的一次执行段仍受 180s / 12 轮约束——**但约束对象从"任务"变成"单次唤醒的活跃段"**

这是最关键的一句：**不改任何现有预算数字，只改"预算算在谁头上"。**

### 3.2 数据模型（新增 3 张表，须同步修订 spec §6 的"锁定 9 张"）

| 表 | 核心字段 | 说明 |
|----|---------|------|
| `task_runs` | id, session_id, goal, status(`running`/`waiting_approval`/`paused`/`done`/`failed`), current_segment, segments_used, total_tokens, created_at, updated_at | 任务实体。status 是新状态机，与现有会话状态解耦 |
| `task_checkpoints` | id, task_run_id, segment_no, messages_cursor, state_json(已完成/待办/约束/已知错误), files_touched_json, tokens_used, created_at | 每次分段结束写一条，**只追加不更新** |
| `task_steps` | id, task_run_id, seq, title, status, tool_call_id, idempotency_key | L1 可空表（占位），L2 幂等依赖它 |

复用既有能力（不新建）：
- 审批仍走 `approvals` 表，只增加 `task_run_id` 外键 + `expired_at` 语义从"作废"改为"挂起"
- 大工具结果仍走 `tool_results` + `result_ref` 指针，不重复造

### 3.3 状态机（任务级，新）

```
created → running ⇄ waiting_approval
              ↓            ↓
           paused ←───────┘（超时/断连/预算耗尽均进入 paused，非终止）
              ↓
           running（人工续跑 / 重启恢复）
              ↓
        done / failed（仅在显式中止或不可恢复错误时）
```

**`paused` 是一等状态**，这是与原设计最大的语义差别：现在"预算耗尽"= 终止，长期任务里"预算耗尽"= 暂停待续。

### 3.4 上下文策略（长任务版）

| 层 | 内容 | 处理 |
|----|------|------|
| 系统层 | 任务目标 + 硬约束（来自 `state_json`） | 每段固定注入，**不进压缩流程**——这是防"忘记约束"的根 |
| 状态层 | 已完成 / 待办 / 已改文件 / 已知错误 | 结构化摘要，机械生成（不靠 LLM 摘要，避免有损） |
| 窗口层 | 当前段的 messages | 沿用现有 75% 三层压缩；**段边界处整体清空**，靠 L1/L2 层重建 |

关键改动：**压缩发生在段内，不在任务内。** 每段结束即落库，下一段从结构化状态重建上下文——这样 ADR-020 的"压缩失败即中断"就被降级为"单段失败"，不再等于任务死亡。

## 4. PRD（EARS 格式验收标准）

| 编号 | 验收标准 | 优先级 |
|------|---------|--------|
| **AC-L01** | While 任务因 12 轮上限或 180s 预算耗尽而中止，系统**必须**将任务置为 `paused` 并写入一条 `task_checkpoints`，且**不得**丢弃已完成的工具调用记录 | P0 |
| **AC-L02** | While 任务处于 `paused`，When 用户点击「继续」，系统**必须**从最近检查点重建上下文并继续执行，**不得**重放已成功并有副作用的工具调用 | P0 |
| **AC-L03** | When 用户关闭浏览器或 SSE 连接中断，系统**必须**保持任务运行至当前段结束再置 `paused`，**不得**因断连直接判失败 | P0 |
| **AC-L04** | While 命中高危工具产生待批调用，若 5 分钟内未决，系统**必须**将任务置 `waiting_approval` 并暂停该任务的时间预算，**不得**作废该审批（与现有 AC-06 的 300s 作废语义**互斥，需显式决策**） | P0 |
| **AC-L05** | If 服务进程重启，When 存在 `running` 或 `waiting_approval` 的任务，系统**必须**将其恢复为 `paused` 并在 UI 上呈现可续跑入口，**不得**静默置为 `aborted` | P0 |
| **AC-L06** | While 任务续跑，If 某个 `fs.write` / `http.request` 的 `idempotency_key` 已存在成功记录，系统**必须**返回上次结果而不重复执行 | P0 |
| **AC-L07** | While 单段执行，系统**必须**仍受 12 轮 / 180s / token 硬顶约束，并在段结束时展示本段成本与任务累计成本 | P0 |
| **AC-L08** | While 用户查看任务详情，系统**必须**展示任务级状态机当前状态、分段历史、每段起止原因（正常完成 / 预算耗尽 / 待审批 / 出错） | P0 |
| **AC-L09** | If 检查点写入失败，系统**必须**中止本段并将任务置 `paused` 且标注原因，**不得**在无检查点的情况下继续执行 | P1 |
| **AC-L10** | 系统**不得**在无人工触发的情况下自动唤醒任务（L3 明确不做，防越界） | P0（反向约束） |

## 5. 分阶段拆解

### 阶段 L1：可中断续跑（建议先做）

| 项 | 内容 |
|----|------|
| **范围** | `task_runs` / `task_checkpoints` 表 + 任务实体化 + 续跑端点 + UI 续跑入口 |
| **必须回答的 C1** | 强化 **Memory**：任务状态从"寄生在 messages"变成"一等实体" |
| **交付物** | 迁移脚本、`services/task/` 编排器、`POST /api/v1/tasks/:id/resume`、工作台任务进度面板 |
| **验收** | AC-L01 / L02 / L03 / L07 / L08 |
| **破坏夹具** | 强制在段中 kill 进程 → 重启 → 断言可从 checkpoint 续跑且已成功工具不重放 |
| **风险** | 中断点落在工具调用中途（tool_call 状态为 `running`）→ 需定义"孤儿工具调用"的收尾规则 |

### 阶段 L2：可恢复（依赖 L1）

| 项 | 内容 |
|----|------|
| **范围** | 审批持久化与挂起语义、幂等键、重启恢复、`task_steps` 启用 |
| **必须回答的 C1** | 强化 **Act**：动作副作用可控、可追、可重入 |
| **交付物** | `approvals` 增加 `task_run_id`、`allow_session` 落库（带 task 作用域）、工具层 `idempotencyKey` |
| **验收** | AC-L04 / L05 / L06 / L09 |
| **破坏夹具** | 同一 `idempotency_key` 重放 3 次 → 断言外部只被写 1 次 |
| **风险** | **ADR-024 需要修订**（5 分钟作废 vs 挂起不过期），这是安全边界变更，必须走 ADR 评审，不能顺手改 |

### 阶段 L3：可编排（**建议暂缓**）

| 项 | 内容 |
|----|------|
| **范围** | 子任务状态机、定时唤醒、人工节点编排 |
| **为什么暂缓** | 按 C1 四维检验，定时自主唤醒强化不了 Act/Judge/Update/Memory 任一维；按 C2 检验，它没有真实消费者能验证"跑对了"。做出来只会让用户从"看着跑"变成"猜它跑成什么样" |
| **重新评估条件** | Judge 侧出现可自动判定的任务正确性判据（例如测试套件能自动给出通过/失败），届时自主长跑才有收敛依据 |

## 7. 明确不做（本轮）

| 不做 | 原因 |
|------|------|
| `process_exec` / 代码执行沙箱 | 长任务下风险放大，与"断点续跑 + 幂等"叠加后攻击面不可控 |
| 多 Agent 协作 | 先把单 Agent 长跑做扎实（沿用 spec §3 立场） |
| 定时自主唤醒（cron 式） | C1/C2 判据不通过，见 §5 阶段 L3 |
| 云端托管长任务 | 与 OD-A8「本地单用户定位」冲突，一旦上云需整体重设计 |
| 任务产物自动归档到 artifacts 面板 | spec §6 明确不建 `artifacts` 表，沿用 `tool_results.artifact_path` |

## 8. 如果只是想"现在就试"（不改代码的验证路径）

在动手开发前，可以用现有能力验证痛点是否真实存在：

1. 用一个需要 **>12 步** 的真实任务（例如"扫 20 个日志文件 → 归类错误 → 写汇总 md"）
2. 观察它在第 13 轮 / 180s 时的终止行为，记录"未完成项"清单的可用性
3. 关键判断：**终止后你必须从零重说一遍任务，还是有办法接着跑？** 如果每次都从零开始，L1 的价值就被证实了

这一步不需要改任何代码，能直接给出"要不要做"的经验依据。
