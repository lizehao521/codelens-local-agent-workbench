### 删分支的连带影响：这两个分支各挂着一个 PR

删 ref 前我只复核了「尖端是不是 `main` 的祖先」，没查这两条分支各自是一个开放 PR 的 head——这是漏项。PR #1（head `fa5d2b77`，merge commit `6b77855c2ecfb30b7d036ed77eeac0f2937a5d6f`）、PR #2（head `0949762a`，merge commit `2f3bd52c33213065b05126a369fec478c8199a6f`）随分支删除被自动关闭。

第一趟删分支后 GET 读到的确实是 `state=closed` 且没带 merged 标记，我据此写下「merged 标记永久不可得」。**那句话是错的，撤回**：重建 ref 想试重开时平台先回 `422 Validation Failed — state cannot be changed. / The pull request cannot be reopened.`（所以重开这条路确实不通），但再读一次 `pulls/1`、`pulls/2` 已是 `merged=true`、`merged_at` 分别是 `2026-11-10T01:45:54Z` / `2026-11-13T14:13:34Z`——合并记录一直在，那是删分支瞬间的异步计数中间态，不是最终结论。两个 merge commit 本地复核都在祖先链里：`git merge-base --is-ancestor <merge_commit_sha> 95c2e56` 退出码 0。

处置：在 PR #1、#2 各贴两条评论——归宿记录（`#issuecomment-6906842454`、`#issuecomment-6906842730`）和上一条的措辞更正（`#issuecomment-6906908128`、`#issuecomment-6906908646`）。贴完再把重建出来的两条 ref 删回原样（`DELETE /git/refs/heads/...` http 204 ×2），处置后读数为远端 `refs/heads` 只剩 `main`，两个 PR 各 `comments=2`、状态仍 `closed`。

**教训记两条**：一是删分支的祖先检查盖不到 PR 这本账，要先 `GET /pulls?state=all` 看 head 引用；二是「计数滞后一到两次写入」的平台字段不能当反证——我先是把中间态写成永久结论，靠一次重读才翻回来。中文评论体另有一处坑，且归因走了两个来回才定准：`--data-binary` 传 `JSON.stringify(...)` 再 `toString('latin1')` 的字符串时，POST 评论直接 `400 Problems parsing JSON`。第一反应是「latin1 把 U+00FF 以上截成低字节」，本地一验就推翻了——`Buffer.from(j,"utf8").toString("latin1")` 是逐字节映射，长度 47/47、回环相等。真正归因用了一个无副作用的探针（`POST /markdown`，同一对中文体两条通道）：argv 通道 http 400，stdin 通道（`--data-binary @-` + `input:`）http 200——坏在 Windows 把 ≥0x80 的 argv 字符再编码一次，到服务端已不是合法 JSON 字节；纯 ASCII 体本来就不受影响，我先前那句「最小 ASCII 体也 400」是没测过的臆断，收回。改走 UTF-8 stdin 后评论 201。
