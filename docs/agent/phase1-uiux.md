## 0. 演进叙事：从「代码为主」到「Agent 运行过程可见」

既有 CodeLens 的设计语言是 **「深色 IDE 工作台」**——左会话 / 中代码 / 右 Agent 输出，chrome 退到几乎不可见，**代码与分析结果是唯一主角**。

本次改造的语义变了：产品从「代码分析 Agent」变成「通用 Agent 工具调用平台」，主角从**静态产物**变成**动态运行过程**。用户要看的不是"分析结果长什么样"，而是"Agent 此刻在干什么、它刚刚动了什么手脚、它凭什么这么判断、哪些操作我必须点头"。

因此演进叙事定为：

> **代码编辑器让位给「运行过程」，结果卡让位给「调用记录」。**
> 界面从「编辑器 + 对话侧栏」升级为「Agent 运行时控制台」。

三条具体变化（不是推翻，是换血）：

| 维度 | 既有 CodeLens | 本次改造 |
|---|---|---|
| 中栏主角 | 代码编辑区（CodeMirror） | **Agent 对话流**（工具调用与文本交替的时序流） |
| 右栏语义 | 结构化结果（问题定位/根因/修复/diff 五卡） | **运行检视器 Inspector**（工具详情 / 上下文与记忆 / 运行日志） |
| 交互焦点 | 提交一次分析 → 等结果 | **持续监督**：看调用 → 必要时点头 → 看结果 → 再看下一轮 |

**留下的东西**（设计连续性硬要求）：Signal Blue `#197FE6` 主色、双主题 + 跟随系统、Inter + Noto Sans SC + JetBrains Mono、Lucide React 1.60.0 唯一图标库（16/20/24px / stroke-width 2）、4px 间距网格、4/8/12 圆角、150/250ms 动效 + caret、rest 用边框不用阴影、禁弹跳缓动、状态栏 28px、焦点环 `:focus-visible` 双层、1px `border-border` 硬分割的 IDE 窗格语言。

## 1. 设计方向与对标品牌

### 1.1 主对标：**Claude Code**（Anthropic 终端 UI）

选它的理由不是"它也是 AI 工具"，而是**它是目前把「工具调用过程可视化」做得最完整的产品**：

- **三段式渲染模型**：每个工具定义自己的 UI 逻辑，分别渲染 `ToolUse`（调用意图：工具名 + 参数）→ `Progress`（执行中：spinner / 实时输出）→ `ToolResult`（结果：diff / 日志 / 表格）。这正好是本项目"工具卡片三区"的原型。
- **权限门内联**：权限请求不弹窗，直接在对话流的工具调用位置呈现；高危动作走 `Permission Request` 组件，读取类操作直接跳过。
- **Compact 边界标记**：上下文被压缩时，在**被截断的那个位置**插入一条视觉指示器（`CompactBoundaryMessage`），而不是全局弹 Toast。这是本项目"压缩 notice 内联"的直接来源。
- **结果状态三分**：`UserToolSuccessMessage` / `UserToolErrorMessage` / `UserToolCanceledMessage` / `RejectedToolUseMessage` 各自独立组件——证明"失败 / 取消 / 被拒"是三种不同视觉语义，不能合并成一个红色叉。
- **截断策略可量化**：Bash 工具非 verbose 模式截断到 2 行或 160 字符——给了本项目"预览截断"一个可对标的量化锚点。

**不足与本项目的偏离**：Claude Code 是终端字符网格，无法承载 JSON 语法高亮与 hover 复制按钮；其工具名直接暴露内部命名（如 `Bash`、`Read`），对本项目的 MCP 工具不够用（本项目需要 serverName 分层）。

### 1.2 辅对标：**MCP Inspector**（官方 MCP 调试工具）

选它是因为**它定义了 MCP 配置区的 UI 惯例**，本项目的 MCP 设置必须与之对齐，否则用户照着文档学 Inspector 之后回到本产品会认不出：

- **左配置 / 中列表 / 右结果**的三段工作区布局，配置区字段固定为 `Transport Type` + `Command` + `Arguments`。
- **绿色 "Connected" 指示灯** + 工具数徽标（`Tools (3)`）的连接状态表达。
- **Tools / Resources / Prompts 分 Tab**，每 Tab 顶部显示数量。
- **Message Log 面板**按时间顺序记录 JSON-RPC 消息（`→ initialize` / `← initialized` / `→ tools/list` / `← tools (3 tools)`），方向箭头 + 事件名 + 数量。
- **错误结构化**：`{ "error": { "code": -32602, "message": "Invalid params: 'b' is required" } }`，JSON-RPC 标准错误码（-32700 / -32600 / -32601 / -32602 / -32603）。

**不足与本项目的偏离**：Inspector 是给开发者的调试台（信息全暴露、无产品化收敛）；本项目的 MCP 区要给普通用户看，所以连接失败必须给「人话原因 + 一个恢复动作」，而不是甩一段 JSON-RPC 报文。

### 1.3 明确不参考的

- **通用聊天产品（ChatGPT / Claude Web 单栏居中流）**：单栏会让右栏的 Inspector 消失，工具参数全挤在窄条里，无法做双层模型。
- **Cursor 的 diff 主导呈现**：本项目不是代码编辑器，diff 只作为文件读写工具的一种结果形态存在，不占主轴。

### 1.4 氛围关键词

克制、可审计、连续、克制留白、可打断。

## 2. 主界面布局

### 2.1 决策：保留三栏，但右栏语义彻底换血

**结论：桌面 ≥1024 保留三栏 —— 左「会话列表」/ 中「Agent 对话流」/ 右「运行检视器 Inspector」。中栏内容整体换血（CodeEditor → AgentConversation），右栏语义整体换血（结果五卡 → Inspector）。**

论证（逐条驳掉"该砍成双栏"）：

1. **砍右栏省下的宽度救不了 JSON**。工具调用的信息量在参数与结果里，两栏布局下这些 JSON 只能全塞进中栏，对话流立刻退化成"JSON 浏览器"——用户会滚着滚着忘记 Agent 说了什么。宽度不能解决信息分层问题。
2. **右栏不是"另一份结果"，而是"同一份结果的深潜层"**。对话流做**扫读层**（一行摘要 + 就地折叠展开，覆盖 90% 场景）；右栏做**深潜层**（完整参数 / 完整响应 / 错误栈 / 重试历史 / 时间线 / 原始报文），覆盖"我要审计这个 Agent 到底干了什么"的 10% 场景但价值极高。这是**渐进披露**，不是信息重复。
3. **三栏骨架是既有设计语言的一部分**。深色 IDE 工作台的"1px `border-border` 硬分割窗格"是 CodeLens 已交付的视觉资产，砍掉右栏等于承认上次的设计语言作废——这对一个改造项目是净损失。
4. **但右栏不能同时装三样东西**（上下文 + 记忆 + 日志 = 超载，违反可见选项 ≤4）。所以右栏做成**单一 Inspector 上下文**：内容由"当前选中对象"决定，同一块 420px 面板在三种内容源之间切换。

**Inspector 的三态内容源**：

| 选中对象 | Inspector 内容 |
|---|---|
| 某次工具调用（点卡片标题栏） | **工具详情**：完整参数 JSON / 完整返回 / 错误详情与原始响应 / 重试历史 / 调用时间线 |
| 工具调用卡片展开态（点「在检视器中打开」） | 同上 + 「固定」标记，可并排比较两次调用 |
| 无选中（默认） | **运行概览**：上下文用量分段分解 / 记忆条目 / 本轮调用统计 / 最近的失败 |

**右栏可折叠为 44px 图标轨**（Rail），折叠后中栏获得全宽，状态记忆在 localStorage。这是 IDE 惯例（Cursor 右栏可折叠），也是"专注阅读长回复"的需求。

## 3. 工具调用可视化设计（核心）

### 3.1 信息架构：一张工具卡片的解剖

```

#### 3.1.1 HEADER 字段规格

对齐 PRD §6.1「工具调用可视化：每张卡片必须展示什么」+ PM 交办的**卡片八字段**（类别图标 / 标识符 / 来源徽标 / 风险徽标 / 状态 / 耗时 / 参数 / 结果+错误区）：

| 字段 | PRD 要求 | 内容 | 样式 | 规则 |
|---|---|---|---|---|
| 类别图标 | 必显 | Lucide 组件，按 `category` 映射（见 §3.9） | 16px，`text-text-secondary` | 唯一图标库，不混用；同一 `category` 恒定同一图标 |
| **工具标识符** | 必显 | **规范名**（点号），如 `http.request` / `fs.read` / `mcp.filesystem.read_file` | `font-mono` `text-sm` `text-text-primary` | **主位，单行**。等宽因为它是代码标识符不是自然语言（PRD §6.1 原文）；它同时是 `tool_calls.tool_name` 的落库值，**卡片显示 = 审计记录显示**，用户复制出去即可检索。**显示规范名而非线上名**（见下方「两个名字」） |
| 来源徽标 | 必显 | `内置` / `filesystem`（MCP server 名） | `text-xs`，底 `bg-bg-tertiary`（内置）/ `bg-accent-subtle`（MCP），字 `text-text-secondary` / `text-accent` | MCP 徽标用 `accent-subtle` 底，**不用实心 accent**（守住每屏 ≤2 处纪律） |
| 风险徽标 | 必显 | `低` / `中` / `高`（取 `tool_call` 事件的 `risk` 字段） | `text-xs`；低 = `text-text-tertiary` 无底；中 = `bg-warning-subtle`+`text-warning`；高 = `bg-danger-subtle`+`text-danger` | **卡片上低风险不显示徽标**（见下方说明）；设置页显示全部三级 |
| 状态 | 必显 | 见 §3.2 状态机 | 16px 图标 + 文字，位于耗时左侧 | 状态**永远**是"图标 + 文字"双通道（不靠颜色单独传达，符合既有附 B） |
| 耗时 | 必显 | `1.2s` / `38ms` | `font-mono` `text-xs` `text-text-secondary` | `<1s` 用 ms，`≥1s` 用 s 保留 1 位；>60s 显示 `1m 12s` |
| 相对时间戳 | 必显 | `+1.2s`（距会话开始的相对时刻，PRD §6.2） | `font-mono` `text-xs` `text-text-tertiary` | 与组内其他卡片形成时间轴，让用户看出**哪一步慢** |
| 所属轮次 | 必显 | `第 3 轮`（PRD §6.1「所属轮次」） | `text-xs` `text-text-tertiary` | 同轮多次调用时**只在组头显示一次**（组内每行不重复），避免噪音 |
| 结果摘要 | 必显（折叠态一行） | `tool_result.summary`（服务端生成，前端直接渲染） | `text-xs` `text-text-secondary` | 折叠态的唯一内容行；展开态由结果区接管。**前端不按类别二次拼装** |
| 折叠箭头 | 必显 | `ChevronDown` / `ChevronRight` | 16px `text-text-tertiary` | 键盘 `Enter`/`Space` 等价 |

**两个名字：规范名（点号）vs 线上名（下划线）**（架构 C-1 · §6.1.1）

这是一个 **P0 级技术约束**，直接决定卡片显示什么：

> 所有 OpenAI 兼容 provider 强制 `tools[].function.name` 匹配 `^[a-zA-Z0-9_-]{1,64}$`，**点号非法 → 整个请求 HTTP 400**（不是跳过单个工具，是整次调用失败）。

因此双轨制：

| | 规范名（canonical） | 线上名（wireName） |
|---|---|---|
| 形态 | `http.request`（点号） | `http_request`（下划线，消毒后） |
| 用途 | 内部标识 / 落库 `tool_calls.tool_name` / **前端卡片展示** / 审计检索 / 用户复制 | **仅下发给 LLM** |
| 用户可见 | 是 | **否** |

- **卡片显示规范名**——「所见 = 所存 = 可检索」成立：用户复制 `http.request` 去检索审计记录、报错信息、落库数据都能对上。若卡片显示下划线形式，用户复制出去就查不到（因为落库的是点号），反而破坏可追溯性。
- **设置页工具详情**可额外展示线上名 + 一句说明「下发时转换为下划线形式」——这是面向开发者的透明度补充，不上卡片。
- 该约束也解释了为什么 MCP 工具的规范名用 `mcp.<serverId>.<tool>`（点号，与内置工具同构，架构 C-10）：**规范名空间与线上名空间解耦**，点号带来的可读性不污染协议层。


**结果摘要由服务端生成，前端只渲染**（架构 §8.1 `tool_result.summary`）——这是折叠态下用户唯一能看到的结果，必须一眼可读。

| 类别 | 服务端生成的摘要句式 | 示例 |
|---|---|---|
| HTTP | `状态码 · 字节数` | `200 · 2,031 字节` |
| 文件 | `行数 · 体积` / `路径（字节数）` | `118 行 · 4.2 KB` / `读取 sandbox/notes.txt（128 字节）` |
| 计算 | 直接给数值 | `38.52` |
| MCP | `serverName · toolName` | `filesystem · read_file` |

> **前端不做按类别二次拼装**：摘要在服务端生成后随 `tool_result` 下发，前端原样渲染。这样摘要规则由后端单点维护，前端无需为每个类别写分支——若前端自行拼装，规则一旦调整就要改前端，且两端句式必然漂移。

**为什么低风险不显示徽标**：如果 90% 的调用都挂一个"低"字徽标，用户会学会完全忽略这一列，徽标就丧失了"高危值此一眼"的信号价值。所以卡片上只显示 `中` / `高`，用**稀缺性**制造注意力。设置页是完整清单，用户在那里建立"哪些是低风险"的心智模型，那里显示全部三级。

**`displayName`（人话名）不出现在卡片上**（PRD §5.2 明确其用途是「设置页 / 审批条 / 示例任务」）。设计理由：卡片的角色是**执行日志**，落库字段是 `tool_calls.tool_name`（标识符），显示标识符保证"所见 = 所存 = 可检索"。而"用户选工具"的那三个场景（设置页清单、审批条、空状态示例任务）恰恰需要人话名，所以 `displayName` 出现在那三处——**职责分离，各用其所长**。右栏 Inspector 详情页额外展示 `displayName` 作为副标题（那是审计场景，完整上下文优先）。

### 3.2 状态机视觉（7 值 status：PRD 六态 + skipped 衍生态）

PRD §6.1 锁定的六态：**待确认 / 执行中 / 成功 / 失败 / 已拒绝 / 超时**（PM 已确认采纳「超时 ≠ 失败」的视觉区分）。下表把它映射到本项目既有的 Token 与图标：

| 状态 | 触发 | 图标（Lucide 16px） | 颜色 | 参数区 | 结果区 | 错误区 |
|---|---|---|---|---|---|---|
| `pending` 待确认 | 调用已生成、等待调度或等待用户批准 | `Circle` 虚线 / `Clock` | `text-text-tertiary` | **默认展开** | 空占位（1px 虚线框 + `等待执行…` text-xs tertiary） | — |
| `running` 执行中 | 正在执行 | `Loader2`（animate-spin） | `text-accent` | 默认展开 | `等待响应…`；HTTP 若服务端支持流式则实时流入 | — |
| `success` 成功 | 正常返回 | `CircleCheck` | `text-success` | **默认折叠** | 预览 + 展开 | — |
| `failed` 失败 | 工具报错（限流 / 参数非法 / 权限拒绝 / 目标不存在 / 内部错误） | `CircleX` | `text-danger` | **默认展开** | 空 | **显示**（错误区） |
| `rejected` 已拒绝 | 用户在确认条上拒绝 | `Ban` | `text-text-secondary` | **默认展开** | 空 | 显示一行「已由你拒绝，未执行」 |
| `timeout` 超时 | 工具自身超时未返回 | `Clock` + `TriangleAlert` | `text-warning` | **默认展开** | 空 | **显示**（warning 色，非 danger） |

> **PRD §6.1 六态与 §6.3「从某步重跑」的衔接（已裁决）**：PRD §6.3 要求"被截断的步骤标记为「已跳过」而非删除"，但 §6.1 的六态里没有「已跳过」的位置。**架构 §8.1 已锁定 `tool_result.status` 为 7 值**——PRD 六态（待确认/执行中/成功/失败/已拒绝/超时）+ `skipped` 衍生态，并注明"对齐 PRD §6.1 六态 + UIUX §3.2.1 衍生态"。用户侧仍是 6 种可理解的状态，`skipped` 按历史注脚呈现。

#### 3.2.1 「已跳过」的落位：`skipped` 衍生态（已裁决）

「从某步重跑」会把该步之后的调用标记为已跳过（PRD §6.3），这是一个**必须可见**的状态——被跳过的步骤仍可展开查看，删掉就丢了审计线索。但它挤不进六态的任何一个位置：

- 它不是 `failed`（没有失败，是被取代）
- 它不是 `rejected`（不是用户拒绝，是系统重跑决策）
- 它不是 `success`（没执行成功，是没执行）

**设计解法：`skipped` 作为 `status` 的第七个可选值，但视觉上按「历史注脚」处理**——即：DB 层 `tool_calls.status` 允许 `skipped`（枚举 7 值），UI 层把它渲染为**最弱的存在感**：

| 维度 | `skipped` 表现 |
|---|---|
| 图标 | `CircleSlash` 16px |
| 颜色 | `text-text-tertiary`（最弱） |
| 整卡 | `opacity-60`（读起来像历史注脚而非待处理项） |
| 参数区 | 默认折叠 |
| 错误区 | 不显示（这不是错误）——改显示一行「此步已被跳过 · 原因：从第 2 步重跑」+ `[查看]` |
| 分组 | 计入所属轮次的调用总数，但**不计入「失败数」** |

**裁决落点**（架构 §8.1 已采纳）：
- `tool_result.status` 锁定 7 值：`pending` / `running` / `success` / `failed` / `timeout` / `rejected` / `skipped`。
- PRD 六态保持不变，`skipped` 作为第七值，**UI 按历史注脚呈现**（可展开查看、不计入失败数）。
- 这样既保住六态的视觉契约（用户只需理解 6 种状态），又让 §6.3 的审计线索有落点。

**决策：running 用 spinner，不用骨架屏。**

理由（四条，按重要性）：
1. **骨架屏承诺了错误的未来**。`.skeleton` 暗示"内容形状已知、大小已知"，但工具结果可能是一段 JSON、一段日志、一份文件、甚至空——形状完全未知。骨架屏会让用户误以为"快好了"，实际可能还要等 30s。
2. **工具执行通常 <1s**。骨架的 shimmer 动画 1.5s 一轮，多数 HTTP 调用在动画播完前就结束了 → 纯噪音。
3. **既有 Token 已有明确分工**：`.skeleton` 用于"排队等首 token"（既有 UIUX §7.7），`.dot-pulse` 用于"三点脉冲"。工具执行期引入第三个占位形态会破坏既有动效语言。**不重复造**。
4. **spinner 是唯一诚实的"未知持续中"信号**，且 `Loader2` 已在既有代码中用于"测试连接中"（`SettingsModal.tsx`），语义一致。

**但对 HTTP 响应体做例外**：服务端支持流式响应时，响应体**实时流入结果区**（与 token 流同一渲染通道），此时结果区有内容在增长，spinner 依然保留在 header（表示"整个调用尚未结束"）。

**`tool_progress` 事件填充 running 态**（架构 §8.1 载荷 `{ callId, stage, message?, at }`）：结果区那一行不写固定的"等待响应…"，而是显示 `tool_progress.message`（如 `读取 sandbox/notes.txt`）。这让 running 态从"正在调用 X"升级为"正在读取 sandbox/notes.txt"——**spinner 表达"在动"，progress 表达"在动什么"**，两者叠加信息量差一个量级。无 `tool_progress` 事件时（非流式工具）回落到固定文案 `等待响应…`（text-xs tertiary）。

**failed / timeout / rejected / skipped 必须视觉区分**（这是很多产品做错的地方）：

- `failed` = 确定的错误，重试大概率还是失败 → **danger** 色，需要用户改变策略。
- `timeout` = 可能是暂时的（服务抖动、网络慢） → **warning** 色，重试是合理的第一步。**与 failed 同为错误态但不同色**，这是 PRD §6.1 明确要求的区分。
- `rejected` = **不是错误**，是用户的主动决策 → **中性**色（`text-text-secondary`），不染红。染色会让"我拒绝"看起来像"Agent 出错了"，是错误归因。
- `skipped` = 用户的重跑决策导致该步作废 → **最弱**的 `text-text-tertiary`，且整卡 opacity 降低，读起来像"历史注脚"而非"待处理项"。

**失败态不整卡染色**：卡片主体保持 `bg-bg-secondary` + 1px `border-border`（IDE 语言），只有状态图标与错误行用语义色。整卡 `bg-danger-subtle` 会让一条含 3 个失败调用的消息变成一整块红色，噪音压过信息（对比既有 UIUX §7.4 的卡片规范：error 用 `danger-subtle` 底 + 重试按钮，那是**消息级**错误卡；工具调用级失败是**行级**的，尺度不同）。

**失败默认展开**（PRD §6.2 明确要求）：错误是模态体验，不是罕见事件——用户第一眼就要看到错在哪。所以 `failed` 的参数区默认展开，与 `success` 的默认折叠相反。

### 3.3 参数区规则

| 规则 | 内容 |
|---|---|
| **默认展开策略** | pending / running / rejected / failed / skipped → 展开；success → 折叠（PRD §6.2：失败默认展开） |
| **折叠内容** | **真实的 JSON 前 12 行**（不是人为摘要）。理由：摘要会丢信息，且用户经常要直接复制原始参数给人看/排查 |
| **截断阈值** | JSON 行数 > 12 **或** 序列化后字符数 > 800 → 折叠，显示前 12 行 + 结尾一行 `… 省略 N 行（共 M 行）` + `[展开全部]` |
| **展开后** | 完整 JSON，不二次折叠；`max-height: 60vh` + `overflow-y: auto` |
| **语法高亮** | 复用既有 `rehype-highlight` + `design-tokens.css` 已定义的 `.hljs-*` 类名（`--c-syntax-keyword/string/comment/function/number/builtin`），代码块语言标记 `json` |
| **字体** | `font-mono` `text-code`（14px/1.6） |
| **key 呈现** | JSON key 原样显示，不做 camelCase 转换或美化 |
| **密钥脱敏** | key 匹配 `key|token|secret|password|authorization`（大小写不敏感，PRD §6.1 口径）时，值渲染为 `••••••` + 12px `EyeOff` 图标，tooltip「已脱敏」，点击「显示原始值」需再点一次（延续既有 `SettingsModal` 的 API Key 显示/隐藏模式） |
| **超长单值** | 单个字符串值 > 200 字符 → 该值单独截断为 `前 200 字符…[展开该值]`，不影响其余 JSON 排版 |
| **空参数** | `{}` → 显示 `无参数`（text-xs tertiary），不留空行 |
| **非 JSON 参数** | 工具参数若非对象（如 MCP 传纯字符串）→ 直接按纯文本 `<pre>` 渲染，不强制包成 JSON |

### 3.4 结果区规则

**三种呈现，按内容判定**：

| 结果形态 | 判定 | 呈现 |
|---|---|---|
| JSON | `content-type: application/json` 或可被 JSON.parse 成功 | 复用参数区的 JSON 折叠渲染器（**同一组件，不重复造**），语法高亮 |
| 纯文本 | 其余 | `<pre class="font-mono text-code">`，保留原始换行与缩进，不做智能折行（代码类结果折行会破坏可读性） |
| 落盘文件 | `tool_results.artifact_path` 非空（PRD §7.1） | 不内联渲染；显示 `完整结果已保存 · 128 KB` + `[下载为文件]` + `[在检视器中打开]` |

**预览截断规则**（对齐 PRD §6.1「完整结果超过 2KB 折叠」）：

- **两级阈值**：
  - **500 字符** = 内联预览长度（沿用任务要求；对标 Claude Code Bash 工具的 160 字符，本产品 payload 更大，放宽到 500）。
  - **2KB** = 完整结果内联折叠阈值（PRD §6.1）。超过 2KB 的结果默认只展示 `inline_preview`（PRD §7.1 的 `tool_results.inline_preview` 字段），完整内容走 `artifact_path` 落盘。
- **按行边界回退**：500 字符若落在行中间，回退到最后一个完整行，保证 JSON 结构不被截断成非法态。
- 结尾提示行固定格式：`… 省略 1,284 字符（共 2,031）`（等宽 text-xs tertiary）+ `[展开全部]`。
- 超过 2KB 时额外标注落盘路径（PRD §6.6 Edge 要求）：
  > `已截断 · 完整结果已保存到 workspace/artifacts/result_7f3a.json（12.4 KB，可下载）`
- 展开后不设上限（Inspector 内可滚动），但 **>10,000 字符**时在展开区顶部加一行 `结果较大（约 12.4k tokens），已占用较多上下文` + `text-warning`（借鉴 Claude Code MCP 工具的 10,000 token 警告阈值）。
- **结果区必须带语义标签**（一行 text-xs tertiary），否则用户分不清这是"HTTP 响应体"还是"读到的文件内容"：
  - `响应体 · application/json · 2,031 字符`
  - `文件内容 · src/services/order.ts · 118 行`
  - `标准输出 · 12 行`
  - `工具返回 · {content:[{type:"text",text:"…"}]}`（MCP 原始结构）

**复制与下载**：每个可复制区一个 `Copy` 16px 按钮（hover 显现、触屏常驻），点击后 150ms 内切 `Check`（`text-success`）1.5s 后恢复 + Toast「已复制」。复制内容 = 原始文本（JSON 复制为格式化后的 JSON，不含行号）。落盘结果额外给 `Download` 16px 按钮（PRD §6.1「下载为文件」）。

### 3.5 错误区规则

**结构（自上而下五层）**：

```
[超时] E_TIMEOUT                            ← 分类标签 + 错误码, font-mono text-xs
目标服务在 10s 内未返回响应                  ← 人类可读原因, text-base, text-text-primary
GET api.internal/orders 已连续失败 2 次      ← 上下文补充, text-sm, text-text-secondary
建议:该域名近期不稳定,可重试或改用备选接口  ← 下一步建议, text-sm, text-text-secondary
[重试] [查看原始响应] [复制错误详情]          ← 动作行, 16px 图标按钮
```

**错误分类标签 + 错误码映射表**（可执行，前端按 `error_kind` 查表渲染；PRD §6.1 要求"分类标签 + 原始错误消息 + 一句下一步建议"）：

| 分类标签 | 错误码 | 人类可读原因 | 标签语义色 | 恢复动作 |
|---|---|---|---|---|
| `超时` | `E_TIMEOUT` | 目标服务在 {N}s 内未返回响应 | warning | [重试] |
| `限流` | `E_RATE_LIMIT` | 已触发调用频率限制，{N}s 后可重试 | warning | [重试]（按钮 N 秒后启用，倒计时显示） |
| `参数非法` | `E_INVALID_ARGS` | 参数校验未通过：{field} {reason} | danger | [查看参数]（跳参数区并高亮该字段） |
| `权限拒绝` | `E_FORBIDDEN` | {tool} 未获得执行授权 | danger | [去工具设置授权] |
| `目标不存在` | `E_NOT_FOUND` | 找不到 {target} | danger | [重试] |
| `网络错误` | `E_NETWORK` | 无法连接到 {host}，请检查网络或服务地址 | danger | [重试] |
| `域名未授权` | `E_DOMAIN_NOT_ALLOWED` | 目标域名 {host} 不在 HTTP 白名单内 | warning | [加入白名单]（直达设置） |
| `路径越界` | `E_PATH_JAIL` | 路径 {path} 超出允许的文件根目录 | danger | [调整文件根目录] |
| `MCP 未连接` | `E_MCP_DISCONNECTED` | MCP 服务器 {server} 未连接 | danger | [重连] |
| `内部错误` | `E_TOOL_INTERNAL` | {tool} 内部异常 | danger | [重试] [查看堆栈]（折叠在高级区） |
| `E_PATH_JAIL` | 路径 {path} 超出允许的文件根目录 | danger | [调整文件根目录] |
| `E_MCP_DISCONNECTED` | MCP 服务器 {server} 未连接 | danger | [重连] |
| `E_TOOL_INTERNAL` | {tool} 内部异常 | danger | [重试] [查看堆栈]（折叠在高级区） |
| `E_RATE_LIMIT` | 已触发调用频率限制，{N}s 后可重试 | warning | [重试]（按钮 N 秒后启用，倒计时显示） |
| `E_PAYLOAD_TOO_LARGE` | 返回内容 {size} 超过 {limit} 上限 | warning | [查看前 500 字符] |

**重试按钮的行为定义**（对齐 PRD §6.3「单步重试 / 改参数重试」）：

- 重试 = **同参重试**（PRD「单步重试」）：同一工具名、同一参数重新执行，**不重新让模型决策**（区别于"让 Agent 换个思路"，那是另一个动作）。
- 成功后在卡片底部追加一行 `重试 1 次后成功`（text-xs success，带 `CircleCheck` 16px），**保留前一次失败记录**（PRD 承诺"前后两次结果都在"，不覆盖原记录）。
- 同一卡片重试次数上限 3 次，超出后按钮转为 disabled + 提示 `已重试 3 次`。
- **改参数重试**（PRD §6.3）：在确认条上可编辑参数 → 生成新令牌 → 重新确认 → 执行；**原参数保留在历史**。UI 上表现为参数区切换为可编辑态（JSON 编辑器）+ `[用新参数重新确认]` 按钮。
- **失败原因禁止空洞文案**：不出现 "Something went wrong" / "请求失败"。每条错误必须回答三问：发生了什么（分类标签 + 错误码 + 原因句）、为什么（上下文补充行）、怎么办（至少一个恢复动作 + 一句下一步建议）。这是既有 UIUX §7.8 规则在工具层的延伸。

### 3.6 多轮工具调用的组织规则

给六条**可执行**规则（不是原则，是前端可直接实现的判断）：

**规则 1 · 同工具连续合并**——同一 assistant turn 内，**连续**出现 ≥3 次**同工具名**的调用 → 合并为一个「调用组」（PRD §6.2「连续调用合并：同一轮内 ≥3 次连续调用折叠为『批量 N 次调用』」）。
> 头部：`[Globe] HTTP 请求 × 3   +2.1s   2.1s   [⌄]`
> 组内每行：一条摘要（方法+路径 / 状态点 + 耗时 + 相对时间戳），行高 24px。
> 默认折叠。

**规则 2 · 异工具不合并**——不同工具名的调用各自独立成卡。用户要能一眼看出"换工具了 = 意图切换了"，合并会抹掉这个信号。

**规则 3 · 轮次边界用缩进表达**——每轮 assistant 消息的第一次工具调用，向上留 16px 间距 + 一条 1px `border-border-subtle` 分隔线。**不用左侧竖线**（侧条纹是明令禁止的反模式），也不用 `01/02` 编号标签。

**规则 4 · 单轮折叠阈值**——同一轮工具调用总数 > 8 → 该轮整体折叠为一行汇总：
> `本轮 14 次调用 · 3 失败 · 12.4s   [展开]`
> 展开后恢复为独立的卡片/组。

**规则 5 · 跨轮绝不合并**——不同轮次永远是不同意图，任何情况下不跨轮合并。

**规则 6 · 组内不逐条就地展开**——调用组展开后，每行点击 → **在右栏 Inspector 打开该次调用的详情**，不在对话流内逐条展开 JSON。理由：对话流是扫读层，一旦在流内展开 JSON，滚动位置与阅读节奏同时崩掉。**单卡（非组）**的展开仍在原地——单卡展开是偶发行为，组内逐条展开是必然行为，必须区别对待。

**规则 7 · 相对时间戳让"哪一步慢"可见**（PRD §6.2）——每张卡片带 `+1.2s` 相对时刻；**组间显示间隔**，例如两组之间标注 `间隔 3.4s`。用户扫一眼时间轴就知道时间花在哪，不用逐条读耗时。

### 3.7 高危工具的审批交互

**形式：就地 inline 确认条（不弹窗、不打断）**，档位强度按 PRD §6.4 三档确认。

PRD §6.4 的核心结论：**不能所有操作都弹窗（用户会无脑点穿），也不能都不弹（不可逆损害无人把关）**。因此确认强度分三档，**由 `ToolDefinition.risk` + 操作性质共同决定**：

| 档位 | 触发条件（PRD §6.4） | 交互形态 | 视觉 |
|---|---|---|---|
| **无确认** | 低风险只读操作（`fs.read` / `fs.list` / `calc.evaluate` / `time.now` / `uuid.generate` / `json.format` / `text.diff`） | 直接执行，结果区出现后置撤销入口 | 无提示 |
| **软确认** | 可逆写入（`fs.write` 新建文件、HTTP GET/HEAD） | 执行后 **30 秒撤销横幅**（PRD §6.4 原文） | 底部横幅 `bg-bg-tertiary` + 1px `border-border` + `[撤销]` 文字按钮 + 30s 倒计时进度条（`bg-accent`，`width` 动画禁用 → 改用 `transform: scaleX`） |
| **硬确认** | 破坏性 / 对外写（`fs.write` 覆盖或删除、非 GET 的外部 HTTP、MCP 写操作） | **就地 inline 确认条** | `bg-warning-subtle` 底 + 1px `border-warning` + `rounded-md` |
| **两步确认** | 灾难性 / 不可逆对外 | 硬确认条 + **需手动键入确认短语** | 硬确认条内追加 `font-mono` 输入框 |

**硬确认条**（本项目的主形态，就地 inline 不弹窗）：

```
┌─ 硬确认条 ───────────────────────────────────────────────────┐
│ [TriangleAlert] 高风险操作需要你的确认                        │
│ HTTP 请求 将向 api.stripe.com 发起 POST 请求                 │
│ 目标域名不在 HTTP 白名单内 · 影响范围:创建真实订单           │
│ [查看完整参数]                                                │
│                                                               │
│ [拒绝]  [允许一次]  [本次会话始终允许]                       │
└───────────────────────────────────────────────────────────────┘
```

- **视觉**：`bg-warning-subtle` 底 + 1px `border-warning` 边框 + `rounded-md`（内嵌于卡片内，不是独立卡片）。图标 16px `TriangleAlert` `text-warning`。
- **文案三要素**：工具 + 动作 + 影响范围。禁止"是否允许执行？"这类空洞提问。PRD §6.4 要求"完整展示目标 + 完整参数 + 影响范围"——参数通过 `[查看完整参数]` 就地展开（不跳 Inspector，保持上下文连续）。
- **三个动作**（可见选项 3 个，符合 ≤4 规则）：

| 动作 | 样式 | 行为 |
|---|---|---|
| **拒绝** | Ghost，`text-danger` | 卡片转 `rejected` 态；参数区保持展开；**拒绝原因作为一条 observation 回喂模型**（PRD §6.3），且模型**不得对同一 (工具, 参数) 再次发起调用**；拒绝记录进 `approvals` 审计表 |
| **允许一次** | Primary，`bg-accent` + `text-text-on-accent` | 执行本次；该工具下次仍需审批 |
| **本次会话始终允许** | Secondary，1px `border-border` | 执行 + 该工具在当前会话内免审批（存服务端 session；会话列表该行显示 `已记住 2 条授权`） |

**两步确认**（灾难性操作，罕见）：在硬确认条内追加一个 `font-mono` 输入框，要求键入服务端下发的确认短语（如 `DELETE workspace`）。**输入短语正确前，"允许一次"按钮 disabled**。短语本身由服务端生成并随待确认调用下发——客户端不可自行推断（与下条安全原则一致）。

**服务端持有原则对 UI 的约束**（PRD §6.4 / §16 S5，安全硬要求）：

> 待确认的工具调用由**服务端**保存并签发令牌（绑定 `sessionId` + `toolCallId` + 工具名 + 参数 + 5 分钟过期）。客户端回传的只有「sessionId + 令牌 + 决定」。**服务端绝不接受客户端提交的工具调用内容**——否则 XSS 或提示注入即可让用户批准的与实际执行的不一致。

对设计的直接约束（这三条必须落到 UI 上，否则安全承诺是假的）：
1. **确认条展示的参数必须是服务端下发的**，不是前端本地缓存的 args。参数区显示的是"服务端已锁定的那份参数"。
2. **令牌 5 分钟过期** → 确认条显示剩余有效时间；令牌失效时按钮全部 disabled + 显示 `确认已过期,此调用已取消`（并按 §3.7 硬超时规则把卡片置 `rejected`）。过期不可静默——静默会让用户以为还在等待批准。
3. **客户端只回传「决定 + 令牌」** → 「改参数重试」必须走服务端重新签发令牌（新参数 → 新令牌 → 重新确认），不能由前端改完直接提交执行。这条决定了「改参数」按钮的行为：**它不是"提交修改"，而是"请求重新确认"**。

**焦点纪律**：确认条出现时**不抢焦点**——不能把用户正在读的正文抢走。改为：输入框上方出现一行 `text-xs` 提示 `1 个操作待确认` + 右下角浮动提示（`shadow-overlay` + `rounded-full`）。键盘用户 `Tab` 可达，`Enter` 触发焦点按钮。

**硬超时**：审批等待超过 **5 分钟**（与令牌过期时间一致）无响应 → 自动按「拒绝」处理，卡片置 `rejected`，原因写 `5 分钟内未响应，按拒绝处理`。理由：让 Agent 无限挂起会锁死整条会话。

- **审批粒度**：按「工具 + 风险等级」而非「单次调用」。同一次审批不覆盖后续同类调用，除非用户显式选「本次会话始终允许」。
- **移动端**：改为底部 ActionSheet（既有约定），仍允许下滑取消 = 拒绝。

**决定提交后的流转**（架构 C-4 落地细节）：用户点「拒绝 / 允许一次 / 本会话始终允许」→ 前端 `POST /api/v1/approvals/:id`，body 只含 `{ token, decision, reason? }`（**不含工具名与参数**——那些由服务端从 `approvals` 表取）→ 服务端校验令牌 → **在原 SSE 流上推送 `tool_result`**（`status: 'rejected'` 或继续执行并推 `status: 'success'|'failed'`）→ 前端据 `tool_result.status` 把卡片转终态。

> **前端不自行改卡片状态**：拒绝后卡片转 `rejected` 是由服务端推送的 `tool_result` 驱动的，不是前端乐观更新。理由与 §3.7「服务端持有」同源——若前端先改状态、后端实际执行了（或拒绝了），两边就会不一致，而用户正是靠这个状态判断"我的操作到底生效没有"。

### 3.8 风险等级定义

对齐 PRD §5.1 工具总表、PRD §5.2 `ToolDefinition`，与架构 C-8 的**两维模型**：

- **`risk`**（`low` / `medium` / `high`）—— 描述**影响面**（这件事有多危险）
- **`approvalMode`**（`none` / `soft` / `hard` / `two_step`）—— 描述**交互强度**（要用户付出多少确认成本）

> 为什么是两个独立维度而不是一个布尔：PRD §5.2 明确「风险与确认档位是两个独立维度」。`requiresApproval: boolean` 表达不了 soft / hard / two_step 三档差异——软确认根本不需要"批准"，它需要的是"事后可撤销"。架构 C-8 已裁定采用两维模型。

| `risk` 等级 | 判定标准 | PRD §5.1 工具与档位 | 对应 `approvalMode` |
|---|---|---|---|
| **低** (`low`) | 只读、不外发、无副作用、可无限重试 | `fs.read`、`fs.list`、`calc.evaluate`、`time.now`、`uuid.generate`、`json.format`、`text.diff`；`http.request` 的 GET/HEAD | `none` |
| **中** (`medium`) | 有网络出口或写操作，但范围受限、可回滚 | `fs.write` 的新建 / 追加 / 重命名 | `soft` |
| **高** (`high`) | 触及外部系统、影响范围不可预判、或有破坏性 | `fs.write` 的覆盖已有文件 / 删除；`http.request` 的 POST/PUT/PATCH/DELETE；MCP 写操作 | `hard`（灾难性场景 `two_step`） |

**风险是"工具 + 操作"的二元判定，不是纯工具属性**——这是 PRD §5.1 的关键设计：同一个 `fs.write`，新建文件是中风险（软确认即可），覆盖已有文件是高风险（必须硬确认）；同一个 `http.request`，GET 是低风险，DELETE 是高风险。因此：

- `ToolDefinition.risk` 与 `ToolDefinition.approvalMode` 是**基线值**，实际值由「基线 + 本次操作的具体参数」共同决定——**由服务端在 `tool_call` 事件中判定并随事件下发**（架构 C-5 / C-9，架构 §6.3 已落完整运行期判定表）。
- 前端**不自行推断**风险等级或确认强度，一律渲染服务端下发的 `risk` 与 `approvalMode`。这与服务端持有原则（§3.7）一致：前端不能成为安全判定的第二来源。
- 字段名以架构契约为准：`risk`（不是 `riskLevel`）、`approvalMode`（不是 `requiresApproval`）。


**确认强度四值（架构 §6 `ToolApprovalMode`：`none` / `soft` / `hard` / `two_step`）与风险的对应**：

| `approvalMode` | 触发条件 | UI 形态 |
|---|---|---|
| `none` | 纯只读、无副作用 | 直接执行，无提示 |
| `soft` | 可逆写入 | 执行后 30 秒撤销横幅 |
| `hard` | 破坏性 / 对外写 | **就地 inline 确认条**（本项目主形态，不弹窗） |
| `two_step` | 灾难性 / 不可逆对外 | inline 确认条 + 键入或勾选确认短语 |

**MCP 工具默认高风险**——用户装一个第三方 MCP Server 时无法预知它会做什么，这是诚实的默认。装完后可在设置页逐个下调（MCP 生态信任是逐步建立的，不是一次性买断）。架构 §6.1.1 补充了一条硬约束：MCP 工具的 `risk` 默认 `high`，用户**可下调但不得自动调高到 `low`**——这是安全底线，UI 的下调滑杆不应提供"调到低"以外的越权选项。

按 PRD §6.1「类别图标 = HTTP 用箭头、文件用文档、计算用计算器、MCP 用插头」的口径：

## 4. 流式渲染细节

### 4.1 事件序列与渲染结构

服务端 SSE 事件序列（**已按架构 §8.1 锁定契约**）：

```
meta → delta → delta → tool_call → tool_progress* → tool_result → delta → … → done
```

**工具相关只有 4 个事件**（架构 §8.1 跨文档裁决 C-2）：`tool_call` / `tool_progress` / `tool_result` / `tool_approval_required`。`rejected` / `skipped` **不单独设事件**，由 `tool_result.status` 区分（`status: 'rejected'` / `'skipped'`）——前端不必为每个状态写一个分支。

> 文本增量事件名沿用现有 `delta`（架构 C-3）：既有 `stream.ts` 的 `case 'delta'` 已在消费，改名会引入回归风险。本文档早期写的 `text-delta` 已对齐为 `delta`。

> **事件名以架构 §8.1 事件表为准，全部为下划线形式**：`meta` / `delta` / `reasoning` / `tool_call` / `tool_progress` / `tool_result` / `tool_approval_required` / `context_notice` / `done` / `error`。
> 实现提醒：架构 §16.1 的 C-2 **裁决正文**把这套命名描述为「中划线（kebab-case）」，但它自己的 §8.1 事件表与全文 114 处引用用的都是**下划线**——C-2 正文的 kebab-case 是**标签笔误**，不要照它写 `case tool-call`。前端按 `event.type` 匹配请一律用**下划线**。（已向架构反馈，见附 D.4）

**渲染为一条 assistant 消息内部的时序流**，不是多个消息气泡：

```
┌─ AI 消息 (单条) ──────────────────────────────────────┐
│ 文本段: 我先拉一下订单服务的原始响应,确认是接口慢还是… │
│                                                        │
│ ┌─ 工具卡 (success) ──────────────────────────────┐   │
│ └──────────────────────────────────────────────────┘   │
│                                                        │
│ ┌─ 工具卡 (running) ──────────────────────────────┐   │
│ │ [Globe] HTTP 请求 [内置]  POST …/retry  ▏spinner│  │
│ │  等待响应…                                       │   │
│ └──────────────────────────────────────────────────┘   │
│                                                        │
│ 文本段: 响应显示 200 但耗时 9.8s,问题在下游…          │
└────────────────────────────────────────────────────────┘
```

**关键**：一条 assistant turn = 一条消息 = 内部文本段与工具卡交替。既有 `Message` 类型（`role: user|assistant` + `content: string`）扩展为 `content: Segment[]`，`Segment = { type: 'text', text } | { type: 'tool', call }`（架构 C-6 已锁定）。

服务端侧对应落库变更：`messages.content` **保持纯文本**（便于检索与摘要），新增 `messages.segments_json` 存分段结构（含工具卡占位与 `callId`），前端据此还原渲染。这是 Phase 3 前端改造的**最大结构性变化**。

### 4.2 caret 位置纪律

- caret（`stream-caret`，`--c-accent` 2px 竖条，1s step-end 闪烁）**只跟在最后一个文本段末尾**。
- 工具卡段**不显示 caret**——工具执行期间不是文本生成，光标闪烁会误导用户"还在写字"。
- 工具执行期间，在该工具卡**上方**显示一行 `text-xs text-text-secondary` + 16px spinner：`正在调用 HTTP 请求…`。
- 排队等首个工具调用（模型还在决定调什么）→ 显示既有 `.dot-pulse` 三点脉冲，不用骨架。

### 4.3 自动滚动纪律

延续既有 UIUX §8.1 + 借鉴 Cline 的阈值经验：

| 情形 | 行为 |
|---|---|
| 视口距底 ≤100px | 跟随滚动（token 流入时） |
| 用户上滚 | 立即锁定位置（解除程序化滚动），右下角浮现「跳到最新」（`shadow-overlay` + `rounded-full`） |
| **工具卡被就地展开** | **强制锁定滚动**，并把该卡**滚到视口内**（不是滚到底部）——否则用户点开参数 JSON，页面却跳到底部，阅读位置断裂 |
| 工具卡被收起 | 触发一次跟随滚动到底部 |
| 审批条出现 | **不触发任何滚动**（不打断） |

补充：Cline 用 24px（贴底判定）/120px（显示滚底按钮）双阈值。本产品沿用既有 100px 单阈值（不新增两套数字造成实现分叉），实现上以"距底 ≤100px 视为贴底"。

### 4.4 渲染节流

- 前端按 **30–60ms** 批量合并 token 渲染（沿用既有 §8.1，不逐 token 重排）。
- 工具卡插入时**不做节流缓冲**，立即渲染（用户要看的是"换动作了"这个信号，延迟它会破坏因果感）。
- 代码块未闭合时按纯文本等宽渲染，闭合后二次语法高亮（既有规则延续）。

#### 5.3.1 「MCP 未连接」的可感知提示（PM 交办项）

**问题**：PRD §11.3 的设计是「未连接的 MCP 能力对模型完全不可见」——这是正确的产品决策（避免闲置 server 抬高每轮成本、避免模型幻觉调用不存在的工具）。但它带来一个 UX 副作用：**用户装了一个 server 却发现 Agent 从来不用它，会以为 MCP 坏了**。PRD §8.3 也要求「server 起不来 / 超时 / 工具清单拉取失败 → 界面给修复入口」。

**设计解法：两级提示，都不打断对话流。**

**级别 1 · 状态栏常驻计数**（低噪音，默认在场）：

```
│ 状态栏 28px  ● 已连接 · deepseek-chat · 上下文 34% · 模式 FC · MCP 1/2 [TriangleAlert] [跳到最新↑]│
```

- `MCP 1/2` = 已连接 1 个 / 共配置 2 个。全部连上时不显示这段（不占噪音预算）。
- 有未连接时数字转 `text-warning`，并带 `TriangleAlert` 16px。**不弹任何东西**。

**级别 2 · 顶栏可点的提示条**（仅当存在"配置了但连不上"的 server 时出现）：

```
┌─ 顶栏下方 inline 提示条 (bg-warning-subtle, 24px 高) ──────────────────┐
│ [TriangleAlert] 1 个 MCP server 未连接,filesystem 的 4 个工具本次不可用 │  [去修复]
└──────────────────────────────────────────────────────────────────────────┘
```

- 位置：**顶栏下方通栏**（不是对话流内、不是弹窗）。对话流是主轴，提示条压在它上面会打断阅读。
- 文案说清**后果**而非只说事实：「4 个工具本次不可用」比「连接失败」有用得多——用户立刻知道 Agent 为什么没用它。
- `[去修复]` 文字按钮直达设置页 MCP 分区并高亮该 server。
- 多个未连接时显示 `2 个 MCP server 未连接,共 7 个工具本次不可用`。
- **连接成功后自动消失**（不是手动关闭——问题解决了提示就该走）。

**级别 3 · 发送前的软提醒**（当用户在本次会话中提到"用 filesystem 读文件"之类却因未连接而失败时）：错误区里补一句 `该 MCP server 未连接,重连后可用` + `[去修复]`，与 §3.5 的错误区结构一致。

> **为什么不做成常驻侧边栏或角标**：角标（badge）是小红点式的，用户不会点开看内容，而这里的用户恰恰需要知道"为什么我的工具没生效"——那是一句需要被读到的**解释**，不是一个需要被发现的**信号**。

### 5.4 安全边界可视化

**这是让用户"看得见 Agent 能碰什么"的地方**，独立分组，用 `border-t` + 小标题，不嵌套卡片。PRD §5.3 定义了四条硬边界，UI 必须把每一条的**当前生效值**显示出来——用户不该靠猜。

```

设计要点：

- **白名单为空时的文案是真实的约束陈述**，不是空洞占位：「未设置白名单，所有 HTTP 请求调用都会被拒绝」——用户立刻理解后果。
- **把"永远被拒绝的目标"显式列出**（内网 / 环回 / 云元数据地址）：这是 PRD §5.3 的硬规则且用户看不见它在生效。写出来比藏起来更安全——用户知道哪些地址永远不通，就不会去配内网域名然后困惑"为什么总是失败"。
- 域名用 `font-mono`（它是配置值不是自然语言），通配符 `*.internal.corp` 明确标注「通配符」。
- path jail 用 `FolderLock` 图标表达"受控目录"，路径 mono 显示；**额外一行说明符号链接的处理方式**（先解析后比较），因为这是用户最可能想钻的空子。
- **数据可携与可清除三键**（PRD §7.1）：「导出全部会话为 Markdown」「导出数据库文件」「彻底清除（含数据库文件与工作区）」。前两个是 `Download` / `Database` 图标，第三个是 danger 区的 `Trash2` + 二次确认。
- 每一项安全边界都在**运行日志**中留痕：被拒绝的越界调用出现在日志里，用户能看到"Agent 试过越界"。

### 6.1 会话列表（延续既有 + PRD §7.1 服务端持久化）

## 8. 通道模式标识（function calling vs ReAct 降级）

**低调但必须可感知。** 双通道降级是产品事实，用户需要知道"当前 Agent 的工具调用解析方式"，否则 ReAct 模式下多出的确认轮次会被当成 bug。

| 模式 | 标识位置 | 视觉 | 出现条件 |
|---|---|---|---|
| `function_calling` | 状态栏末段 | `模式 FC` — `font-mono text-xs text-text-secondary` | 默认。**不额外强调**，正常态即无需标注 |
| `react`（降级） | 状态栏末段 + **输入区上方一行** | 状态栏：`模式 ReAct` — `font-mono text-xs text-warning`；输入区上方：`TriangleAlert` 16px `text-warning` + 「兼容模式:本次以 ReAct 解析工具调用,可能需要更多轮确认」+ `text-accent` 文字链「了解」 | 当模型不支持原生 function calling 时 |

- **正常态不显示额外提示**——每屏噪音预算有限（既有 §3.4 强调色 ≤2 处纪律同理）。模式不是异常，不需要用户每次都看。
- 降级态在输入区上方提示，因为降级会**多出确认轮次**（ReAct 需要模型输出显式调用标记），这直接改变了用户的操作节奏，必须在动手前告知。
- 「了解」展开一个 inline 说明（不是新弹窗）：「当前模型不支持原生 function calling,平台已降级为 ReAct 模式解析工具调用。该模式下工具调用可能不准确,且需要更多轮确认。」
- **不做主题色区分**（不引入第二种色相），只用既有的 warning 语义色 + 文字。

| **触屏目标** | ≥44×44px，按钮间距 ≥8px | 工具卡内的图标按钮（复制/展开）在触屏下常驻显示且命中区扩到 44px（视觉仍是 16px 图标） |
| **reduced-motion** | 动效归零、caret 停闪、shimmer 停 | `Loader2` 旋转在 reduced-motion 下停止旋转，**但状态不能因此丢失** → 保留图标 + 「执行中…3.2s」文字（用数字时间代替旋转表达进行中） |
| **长内容** | — | 超长工具名/域名/path 用 `truncate` + `title` 属性全量；等宽字体下 path 截断保留**尾部**（尾部更有辨识度：`…/services/order-service.ts`） |
| **键盘与滚动** | — | 工具卡展开/收起不改变焦点位置；自动滚动被用户上滚打断后**不恢复**（除用户点「跳到最新」） |

1. **既有已上线代码已经在用规范名**——`Toast.tsx` / `ResultPanel.tsx` / `SettingsModal.tsx` 共 8 处用 `CircleCheck` / `CircleX`。继续用规范名 = 零改动，不产生同屏两种写法。
2. **旧别名是过渡期产物**——Lucide 1.x 大规模重命名后保留了旧名做兼容，未来版本可能移除。
3. **架构 §12.3 的表格用的是旧别名**（`CheckCircle2` / `XCircle`）——这与既有代码不一致，建议架构同步改为规范名，避免实现方照抄后与既有组件风格割裂。

### 10.3 需要前端结构性改造的点（给架构师与 Phase 3 的提醒）

1. **Message 类型扩展**：`content: string` → `content: Segment[]`（`{type:'text',text}` | `{type:'tool',call}`），这是流式渲染工具卡的前提。既有 `client/src/types/index.ts` 的 `Message` 接口需要扩展。服务端侧对应：`messages.content` 保持纯文本，新增 `messages.segments_json`（架构 C-6）。
2. **工具调用事件语义（架构 §8.1 已锁定）**：只需处理 **4 个工具事件**——`tool_call` / `tool_progress` / `tool_result` / `tool_approval_required`，每条携带 `callId` 以便乱序到达时正确归位。`rejected` / `skipped` 由 `tool_result.status` 区分，**不单独设事件**（架构 C-7）。`tool_result.status` 锁 **7 值**（`pending`/`running`/`success`/`failed`/`timeout`/`rejected`/`skipped`），与本文档 §3.2 状态表一一对应。
3. **审批回执通道（架构 C-4 已锁定）**：独立 `POST /api/v1/approvals/:id`，**不在 SSE 同流回传决定**。理由：审批可能跨数分钟（用户思考时长），SSE 长连接需靠 15s 心跳维持，不适合承载用户决策。服务端在审批前已把待执行调用**保存到服务端**（`approvals` 表 + 内存挂起句柄）并签发 `approvalToken`，客户端 body 只含 `{ token, decision, reason? }`——**服务端绝不接受客户端提交的工具调用内容**（PRD §6.4 服务端持有原则，防"批准的与实际执行的不一致"漏洞）。前端收到 `tool_approval_required` 事件（含 `reason` / `approvalToken` / `expiresAt`）后渲染 inline 确认条；**决定提交后由服务端在原 SSE 流上推送 `tool_result`，前端据其 `status` 转终态，不做乐观更新**（见 §3.7）。
4. **风险与确认档位随事件下发（架构 C-5 已锁定）**：服务端在 `tool_call` 事件中下发 `risk`（`low|medium|high`）与 `approvalMode`（`none|soft|hard|two_step`），**前端不自行推断**（§3.8 已论证：前端不能成为安全判定的第二来源）。
5. **压缩事件（架构 §8.1）**：事件名 `context_notice`，载荷 `{ reason: 'compacted'|'truncated'|'tool_result_compressed', removedMessages?, estimatedTokensBefore?, estimatedTokensAfter?, summaryPreview? }`。UI 按 §6.3 渲染内联 notice（插在被压缩的那一轮之前，不是末尾）；`reason` 三值对应三种措辞，不要统一成"已压缩"。
6. **模式字段（架构 §8.1 `meta` 事件）**：`meta` 首帧携带 `channel: 'native' | 'react'` 与 `degraded: boolean` 与 `degradedReason?`，另有 `iteration` / `maxIterations` / `contextWindow` / `estimatedPromptTokens` / `toolCount`。UI 按 §8 渲染模式标识——注意字段名是 **`channel`** 而非 `mode`。
7. **结果落盘字段**：`tool_results.inline_preview` + `artifact_path` + `bytes` + `truncated`（PRD §7.1）——前端按 §3.4 的两级阈值渲染，"下载为文件"直接用 `artifact_path`。
8. **不新增颜色 Token**——若实现中出现任何硬编码色值，视为违反 Spec §8 铁律。
