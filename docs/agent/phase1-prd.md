## 1. 产品定位与一句话描述

### 1.1 一句话描述

**CodeLens 是一个开箱即用的本地网页版通用 Agent 工作台——用一句自然语言交代目标，它自己决定调用哪些工具、传什么参数、循环多轮直到把活干完；工具调用过程逐条可视化，你可以随时打断、批准或重试；对话存在你自己的机器上，用自己的模型 Key，代码不外传。**

### 1.2 升级叙事：从「透镜」到「工作台」

CodeLens v1.0 是一个**单点工具**：你贴一段代码，选「分析 / 解释 / 调试 / 优化」，它给你结构化答案。它解决的是「看不懂这段代码」。

CodeLens v2.0 是一个**通用 Agent**：你交代一个目标（「把这个接口的返回转成 CSV 并算一下平均耗时」），它自己规划、调用工具、观察结果、修正、再来一轮，直到任务完成。工具调用过程是可见的、可干预的、事后可复盘的。

| 维度 | v1.0 代码分析 | v2.0 通用 Agent 工作台 |
|------|--------------|----------------------|
| 输入单位 | 一段代码 + 一个固定能力选择 | 一句自然语言目标 |
| 能力供给 | 4 个内置提示词模板 | 4 类可插拔工具（HTTP / 文件 / 计算与系统 / MCP） |
| 执行形态 | 一次 LLM 调用 → 一段结构化输出 | Agent 循环：规划 → 多次工具调用 → 观察 → 修正 → 结论 |
| 过程可见性 | 只有最终结果 | 每次工具调用的名称、参数、状态、耗时、结果逐条展示 |
| 人的介入点 | 换一段代码重来 | 随时打断、批准高危操作、单步重试、从某步重跑 |
| 状态持久化 | 浏览器 localStorage | 服务端 SQLite 文件，跨浏览器可用恢复码找回 |
| 扩展方式 | 改提示词模板 | **新增工具只需注册一条定义**（name + description + JSON Schema + handler） |

**不变的三条底线**（v1.0 已被市场验证，v2.0 继续继承）：BYOK 自带 Key（成本用户自控）、免登录（无账号体系）、数据优先留在本机（v1.0 是零留存，v2.0 是本地 SQLite 持久化 + 可一键清除）。

### 1.3 定位坐标（我们是什么 / 不是什么）

**是**：一个「能动手」的 Agent 工作台——重点在工具调用的**透明、可控、可恢复**，而不是模型本身多聪明。

**不是**：
- 不是 Dify / n8n 那种**可视化编排平台**（那是「你画流程，机器执行」；我们是「你给目标，Agent 自己规划」）
- 不是 ChatGPT / Claude 网页版那种**纯对话窗**（它们没有工具过程可视与高危审批闸）
- 不是 Cline / Roo Code 那种**IDE 插件**（它们绑编辑器、绑项目配置；我们零安装、开浏览器即用）
- 不是**云端多租户 SaaS**（本地跑，单用户，SQLite 文件即全部数据）

### 1.4 产品命名

内部代号沿用 `CodeLens` 不改，避免仓库内大量路径、构建产物与文档引用同步改名的成本（见 OD-01）。对外定位语从「编程 Agent」改为「通用 Agent 工作台」。是否需要更换对外品牌名，登记为 OPEN 决策，由「首次对外公开演示前」触发复现。

## 2. 问题陈述

### 2.1 谁在什么场景下遇到了什么痛点

**场景**：一个后端工程师排查线上问题。当前流程是：开终端 `curl` 调接口 → 把返回贴进编辑器 → 肉眼找字段 → 再开一个窗口算聚合 → 把结论手动写进工单。

**现在怎么解决的**：
- 通用 LLM 聊天窗：能问「这段 JSON 是什么意思」，但它**摸不到你的接口、读不到你的文件、算不了你的数据**。你只能把响应手动贴进去，贴的时候还得自己脱敏。
- 终端 + 手工脚本：能干，但每一步都要人复制粘贴，一次排查要开 4 个窗口。
- Cline / Roo Code / Claude Code：能干且干得好，但**绑 VS Code / 绑终端 / 绑项目配置**；换个环境（同事机器、临时服务器、只有浏览器的那台笔记本）就要重配一遍。Roo Code 的 modes 配置、文件白名单、auto-approve 策略有明确学习成本。

**为什么不行**：
1. **能力割裂**：会思考的和会动手的分成两套工具，人成了中间的搬运工（这就是 MCP 生态在解决的问题，但 MCP 又要求用户先装 server）。
2. **过程黑盒**：所有能干活的 Agent 工具里，能同时满足「全程可见 + 可中途干预 + 失败可恢复 + 成本可预估」的极少。Cline/Roo 的审批体验是**逐步弹窗**（一次操作一次确认），任务一多就被用户无脑点穿——这正是「所有操作确认权重相同」的反模式。
3. **状态易失**：换浏览器、换机器、清缓存，任务现场就没了。长任务被上下文撑爆后，前面的决策与待办一起消失。

### 2.2 我们要解决的三件事

1. **让 Agent 能动手，且动手范围本地可控**——HTTP 打任意外部 API、文件读写锁在沙箱目录、计算与系统能力开箱即用、MCP 作为可选连接器接入你已有的生态。
2. **让过程透明且人始终握有方向盘**——工具调用逐条可视化（名称/参数/状态/耗时/结果），高危操作按**三档强度**分级确认，随时可打断、可单步重试、可从任意一步重跑。
3. **让状态不丢**——服务端 SQLite 持久化，跨浏览器用恢复码找回；上下文快满时自动压缩，但**决策、文件清单、验证命令、待办永不丢**。

## 3. 目标用户画像与核心 Agent 任务场景

三个 persona 延续 v1.0 的用户基因（小林 / 阿豪 / 老周），但从「问代码的人」升级为「交代任务的人」。

### Persona 1：小林 — 自学转行者 / 在校生（入门用户，量最大）

- **背景**：22 岁，计算机专业大四或自学转行中，Python / JavaScript 为主，用 DeepSeek 或 Kimi 的低价 API，预算敏感。
- **痛点**：
  - 问「弱智问题」有心理压力，希望有个随时待命、不评判的助手。
  - 学一门新技术的路径是：官方文档 → 博客 → Stack Overflow → 试错，每一步都要手动来回切，**信息永远攒不齐**。
  - 装不动 Dify（6 个容器）、搞不定 n8n（节点表达式）、不敢装 IDE 插件（怕污染环境）。
- **诉求**：打开网页就能用（免注册、免安装）；能一句话交代「把这份 API 文档里的所有接口按方法分类列成表格」；**看得见它每一步在干什么**，否则不敢放手让它跑。
- **核心 Agent 任务场景**：
  - 「把这个网页的接口列表抓下来，按 GET/POST 分组，输出成表格」
  - 「读这个 CSV，算每列的均值和标准差，把异常行标出来」
  - 「我现在这段代码报这个错，去查一下这个库的官方文档怎么说的」

### Persona 2：阿豪 — 3 年后端工程师（核心用户，工具调用深度最高）

- **背景**：28 岁，Java / Go 后端，公司用 DeepSeek/GLM 私有部署，接口在内网、有鉴权，代码不能贴到外部账号体系。
- **痛点**：
  - 排查一个跨 3 个服务的链路，要在终端、日志文件、IDE 之间来回切，**每次切上下文都要重建 mental model**。
  - 通用聊天窗不知道他的内网接口长什么样，只能他口述；口述出来的参数名经常和真实接口对不上。
  - GitHub Copilot 订阅制（$10-39/月）且 2025 年底以来补全质量波动；Cursor 2025-06 定价风波后不再信任订阅制工具的额度透明度。
  - 公司代码不能贴到强账号体系的第三方工具里，合规上过不去。
- **诉求**：**一个能同时调内网 HTTP 接口、读本地日志文件、算聚合的 Agent**；每一步能看到真实请求与响应（他自己要贴进工单）；高危的写操作必须先问过他；自己的 Key 自己充钱，成本可见可控。
- **核心 Agent 任务场景**：
  - 「调 order-service 的 /orders?status=paid，拉最近 100 条，算每单平均金额，失败的单独列出来」
  - 「读 logs/app-2026-10-20.log，统计每个 error 级别的出现次数和首次出现时间」
  - 「把这 3 个接口的响应字段对齐，输出差异表」

### Persona 3：老周 — 独立全栈开发者 / 小团队负责人（生态用户，MCP 主要受益方）

- **背景**：35 岁，一个人干全栈，本机已经跑着一套自己的 MCP Server 生态（自建的数据库查询 server、内部接口 server），平时用 Continue / Roo Code 这类 BYOK 插件。
- **痛点**：
  - 订阅费叠加（Copilot $10 + Cursor $20 + Claude $20）肉疼；IDE 插件越装越重，换台机器重配一遍。
  - Roo Code / Cline 绑定 VS Code，配置 modes 有学习成本；**但他自己的 MCP Server 只能在这些 IDE 插件里用**。
  - 自己的内部 MCP server 只能接一个前端，团队其他人用不上。
- **诉求**：一个网页版 Agent 工作台，**能接上他已有的 MCP Server**（本机 stdio 方式，不改他现有 server），同时保留 BYOK 成本透明与零安装；**数据不出本机**（他给客户做私有化部署，模型走可配置的内网端点）。
- **核心 Agent 任务场景**：
  - 「查一下库里上周退款单的金额分布」（走他自己的 database MCP server）
  - 「把我们内部 API 的三个版本变更列出来」（走自建 HTTP MCP server）
  - 「把这次的结论整理成一份给客户看的说明文档，写到工作区里」（走文件工具 + 通用 LLM）

## 4. 核心用户旅程

```
【首次打开】无需注册
  → 空状态直接展示真实能力（不是营销文案）：
     「4 类工具待命中：HTTP 请求 / 文件读写 / 计算与系统 / MCP 连接器」
     + 三个可一键填入的真实示例任务（附完整输入文本，用户可改）
     + 「配置模型 Key」入口（引导页内联，不跳页）
  → 配置 BYOK：选择供应商预设（DeepSeek / 智谱 GLM / Moonshot Kimi / 通义 Qwen / 自定义 OpenAI 兼容端点）
     → 粘贴 Key → 选模型 → 「测试连通性」（同时探测该模型是否支持原生 function calling）
  → Key 仅存入本浏览器，界面明示「Key 与会话内容不会上传到任何第三方服务」

【核心循环】每次任务
  → 输入自然语言目标（或粘贴一段 JSON/日志/报错栈作为上下文）
  → Agent 第一轮输出一句话预告：「我打算做三件事：调 X 接口取数据 → 用计算工具算聚合 → 把结果写成 CSV」
  → 逐条流式渲染工具调用卡片（图标 + 工具名 + 状态 + 耗时 + 参数摘要 + 结果摘要）
  → 若命中高危操作（写文件 / 发非 GET 的外部请求 / MCP 写操作）→ 暂停并弹出对应档位的确认
  → 用户可：批准 / 拒绝并要求换路径 / 打断 / 改参数后重试该步
  → 循环直至 Agent 给出最终答案（答案区与工具调用区分离，答案可复制）
  → 追问（保留全部上下文与工具结果，不重新解释背景）

【任务复盘】
  → 左侧会话列表（服务端 SQLite，含工具调用次数、耗时、Token 估算）
  → 点开任意历史会话 → 完整重放工具调用时间线（可折叠/展开全部/只看失败）
  → 导出执行记录为 Markdown（含每步参数与结果，供贴进工单或 issue）

【跨浏览器找回】
  → 创建会话时给出「恢复码」（8 位字符）
  → 换浏览器 → 「用恢复码恢复会话」→ 输入码 → 会话与全部工具调用历史回来
  → 或：同浏览器自动关联（localStorage 存设备令牌，服务端只存其哈希）
```

**高危工具确认分支（展开）**

```
Agent 请求：写入文件 workspace/report.csv（12 KB，已有同名文件将被覆盖）
  → 服务端挂起本次执行，生成签名令牌（绑定 sessionId + toolCallId + 工具名 + 参数摘要 + 5 分钟过期）
  → 工具卡片就地展开 inline 确认条（不弹窗、不打断对话流）：完整展示目标路径、被影响行数、参数全文
  → 三选一：
      ① 允许一次 → 回传 sessionId + 令牌 + 决定 → 服务端校验令牌 → 执行 → 落审计
      ② 本次会话始终允许该工具 → 执行 + 会话级免审批记忆（会话列表显示「已记住 N 条授权」，可撤销）
      ③ 拒绝（可附原因）→ 拒绝原因回喂模型 → 模型换路径（模型不得对同一参数再重试）
  → 若用户在展开的参数区编辑了参数 → 生成新令牌 → 重新走一次确认（新参数 = 新风险判定）
  → 服务端从头到尾持有「待执行工具调用」，客户端只回传「决定 + 令牌」，绝不接受客户端重建的工具调用内容
  → 5 分钟无响应 → 自动按拒绝处理，卡片置「已拒绝」，原因写「5 分钟内未响应，按拒绝处理」
```

## 5. 四类工具的能力边界与安全分级

### 5.1 工具总表

| 类别 | 工具 | 能力 | 安全档位 | MVP |
|------|------|------|---------|-----|
| **HTTP 请求** | `http.request` | 任意外部 API：自定义 method / headers / body / query；JSON 与纯文本响应；超时与重试策略 | GET/HEAD = 低（自动执行）；POST/PUT/PATCH/DELETE = 高（硬确认） | P0 |
| **文件读写** | `fs.read` | 读沙箱目录内文件（支持行范围、关键字搜索、glob 匹配） | 低（沙箱内只读） | P0 |
| | `fs.write` | 新建/覆盖/追加/重命名/删除沙箱目录内文件 | 追加/新建 = 中（软确认：可撤销横幅 30 秒）；覆盖已有文件 / 删除 = 高（硬确认） | P0 |
| | `fs.list` | 列目录、查文件大小与修改时间 | 低 | P0 |
| **计算与系统** | `calc.evaluate` | 表达式求值（四则/幂/三角/进制转换），受限语法沙箱 | 低 | P0 |
| | `time.now` | 当前时间、时区换算、日期加减 | 低 | P0 |
| | `uuid.generate` | 生成 UUID v4 | 低 | P0 |
| | `json.format` | JSON 美化 / 压缩 / 校验 / 路径提取（JSON Pointer） | 低 | P0 |
| | `text.diff` | 两段文本差异比对 | 低 | P0 |
| **MCP 生态** | 规范名 `mcp.<serverId>.<tool>`（如 `mcp.filesystem.read_file`）<br>卡片显示 `serverName · toolName` | 连接用户本机已装的 MCP Server，复用其工具 | 继承该 MCP server 自身语义，**默认按「高」起评**；用户可在连接器页逐个下调风险等级 | **P1（可选连接器）** |

> **命名与展示约定（与设计文档一致）**：工具标识符统一采用 `命名空间.工具名` 的点号形式（`http.request` / `fs.read` / `calc.evaluate`），在界面上以等宽字体显示为**代码标识符**而非自然语言标签。点号命名与 MCP 生态的 `serverName.toolName` 约定同构，内置工具与 MCP 工具因此在同一坐标系里可读、可排序、可去重；面向人的自然语言名称作为**辅助文案**出现在说明位置（设置页、审批条、示例任务中）。MCP 工具在界面上采用 `serverName · toolName` 两段式（中间分隔符），以便溯源「哪个 server 提供的哪个工具」；本产品只连本机 stdio server，工具数量可能远超内置，因此溯源是硬要求。

> **【P0 实现约束 · 双轨命名制】上表的点号是「规范名」（canonical），仅用于内部标识、落库、卡片展示与审计检索；下发给 LLM 的 `tools[].function.name` 必须使用「线上名」（wire，下划线形式）。**
>
> 原因：所有 OpenAI 兼容 provider 强制校验 `tools[].function.name` 匹配 `^[a-zA-Z0-9_-]{1,64}$`，**点号不在允许字符集内**。违规时不是跳过单个工具，而是**整次请求被拒（HTTP 400）**，错误形如 `Invalid 'tools.function.name': string does not match pattern`。已有生产事故：某 Agent 框架因 MCP 工具名带点号（`aippt.doc_beautify`）在 DeepSeek 上 100% 失败；某插件因工具名 `demo.time` 上线即 400。根因是 MCP 规范允许点号、而 OpenAI 兼容协议层不允许——**协议转换层必须做名字消毒**。
>
> | 轨道 | 形式 | 用途 | 出现位置 |
> |------|------|------|---------|
> | 规范名 canonical | 点号 `http.request` | 内部标识、落库 `tool_calls.tool_name`、卡片展示、审计检索、用户复制 | 卡片标识符列、设置页、数据库 |
> | 线上名 wire | 下划线 `http_request` | **仅**下发给 LLM | 上游请求体 `tools[].function.name` |
>
> 消毒规则（纯函数，必须有单测）：点号与非法字符 → `_`；连续下划线压缩；去首尾下划线；不以字母开头则前置 `t_`；截断至 64 字符；冲突追加 `_2` / `_3`（**规范名保持不变**）。内置工具消毒示例：`http.request` → `http_request`；MCP 工具消毒示例：`mcp.filesystem.read_file` → `mcp_filesystem_read_file`。注册期校验规范名匹配 `/^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$/`，不匹配直接抛错（**加载期拒绝，而非上线后才炸**）。回程用 `wireName → canonical` 反查表还原；反查失败 → `errorCode=TOOL_NOT_FOUND`。
>
> **实现者注意**：直接拿本表的名字下发 LLM 会全线 400。消毒与反查必须是**同一个纯函数的两处调用**（不得两处实现漂移）。详见架构文档 §6.1.1。

### 5.2 工具注册契约（新增工具只需注册一条定义）

这是「易于扩展新工具」的落地形式，也是**权限感知 Function Calling** 的落点：不在白名单内的工具，**模型根本不知道它存在**（而不是知道了但被拒）。

```typescript
interface ToolDefinition {
  name: string;                    // 规范名（canonical），点号命名空间，如 "http.request"
  wireName: string;                // 线上名（wire），下发给 LLM 用，下划线形式，如 "http_request"（见上方 P0 双轨约束）
  displayName: string;             // 面向人的自然语言名称，如 "HTTP 请求"（设置页 / 审批条 / 示例任务用）
  category: 'http' | 'file' | 'compute' | 'mcp';
  description: string;             // 给模型看，必须写清「什么时候用我」
  inputSchema: JSONSchema;        // 参数校验用（zod schema 双向映射）
  risk: 'low' | 'medium' | 'high';            // 基线风险等级
  approvalMode: 'none' | 'soft' | 'hard' | 'two_step';  // 基线确认档位
  enabled: (ctx) => boolean;       // 例如 MCP 工具：仅当该 server 已连接才为 true
  handler: (args, ctx) => Promise<ToolResult>;
}
```

> `risk`（风险等级：低/中/高）与 `approvalMode`（确认档位：无/软/硬/两步）是**两个独立维度**：风险描述操作的潜在影响面，确认档位描述交互强度。映射规则：`low → none`、`medium → soft`、`high → hard`；`two_step` 仅在用户或规则显式升级时使用（如「删除整个工作区目录」）。MCP 工具默认 `high`，但**用户可在连接器页逐个下调**——这是 MCP 默认高风险带来的必要补偿。
>
> **两者都是「基线值」，实际值在运行期按参数判定**（同一个 `fs.write`，新建文件是 medium，覆盖已有文件是 high）。**风险判定归服务端**，实际 `risk` 与 `approvalMode` 随 `tool_call` 事件下发给前端——前端不得成为安全判定的第二来源。判定表见架构文档 §6.3。

**扩展契约承诺**：新增一个工具 = 新增一个 `ToolDefinition` 对象 + 一行注册调用。**不改动** Agent 循环、不改动前端可视化、不改动 OpenAPI 主契约（仅新增工具描述端点）。此承诺需由架构师在 Phase 2 落地为「工具清单契约测试」：新增工具未注册则测试红。

### 5.3 安全边界（详见 §16 风险表）

- **HTTP 工具**：仅 https；拒绝 URL 内嵌凭据；拒绝内网/环回/链路本地/云元数据地址（169.254.169.254、metadata.google.internal 等）；**DNS 解析后逐一校验解析地址为公网**（防 DNS rebinding）；手动跟随重定向且**每跳重新校验**；响应体大小上限与超时。
- **文件工具**：先 `realpath` 解析符号链接再判断是否落在沙箱根内（**先解析后比较**，顺序不可颠倒）；拒绝绝对路径、拒绝含 `\0` 的路径、拒绝 `..` 逃逸；沙箱根默认 `<项目目录>/workspace`，可配置。
- **MCP 工具**：MCP server 以**用户本机子进程**运行，权限等于用户权限——因此（a）默认不启用，（b）启用即在设置页明示「该 server 以你的用户权限运行，工具调用会被记录」，（c）只允许 stdio 本地进程，不接受远程 URL（避免把任意远端变成工具源）。

## 6. Agent 体验的关键交互点清单

### 6.1 工具调用可视化：每张卡片必须展示什么

| 字段 | 是否必显 | 展示规则 |
|------|---------|---------|
| 类别图标 | 是 | 文字定义图标语义（HTTP = 地球图标、文件 = 文档图标、计算 = 计算器图标、MCP = 插头图标），由统一 SVG 图标库提供（沿用既有交付物锁定的图标库，不引入第二套）；同一工具恒定同一图标 |
| 工具标识符 | 是 | 点号命名标识符（`http.request`），等宽字体显示（它是代码标识符不是自然语言） |
| 来源徽标 | 是 | 内置工具标「内置」；MCP 工具标 `serverName · toolName` 两段式，可溯源 |
| 风险徽标 | 是 | 三级：低 / 中 / 高。**卡片上低风险不显示徽标**（用稀缺性保住「高危值此一眼」的信号价值），设置页显示全部三级 |
| 状态 | 是 | **六态 + 一个历史注脚值**：待确认 / 执行中 / 成功 / 失败 / 已拒绝 / 超时，外加第七值 `skipped`（**不是终态错误**，用于 §6.3「从某步重跑」时标记被截断的步骤，UI 按历史注脚弱化呈现：整卡弱化 + 斜杠图标，**仍可展开查看，且不计入失败数**）。状态永远是「图标 + 文字」双通道，不靠颜色单独传达。**超时与失败必须视觉区分**（超时 = 可能是暂时的，重试是合理的第一步；失败 = 确定的错误，需要换策略）；**已拒绝不是错误**，用中性色不染红；枚举以架构 §8.1 锁定的 `tool_result.status` 七值为准 |
| 耗时 | 是 | `<1s` 用毫秒、`≥1s` 用秒保留一位、`>60s` 显示分秒 |
| 参数 | 展开显示 | 格式化 JSON + 语法高亮；密钥类字段（匹配 `apiKey|token|secret|password|authorization|cookie`）默认脱敏为掩码，可手动展开显示原值 |
| 结果摘要 | 是（折叠态一行） | 成功：一句摘要（HTTP → 状态码 + 字节数；文件 → 行数 / 字节；计算 → 数值；MCP → server/tool 名） |
| 完整结果 | 展开显示 | 超过 2KB 折叠；提供「复制」「下载为文件」；文本结果保留原始换行不智能折行；JSON 与参数区复用同一渲染器 |
| 错误信息 | 失败/超时时必显 | 分类标签（限流 / 超时 / 参数非法 / 权限拒绝 / 目标不存在 / 内部错误）+ 原始错误消息 + 一句「下一步建议」+ 重试入口 |
| 所属轮次 | 是 | 第 N 轮任务；同轮多次调用分组显示 |

### 6.2 折叠策略与时间线节奏

- **默认折叠**：成功卡片只显示一行摘要（图标 + 标签 + 状态 + 耗时 + 摘要）。这是「工具日志不吵」的底线——一个跑 20 步的任务，不能刷屏。
- **失败默认展开**：错误是模态体验，不是罕见事件（引自 agent UI 设计模式研究）。用户第一眼就要看到错在哪。
- **执行中展开参数**：让用户在等待期间能预判它要干什么，而不是执行完才发现参数不对。
- **连续调用合并**：同一轮内 ≥3 次连续调用折叠为「批量 N 次调用」，展开后是子列表。
- **相对时间戳**：每条卡片带相对时间（如「+1.2s」），组间显示间隔，让人能看出哪一步慢。
- **滚动策略**：自动跟随最新输出；用户手动向上滚动即暂停跟随并标记「已暂停自动跟随」，不强行拽回。

### 6.3 人可以做什么（干预能力矩阵）

| 干预动作 | 何时可用 | 行为定义 | 状态保全承诺 |
|---------|---------|---------|------------|
| **打断（全局停止）** | Agent 运行中任意时刻（流式输出中、工具执行中、等待确认中） | 立即停止当前循环；保留已完成的全部工具调用与结果；给出一句「已停止，当前进展如下」 | 不丢已完成步骤 |
| **拒绝并换路** | inline 确认条 | 拒绝原因作为一条 observation 回喂模型；明确告知「不要以相同参数重试」，模型不得对同一 (工具, 参数) 再次发起调用 | 拒绝记录进审计 |
| **改参数重试** | inline 确认条（展开参数区） | 用户编辑参数 → 生成新令牌 → 重新确认 → 执行；新参数按新风险重新判定 | 原参数保留在历史 |
| **单步重试** | 任意已完成的工具调用 | 以原参数重跑该调用，结果追加为新一条（不覆盖原记录） | 前后两次结果都在 |
| **从某步重跑** | 任意工具调用 | 截断该步之后的所有步骤，以该步为起点继续；被截断的步骤标记为「已跳过」而非删除 | 被截断步骤仍可展开查看 |
| **补充约束** | 任意时刻 | 输入一句话追加到当前任务上下文，Agent 继续 | 追加内容进入压缩时的「用户原话」锚点 |
| **查看原始结果** | 任意时刻 | 展开完整结果 / 复制 / 下载 | 完整结果落盘保存，不受前端折叠影响 |
| **只重放不执行** | 历史会话 | 打开历史会话只查看，不触发新执行 | 历史只读 |

### 6.4 高危操作的三档确认强度

引自 agent UI 设计模式研究的核心结论：**不能所有操作都弹窗（用户会无脑点穿），也不能都不弹（不可逆损害无人把关）**。

| 档位 | 触发条件 | 交互形态 | 例子 |
|------|---------|---------|------|
| **软确认** | 可逆写入 | 执行后 30 秒撤销横幅（不打断流程） | 追加写入新文件、`fs.write` 创建新文件 |
| **硬确认** | 破坏性 / 对外写 | **就地 inline 确认条**（不弹窗、不打断对话流）：完整展示目标 + 完整参数 + 影响范围，提供「允许一次 / 本次会话始终允许 / 拒绝（可附原因）」 | 覆盖已有文件、删除文件、非 GET 的外部 HTTP 请求、MCP 写操作 |
| **两步确认** | 灾难性 / 不可逆对外 | inline 确认条 + 必须勾选「我已审阅参数并接受风险」（或键入确认短语）才启用「允许」 | 向外部服务提交无法撤销的操作、删除整个工作区目录 |

**形态选择依据**：确认闸必须**长在对话流里**（inline），而不是弹一个把上下文打断的模态窗——模态窗会把用户从「正在读的推理」里拽出来，用户在脱离上下文的状态下做安全决策正是「无脑点穿」的成因。inline 确认条让用户在**看到工具意图与参数的同一屏**做决定。

**焦点与超时纪律**：
- 确认条出现时**不抢焦点**（不能把用户正在读的正文抢走），改为输入框上方出现「N 个操作待确认」提示 + 浮动提示，键盘用户 Tab 可达。
- 审批等待超过 **5 分钟**无响应 → 自动按「拒绝」处理，卡片置「已拒绝」，原因写「5 分钟内未响应，按拒绝处理」——避免 Agent 无限挂起锁死整条会话。
- 审批粒度按「工具 + 风险等级」而非「单次调用」；一次「允许一次」不覆盖后续同类调用，除非用户显式选「本次会话始终允许」（会话级记忆存服务端，会话列表显示「已记住 N 条授权」）。

**服务端持有原则（安全硬要求）**：待确认的工具调用由**服务端**保存并签发令牌（绑定 sessionId + toolCallId + 工具名 + 参数摘要 + 5 分钟过期）。客户端回传的只有「令牌 + 决定」。**服务端绝不接受客户端提交的工具调用内容**——这是当前大量 human-in-the-loop 实现被公开指出的可利用漏洞（服务端用客户端传来的 messages 重建待执行调用，XSS 或提示注入即可让用户批准的与实际执行的不一致）。

**回执通道（跨文档裁决 C-4）**：审批决定走**独立端点** `POST /api/v1/approvals/:id`，body 只含 `{ token, decision, reason? }`；**待执行调用的参数一律从服务端 `approvals` 表取**。决定提交后，服务端在**原 SSE 流**上推送 `tool_result`（`status: 'rejected'` 或继续执行的结果），前端据此更新卡片。

> 为什么不走 SSE 同流：审批可能跨越数分钟的用户思考时长，SSE 长连接不适合承载「等一个人做决定」；独立端点让审批具备可重试、可审计、可跨连接恢复的性质。代价是前端多一个 HTTP 调用，收益是审批链路与服务端状态机解耦。

**拒绝后回喂规则**：拒绝原因作为一条 observation 回喂模型，且明确告知「不要以相同参数重试」——模型必须换方案，否则会反复撞同一堵墙消耗预算。

### 6.5 首屏与空状态（不出现空洞占位文案）

- 空状态标题使用真实能力描述：「4 类工具待命中」，副标题说明每类能做什么。
- 三个真实示例任务（可一键填入、可编辑）：
  1. 「抓 https://example.com/api/docs 里的接口列表，按方法分类成表格」
  2. 「读 workspace/data.csv，算每列均值与标准差，把偏离超过 2σ 的行单独列出」
  3. 「用计算工具算 (1234.5 * 87) / 13，并给出保留两位小数的结果」
- 空状态**不出现**「Welcome」「Lorem ipsum」「Sign up today」等占位文本。

### 6.6 五个必备状态覆盖

| 状态 | 设计 |
|------|------|
| Loading | 骨架屏 + 当前阶段文字（「正在调用 HTTP 请求…」）+ 停止按钮 + 预计剩余时间（基于已用轮次与历史均值） |
| Empty | 见 §6.5，真实能力 + 可点击示例 |
| Error | 错误分类（模型 / 网络 / 权限 / 工具 / 参数）+ 明确原因 + 可操作按钮（重试 / 换模型 / 打开设置）+ 降级提示 |
| Populated | 结果高亮 + 一键复制 + 继续追问入口 + 工具调用时间线折叠在下方 |
| Edge | 超长输出截断并标注「已截断，完整结果已保存到 workspace/…（可下载）」+ 成本上限提醒 + 内容安全过滤提示 |

| `sessions` | id, title, created_at, updated_at, device_token_hash, recovery_code, provider, model, summary | 会话主记录 + 恢复码 + 压缩摘要 |
| `messages` | id, session_id, seq, role, content, tokens, is_summary, created_at | 对话消息（含被压缩后的摘要消息） |
| `tool_calls` | id, session_id, message_id, tool_name, args_json, status, risk, started_at, ended_at, duration_ms, error_kind, error_msg, result_ref | 每次工具调用的完整记录（参数与结果是审计与复盘的一等公民） |
| `tool_results` | id, tool_call_id, inline_preview, artifact_path, bytes, truncated | 结果内联摘要 + 大结果落盘路径（`artifact_path` 直接指向落盘文件，**不依赖 `artifacts` 表**） |
| `artifacts` | id, path, bytes, sha256, created_at, source_tool_call_id | 落盘的大结果与产出物—— **本期不建表**：改由 `tool_results.artifact_path` 指向落盘文件即可满足「结果落盘 + 只留指针」的需求 |
| `approvals` | id, tool_call_id, challenge_token_hash, decision, decided_at, approver | 人工确认审计（决定与参数绑定，不可篡改） |
| `provider_capabilities` | provider, model, supports_function_calling, probed_at, notes | function calling 能力探测结果（避免每轮试探） |
| `local_events` | id, session_id, event, props_json, created_at | 本地埋点（见 §14.4）—— **本期不建表**：沿用 CodeLens 既有「前端本地事件日志」实现，埋点数据不出浏览器，不强制落服务端 |

**跨浏览器恢复的两条路径**（免登录 + 服务端持久化的必然解）：

1. **同浏览器自动关联**：创建会话时生成随机设备令牌存 localStorage，服务端只存其 SHA-256。同一浏览器打开即自动列出该设备的会话。
2. **跨浏览器 / 跨设备**：创建会话时生成 8 位恢复码（服务端只存哈希），用户复制到另一浏览器输入即可恢复会话与全部工具调用历史。恢复码可手动重新生成（旧码立即失效）。

**数据可携与可清除**：设置页提供「导出全部会话为 Markdown」「导出数据库文件」「彻底清除（含数据库文件与工作区）」三键。

### 7.2 上下文压缩：三层策略 + 保真原则

**问题**：长任务里工具结果会迅速吃掉上下文。业界实测（Claude Code 上下文窗口文档、agent 上下文工程资料）表明，一个跑 50 次文件读取的会话轻松破 100K token；而**粗暴截断最旧的 token** 会丢 live constraint（Agent 忘了「不要改数据库层」这类硬约束，两轮后直接违反）。

**三层压缩**（借鉴 Claude Code 已公开的三层结构 + 上下文工程规范，做适合本产品的裁剪）：

| 层 | 机制 | 触发 | 成本 |
|----|------|------|------|
| L1 工具结果瘦身 | 单条工具结果 > 8K token 时：正文落盘（`artifacts`），上下文内只留「摘要 + 路径 + 前 500 字符 + sha256」 | 每次写入结果时 | 0 |
| L2 消息摘要压缩 | 估算占用 > 模型窗口的 75% 时，对历史做结构化摘要 | 每次 LLM 调用前估算 | 1 次小模型调用 |
| L3 近期原文保留 | 摘要之外**始终保留最近 6 轮原文**，不是「摘要完就没了」 | 随 L2 | 0 |

**L2 摘要的九段结构**（照抄已被验证有效的分段式摘要 prompt 骨架，不做自由发挥）：

1. 原始请求与意图
2. 关键技术概念
3. 涉及的文件与代码段（保留路径与关键片段）
4. 遇到的错误与对应修复
5. 问题解决过程与**已做出的决策及其理由**
6. 用户原话（逐字保留，不改写）
7. 待办事项
8. 当前工作（精确到「刚做完什么、正在做什么」）
9. 可选的下一步（附对话原文引用）

**保真原则（压实是摘要不是清空）**——以下内容**永不丢弃**，压缩与摘要都必须保留：

- 原始用户诉求（第一轮 user message 原文）
- 已做出的关键决策及其理由
- 已修改 / 已创建的文件清单
- 验证命令与验证结果
- 未决问题与已知坑
- 当前计划与下一步

**锚点清单保活**：系统提示、当前任务目标、上述保真清单，在每次 LLM 请求中作为固定前缀重新注入（不参与压缩淘汰），对应知识库「恰当高度指令」原则——给目标 + 约束 + 验收 + 工具，把「怎么做」留给执行。

**摘要用小模型**：摘要调用可配一个便宜模型（默认取同供应商的轻量型号），成本可控；若摘要失败 → 不压缩，直接报「上下文已满，请新建会话或缩短任务」，**不静默截断**（对应「污染即清并回退」纪律）。

**压缩后自检**：压缩完成后，检查保真清单是否齐全（机械可验），缺项则用原文补齐。缺项即视为压缩失败，回退并提示用户。

### 7.3 上下文预算与成本护栏

- 每轮请求前估算 token（估算器按 provider 分词口径近似，误差提示为「估算」）。
- 顶部常驻上下文占用条（已用 / 窗口上限），超过 75% 变琥珀色，超过 88% 变警示色并提示「即将触发压缩」。
- 单任务 Token 花费估算随最终答案展示（v1.0 原 P1 项，因 Agent 场景成本敏感度高，**提升进 MVP**）。

## 8. 错误重试、降级与熔断

### 8.1 错误分类（先分类，再决定是否重试）

「全局重试计数」是最常见的错误做法。行业实测：ReAct 式 Agent 的重试预算有约 90% 花在**永远不可能成功**的错误上——最典型的是模型幻觉出一个不存在的工具名，用指数退避去重试一个字典里根本没有的 key，指数退避救不了它。

因此：**工具名与参数先在代码侧做确定性校验，不交给模型重试**。

| 错误类型 | 判定 | 处理 | 是否重试 |
|---------|------|------|---------|
| 参数非法 / 不符合 schema | zod 校验失败 | 立刻把**具体字段级错误**回喂模型（「参数 url 缺失；参数 method 需为 GET/POST/...」），不消耗重试预算 | 否（换参数重来算新调用） |
| 工具不存在（幻觉） | 名称不在注册表 | 立刻回喂「该工具不存在，你当前可用的工具是：…」，模型必须改选 | 否 |
| 权限 / 路径越界 / SSRF 拦截 | 安全网关拒绝 | 明确告诉模型「该操作被安全策略拒绝，原因是 X」，**不给绕行建议**；同一被拒目标在本次任务内不再重试 | 否（并对同目标做任务内封禁） |
| 目标不存在（文件/接口 404） | 资源层返回 | 回喂模型，让它换路径 | 否 |
| 限流 429 | 上游返回 | 指数退避 + 抖动（jitter）重试，最多 2 次 | 是 |
| 上游 5xx / 临时不可用 | 上游返回 | 指数退避重试，最多 2 次 | 是 |
| 网络超时 | 连接层 | 同上；HTTP 工具重试仅对幂等方法（GET/HEAD）自动进行，非幂等不自动重试（需重新确认） | 是（幂等才自动） |
| 工具执行超时 | 工具自身超时 | 回喂模型「工具超时」，允许它换参数或换工具 | 由模型决定 |
| 熔断打开 | 该工具已熔断 | 直接返回「该工具暂时不可用（连续失败 N 次）」，**不触发 LLM 调用** | 否 |

### 8.2 熔断与循环检测

- **每工具熔断器**：同一工具在本次任务内连续失败 3 次 → 打开熔断，后续调用直接快速失败，提示模型换路。熔断状态在会话内可见（工具卡片上标「已熔断」）。
- **循环检测**：以 `(工具名, 参数归一化哈希)` 为键。
  - 同一键连续出现 2 次 → 向模型注入一条 observation：「你正在重复同一个调用，请换参数或换工具」。
  - 同一键连续出现 3 次 → 判定死循环，**中止本次任务**，保留已完成结果，给出「检测到重复调用，已停止」的明确说明与「从该步重跑 / 换路径 / 换工具」三个恢复入口。
- **最大轮次**：单任务默认最多 12 轮 LLM 调用（可配置 5–30）。达到上限 → 中止并输出「已达最大轮次，当前进展与未完成项如下」，不静默截断。
- **任务级重试预算**：单任务内所有工具重试合计上限 5 次，超出后不再自动重试，只允许用户手动触发。

### 8.3 降级链

```
① 模型原生 function calling（首选）
   └ 不支持 / 探测未通过 → ② ReAct 提示词解析降级
                          └ 仍不可用 → ③ 纯对话模式（明确告知「本次无法调用工具」）
```

- **能力探测**：切换模型或首次使用该模型时，发一次最小探测请求（定义一个只有一个参数的假工具，要求模型调用它），记录 `supports_function_calling` 到 `provider_capabilities` 表。**不在每轮试探**（每次试探都白烧 token 且拖慢首字延迟）。
- **ReAct 降级格式**：采用 XML 风格标签包裹 JSON（`<tool_call>{"name":...,"arguments":{...}}</tool_call>`），与主流 XML 风格 Agent 提示词约定兼容；解析失败按纯文本处理（不硬解、不抛错打断流式输出）。**不用 Markdown 围栏**——围栏易被模型输出里的代码块干扰。
- **ReAct 通道的工具清单用「线上名」**（与原生通道一致，保证模型产出的名字能被反查表还原）；但**提示词中同时给出规范名供人读**：工具清单条目形如 `{"name": "http_request", "displayName": "HTTP 请求"}`——模型看到的是能调用的名字，人读到的是可理解的名称。
- **模型不可用降级**：主供应商 5xx / 限流连续失败 → 自动切到用户配置列表中的下一个供应商（沿用 v1.0 已有的五家 provider 架构：DeepSeek / GLM / Kimi / Qwen / 自定义 OpenAI 兼容端点），并在界面上明示「已切换到 X，原因是 Y」。
- **工具不可用降级**：MCP server 未连接 / 连接失败 → 该工具**不进入本次请求的工具清单**（模型看不到它），并在界面上给出「1 个 MCP server 未连接」提示与修复入口。

### 9.3 竞品结论（四条）

1. **「能干活的 Agent」与「看得清的 Agent」之间存在真实断层**。Dify/n8n 干得动但过程是节点画布；Cline/Roo/Claude Code 看得清但绑环境；ChatGPT 两者都不做。**没有一个产品同时满足：零安装 + 本地可跑 + 过程逐条透明 + 三档风险分级 + 跨浏览器恢复 + 自带四类工具**。这就是我们的位置。
2. **双通道（原生 function calling / 提示词降级）已被独立验证**：Open WebUI 早已提供「Native / Default」双模式并明确说明「Default 模式不要求模型支持 function calling，但链式调用可靠性不如 Native」——本项目的技术选型不需要赌单一模型能力。
3. **MCP 是增量，不是地基**。官方参考 server 中**仅 7 个仍在维护**（Everything / Fetch / Filesystem / Git / Memory / Sequential Thinking / Time），GitHub、PostgreSQL、Puppeteer、Slack、SQLite、Google Drive 等大批 server 已归档（GitHub 官方 server 已被 Brave / Zencoder 等接手、社区 server 官方声明「未经测试，风险自负」）。更关键的是：这三个最常用的官方 server（Filesystem / Fetch / Time）**恰好就是我方内置的文件 / HTTP / 时间工具**。因此 MCP 的正确定位是「接入你已有的私域生态」，做成可选连接器是唯一合理形态。
4. **「无脑点穿」是审批设计的头号反模式**。业界模式研究明确指出：所有操作同权重确认 → 用户不读就点；全不确认 → 不可逆损害无人把关。三档分级（软 / 硬 / 两步）是唯一被验证的解法。

## 10. 市场空白与差异化机会

### **机会 1：Agent 的「过程可见性 + 人始终握方向盘」在通用（非编码）场景仍是空白**

**依据**：
- 现有通用 Agent 平台（Dify / n8n）的过程是**节点画布**，面向「设计者」而非「使用者」；普通用户看到的是「我画了个流程」，不是「它刚才替我做了什么」。
- 编码 Agent（Cline / Roo / Cursor）把过程透明做到了极致，但服务对象是**开发者**，且绑 IDE——非开发者用不上，开发者也常因为「每步一弹窗」而关掉审批。
- agent UI 模式研究的结论：Agent 自主性越高，界面越该像**审阅工具**而不是聊天窗（inbox + 审批队列 + 运行时间线），而这块目前只有 Devin / Claude Code 这类**面向工程师**的产品在做。

**我们的机会**：把「运行时间线 + 分级审批 + 一键从某步重跑」这套工程师级信任机制，做成**面向所有职业用户的通用 Agent 工作台**。具体到界面：普通用户看到的是自然语言步骤（「读取订单接口」），高级用户展开看到原始参数与响应——**双层可读性**。

### **机会 2：Agent 的「上下文工程」在国产模型 + 本地部署场景几乎无人做对**

**依据**：
- Claude Code 公开的三层压缩（工具结果瘦身 / 缓存友好布局 / 九段结构化摘要）建立在一套极其成熟的上下文工程之上；社区总结的通用结论是「压实是摘要不是清空」「压实必须保住决策、改动文件清单、验证命令」。
- 而市面上自托管 Agent 平台的上下文处理普遍停留在「截断最旧的」或「按 session 简单存」，长任务一压缩就丢约束。
- 面向国产模型（DeepSeek / GLM / Kimi / Qwen）的上下文预算适配几乎没有专门方案，而这恰恰是国内自托管用户的主力模型。

**我们的机会**：把**保真清单锚点**（原始诉求 / 决策与理由 / 文件清单 / 验证命令 / 待办）+ **九段结构化摘要** + **大结果落盘只留指针**做成产品能力，并对国产模型的窗口口径做精确适配。落地上用「压缩后机械自检，缺项即回退」把「压缩保真」从提示词工程变成可测的工程断言——这与项目内《强化Agent》宣言里「判据自己要先被判据检验」的要求同构。

### **机会 3：「本地优先 + 自带 Key + 四类通用工具」的组合在中文市场几乎无人占位**

**依据**：
- Coze / 扣子：零代码友好、插件丰富（800+）、多渠道发布，但**不支持私有化部署**，数据必须过字节云；生态绑定明显，脱离字节系（微信 / 淘宝）后能力大幅下降；多节点流程调试报错模糊。
- Dify：可私有部署，但运维重（6 容器 / 100+ 环境变量）；modified Apache 2.0 有转售限制。
- LobeChat / Open WebUI：可自托管，但前者是前端框架需自建后端，后者偏 Ollama 聊天场景。
- 也就是说：**「一条命令本地跑 + 不用注册 + 用国产模型 + 自带 4 类工具 + 能连自己的 MCP + 过程全可视化」这个组合，目前没有产品完整占据**。

**我们的机会**：CodeLens v1.0 已经把「免登录 + BYOK + 零安装 + 国产模型直连」这四项验证过了（43 服务端测试 + 13 前端测试的已上线产品）。v2.0 是在这个已被验证的地基上加「真正能动手」的两件事，**不是从零另起一个赛道**——这是我们相对所有新进入者的最大优势：地基已交付，不确定性低。

### **机会 4（附加）：把 MCP 从「生态负担」变成「一行配置」**

**依据**：MCP 接入的技术成本其实很低（TS SDK：`StdioClientTransport` 拉起子进程 + `listTools()` + `callTool()`，工具 schema 直接就是 function calling 需要的 JSON Schema），但**认知成本极高**：用户得知道什么是 MCP、自己装了什么 server、装在哪、配什么 env。

**我们的机会**：设置页做「MCP 连接器」——**只连本机已有的**，粘贴一段 command/args 即可；连上后自动列出该 server 提供的工具（人话标签 + 分类 + 风险档），用户勾选启用；**未连接的 MCP 能力对模型完全不可见**（不污染工具清单、不增加提示词开销、不制造幻觉）。这是一个把「生态冷启动」彻底外包给既有生态的设计。

### 11.3 「MCP 生态接入」的明确取舍论证（用户点名要，但必须论证其不拖累 MVP）

**结论：MCP 进 Phase 1 交付范围，但分级为 P1，且必须以「可选连接器」形态实现——未连接时该能力对模型完全不可见，对新用户零冷启动负担。**

**支持纳入的理由（不可忽视）**：
1. 用户已明确点名，属拍板约束，不可再讨论。
2. 它是本产品**唯一能接入私域生态**的通道——老周这类用户已经在本机跑着 MCP Server，我们的内置工具永远无法覆盖他的内部系统。MCP 是「接住存量生态」的唯一手段。
3. 技术成本其实不高：TS SDK 的 `StdioClientTransport` + `listTools()` + `callTool()` 即可，工具 schema 直接就是 function calling 需要的 JSON Schema（官方文档明确「listTools() 的每项 name / description / inputSchema 与 function calling 工具定义一一对应」）。

**必须做成「可选连接器」而不是「一等能力」的四条论证**：

| # | 论证 | 依据 |
|---|------|------|
| A1 | **生态碎片化严重**：官方参考 server 中**仅 7 个仍在维护**（Everything / Fetch / Filesystem / Git / Memory / Sequential Thinking / Time）；GitHub、PostgreSQL、Puppeteer、Slack、SQLite、Sentry、Google Drive、Google Maps 等已移入归档仓库；社区 server 官方声明「未经测试，风险自负」。把 MCP 做成开箱即用能力，等于把一个可信度不一的目录塞进用户面前。 | 官方 servers 仓库现状 + 各方评测 |
| A2 | **最常用的三个官方 server 已被我方内置工具覆盖**：Filesystem ≈ `fs.read` / `fs.write`、Fetch ≈ `http.request`、Time ≈ `time.now`。MCP 的**增量价值**只存在于「用户自己已有的私域 server」，而非官方目录。 | 官方 server 清单 vs 我方工具表 |
| A3 | **冷启动负担是真实的**：用户要先理解 MCP 是什么 → 装 Node/uvx → 装 server → 配 command/args/env → 配凭据。任一步断掉，新用户得到的是「一个连不上的功能」，体验上是负资产。 | MCP 官方 quickstart 的配置步骤 |
| A4 | **供应链与权限风险**：MCP server 以**用户本机子进程**运行，权限等于用户权限。默认启用等于默认引入第三方代码执行面。 | MCP 官方文档的 stdio 客户端行为 + 安全指南 |

**具体设计（让 MCP 不拖累 MVP 体验的六条措施）**：

1. **默认关闭 + 能力不可见**：未连接任何 MCP server 时，MCP 工具**不进入工具清单**，模型看不到它们（权限感知 Function Calling：不是「知道但不能用」，而是根本不知道）。因此对纯新手，MVP 体验与「没有 MCP」完全一致，零污染、零额外 token 开销、零幻觉风险。
2. **连接器设置页独立**：设置页 → 「MCP 连接器」→ 只支持**本机 stdio**（command + args + env），不接受远程 URL（避免把任意远端变成工具源）。填完即测连接，实时显示该 server 提供的工具清单（人话标签 + 来源 server + 建议风险档）。
3. **预置三条可复制的官方配置**（Filesystem / Fetch / Time），一键填入命令模板，让「装第一个 MCP」从 30 分钟降到 3 分钟——**且明确标注这三条的能力我方内置工具已覆盖**（引导用户把 MCP 用在私域 server 上，而不是重复装官方三个）。
4. **工具来源可视化隔离**：MCP 工具在卡片上有独立的「插头图标 + server 名 + 来自外部」标记，写操作一律走硬确认档。
5. **连接健康与降级**：server 起不来 / 超时 / 工具清单拉取失败 → 该 server 整体停用（其工具从本次请求清单移除）+ 界面给修复入口；**不让一个坏 server 拖垮整次任务**。
6. **不进 MVP 验收基线**：MCP 相关的验收标准在 P1 阶段单独评审；MVP 的 P0 验收不依赖任何 MCP server 存在。

**RICE 补充说明**：MCP 的 Reach 评 3（首月只有少数已有 MCP 生态的用户）、Confidence 评 50%（生态碎片化使效果不确定），Score = (3 × 3 × 0.5) / 3 = **1.5，是全表最低**。本项目仍将其纳入 Phase 1 交付，**依据是用户显式拍板约束优先于 RICE 排序**；RICE 的作用是据此决定**实现形态必须最轻**（可选、默认关闭、零侵入）与**优先级必须最低**（不占 P0 验收资源）。这是一个「按用户要求交付、但按数据限制其范围」的显式取舍，不是隐性妥协。

## 12. 验收标准（Given / When / Then）

> AC-01 ~ AC-12 为初版；**AC-13** 为 v1.1 回改新增（工具名双轨制），对应架构裁决 C-1。

### AC-01 · BYOK 与能力探测
- **Given** 用户首次打开且尚未配置 Key，**When** 打开设置并粘贴一个有效 Key、选择「DeepSeek」与某模型、点击「测试连通性」，**Then** 系统完成一次真实连通性请求，并明确返回该模型**是否支持原生 function calling**（支持 / 不支持 / 探测失败），结果写入 `provider_capabilities`。
- **Given** 某模型已探测为「不支持 function calling」，**When** 用户发起任务，**Then** Agent 自动走 ReAct 提示词解析通道，界面在工具调用卡片上标注「提示词解析模式」。

### AC-02 · Agent 自主循环
- **Given** 用户输入「读 workspace/data.csv，算每列均值，把结果写成 summary.md」，**When** 发送，**Then** Agent 在**不追加用户指令**的情况下自主发起 ≥3 次工具调用（`fs.read` → `calc.evaluate` → `fs.write`），最终给出结论。
- **Given** 一次任务中工具调用达到 12 轮上限，**When** 触发上限，**Then** 系统中止循环、保留已完成结果、输出「已达最大轮次」与未完成项说明，**不静默截断**。

### AC-03 · 工具调用可视化
- **Given** 一次任务产生 5 次工具调用，**When** 渲染完成，**Then** 每条调用在时间线上展示：类别图标、工具标签、状态、耗时、参数摘要、结果摘要；成功卡片默认折叠、失败卡片默认展开。
- **Given** 某次工具调用返回 3KB JSON，**When** 用户展开结果，**Then** 完整内容可见并可复制；**Given** 结果超过 8K token，**When** 写入，**Then** 正文落盘 `artifacts` 表，卡片只显示摘要 + 路径 + sha256 前 12 位。

### AC-04 · 三档确认
- **Given** Agent 请求写一个新文件（可逆），**When** 用户批准，**Then** 执行后出现 30 秒撤销横幅。
- **Given** Agent 请求覆盖已有文件，**When** inline 确认条出现，**Then** 确认条完整展示目标路径、被影响行数、完整参数，并提供「允许一次 / 本次会话始终允许 / 拒绝」三个动作。
- **Given** inline 确认条已展示，**When** 攻击者（或 XSS）改写前端提交的 `messages` 数组以替换待执行调用，**Then** 服务端**拒绝执行**（因为服务端只认自己签发的令牌与参数摘要，令牌不匹配即 409），并记录一条 `approvals` 异常审计。
- **Given** 审批决定被提交，**When** 客户端调用 `POST /api/v1/approvals/:id`（body 仅含 `{token, decision, reason?}`），**Then** 服务端从 `approvals` 表取出待执行调用的参数并执行或拒绝，随后在原 SSE 流上推送 `tool_result`；**客户端 body 中不存在的任何字段都不参与决策**。

### AC-13 · 工具名双轨制（回改新增）

- **Given** 一个规范名为 `http.request` 的已注册工具，**When** 系统向 provider 下发工具清单，**Then** 请求体中 `tools[].function.name` 的值为 `http_request`（下划线），**不出现点号**；请求返回 HTTP 200。
- **Given** provider 返回 `tool_calls[].function.name = "http_request"`，**When** 系统执行该调用，**Then** 通过反查表还原为规范名 `http.request` 并落库 `tool_calls.tool_name`；**Given** 反查失败，**Then** 返回 `errorCode=TOOL_NOT_FOUND` 且不执行任何工具。
- **Given** 存在两个规范名（`http.request` 与 `http_request`），**When** 注册完成，**Then** 两者线上名分别为 `http_request` 与 `http_request_2`，**规范名均不变**；注册期校验不匹配点号命名空间的规范名时**直接抛错**。
- **Given** ReAct 降级通道，**When** 提示词中的工具清单被构造，**Then** 清单条目的 `name` 为线上名、同时含 `displayName` 供人读。

### AC-05 · 持久化与跨浏览器恢复
- **Given** 一次含 6 次工具调用的会话，**When** 关闭浏览器并在另一浏览器输入 8 位恢复码，**Then** 会话消息与全部 6 条工具调用记录（含参数与结果）完整恢复。
- **Given** 恢复码已被使用过一次，**When** 再次使用，**Then** 拒绝并提示「恢复码无效或已失效」；**Given** 用户手动重新生成恢复码，**Then** 旧码立即失效。

### AC-06 · 上下文压缩
- **Given** 上下文占用达到模型窗口 75%，**When** 触发压缩，**Then** 产出一份包含九段结构的摘要，且**保真清单机械自检通过**（原始诉求 / 决策与理由 / 文件清单 / 验证命令 / 待办 五项齐全）。
- **Given** 压缩后自检发现缺项，**When** 系统处理，**Then** 回退压缩并提示用户「上下文已满，请新建会话或缩短任务」，**不静默截断**。
- **Given** 压缩后继续对话，**When** 模型被问及「我们之前说过不要改数据库层」，**Then** 该约束仍在上下文中（来自保真锚点或摘要），模型不违反该约束。

### AC-07 · 错误重试与熔断
- **Given** 某工具连续失败 3 次，**When** 第四次被调用，**Then** 直接返回「该工具暂时不可用」而**不触发 LLM 调用**，且卡片标注「已熔断」。
- **Given** 模型幻觉出一个不存在的工具名，**When** 发起调用，**Then** 立即回喂「该工具不存在，当前可用工具为：…」，**不消耗重试预算、不产生退避等待**。
- **Given** 同一 (工具, 参数) 连续出现 3 次，**When** 判定循环，**Then** 中止任务、保留已完成结果、给出「检测到重复调用」说明与三个恢复入口。

### AC-08 · 供应商降级
- **Given** 主供应商返回连续 5xx，**When** 触发降级，**Then** 自动切到配置列表中的下一个供应商，界面明示「已切换到 X，原因是 Y」，任务不中断。

### AC-09 · 沙箱与 SSRF
- **Given** 文件工具请求 `../../etc/passwd`，**When** 执行，**Then** 被拒绝并提示「路径超出工作区范围」；**Given** 请求沙箱内真实存在的符号链接指向外部，**When** 执行，**Then** 被拒绝（先解析符号链接再判定）。
- **Given** HTTP 工具请求 `http://169.254.169.254/latest/meta-data/`，**When** 执行，**Then** 被 SSRF 网关拒绝并记录审计。
- **Given** HTTP 工具请求 `https://example.com` 且该站 302 跳到内网地址，**When** 执行，**Then** 重定向被拒绝（每跳重新校验）。

### AC-10 · 跨浏览器记忆接续
- **Given** 用户在会话 A 中让 Agent 读了 3 个文件并得出结论，**When** 在同一浏览器新开会话 B 提问「刚才那些文件的字段对齐了吗」，**Then** 系统在会话 B 的上下文中**不包含**会话 A 的内容（会话隔离），但会话 A 的完整记录可从历史列表打开查看与继续追问。

### AC-11 · 空状态与五态覆盖
- **Given** 首次打开无任何会话，**When** 渲染首页，**Then** 展示「4 类工具待命中」与 3 个真实可点击示例任务，**页面不出现** "Welcome to" / "Lorem ipsum" / "Sign up today" 一类占位文本。
- **Given** 某次请求因上游限流失败，**When** 渲染错误态，**Then** 展示错误分类（限流）、原始原因、三个操作（重试 / 换模型 / 打开设置）。

### AC-12 · 扩展契约
- **Given** 开发者新增一个 `ToolDefinition`（name / label / description / inputSchema / risk / handler）并注册，**When** 运行契约测试，**Then** 该工具自动出现在模型工具清单、出现在设置页工具列表、并在卡片上正确渲染六种状态，**无需修改** Agent 循环代码与前端可视化代码；**Given** 未注册的具名工具，**When** 被模型调用，**Then** 返回「工具不存在」并回喂可用工具列表。

## 13. 边界条件

| 类别 | 边界 | 处理 |
|------|------|------|
| **空状态** | 无会话 / 无 Key / 无工作区文件 / 无 MCP 连接 / 工具清单为空 | 四种空态分别给出不同的真实内容与唯一下一步动作（配置 Key / 放文件 / 去连接器 / 换模型），不用通用占位 |
| **加载状态** | 首字延迟、工具执行中、压缩中、MCP 拉取工具清单中 | 骨架屏 + 阶段文案 + 停止按钮；压缩中显示进度（已处理轮次 / 总轮次） |
| **错误状态** | 模型错误 / 网络错误 / 权限错误 / 工具错误 / 参数错误 / 上下文超限 / 沙箱拒绝 / SSRF 拒绝 | 8 类错误各有独立分类标签、原文、建议与可用操作；沙箱与 SSRF 拒绝**不向模型提供绕行提示** |
| **边界值** | HTTP 响应体 0 字节 / 超过上限 / 非 JSON / 二进制；文件 0 字节 / 超大文件 / 二进制；计算表达式超长 / 除零 / 嵌套过深；MCP 工具返回 10MB 内容 | 统一策略：**超限即落盘 + 留摘要**，不做静默截断；二进制给下载而非内联；除零与深层嵌套返回明确数学错误而非崩溃 |
| **并发** | 同一会话并发发起两次任务；同一工具被并发调用 | 同会话串行化（第二次排队并提示「上一任务进行中」）；工具执行并发上限按工具类型设定（HTTP 可并发、文件写串行） |
| **离线 / 断网** | 模型请求期间断网；MCP server 进程被杀 | 模型请求断网 → 可重试错误 + 保留已有步骤；MCP 进程退出 → 该 server 标记不可用，其工具从清单移除，任务继续（其他工具不受影响） |
| **权限拒绝** | 文件权限不足、目录不可写、用户拒绝授权、工具未授权 | 明确区分「用户拒绝」与「系统拒绝」：用户拒绝 → 回喂模型换路；系统拒绝 → 提示修权限，均记录审计 |
| **上下文超限** | 模型返回 prompt too long | 先走压缩重试一次；仍失败 → 提示新建会话，不做截断 |
| **恢复码** | 错误 / 过期 / 已重置 / 跨设备使用 | 一律拒绝并给明确原因（不泄露「该码是否存在」以外的信息）；恢复码本身不携带任何内容，解码失败信息统一 |
| **时间** | 服务器时区错、跨时区、UTC 与本地时间混淆 | `time.now` 显式返回 UTC + 本地双时间戳；所有记录存 ISO 8601 UTC |
| **长会话列表** | 数百个会话 | 列表分页 + 按更新时间排序 + 搜索；恢复码入口固定位置不被列表挤走 |

### 14.5 数据埋点方案

**隐私前提（承接 v1.0 的合规边界）**：产品免登录，**不做远程数据上报**。所有埋点写入**本地 SQLite 的 `local_events` 表**，仅供用户本人在设置页查看与导出。这既保留产品假设的可验证性，又不破坏「数据留在本机」的承诺。**不上报 IP、不存原始输入内容**。

| 事件类别 | 事件名 | 说明 |
|----------|--------|------|
| 获客 | `first_open` | 首次打开（本地计数即可，无需远程） |
| 获客 | `provider_configured` | 完成 BYOK 配置（附 provider 与模型名，**不含 Key**） |
| 激活 | `first_tool_call` | 完成第一个真实工具调用（激活事件，最关键） |
| 激活 | `first_task_completed` | 第一次 Agent 自主完成一个任务（≥1 次工具调用并产出最终答案） |
| 留存 | `session_resumed` | 恢复一个历史会话（验证持久化价值） |
| 留存 | `session_restored_by_code` | 用恢复码跨浏览器恢复（验证跨浏览器恢复价值） |
| 留存 | `followup_asked` | 在同一会话内追问（验证多轮记忆） |
| 转化 | `approval_shown` / `approval_decided` | 高危确认曝光与决定（决定分布：批准/拒绝/改参数） |
| 转化 | `interrupt_clicked` | 用户主动打断（自主性过早的信号） |
| 转化 | `rerun_from_step` | 从某步重跑（结果不可信或结果不对的信号） |
| 异常 | `tool_call_failed` | 工具失败（附 `error_kind`、工具名，**不含参数原文**） |
| 异常 | `tool_circuit_open` | 某工具熔断 |
| 异常 | `loop_detected` | 检测到重复调用循环 |
| 异常 | `context_compacted` | 触发压缩（附压缩前后 token 估算） |
| 异常 | `error_occurred` | 前端 / 服务端错误（附阶段与错误分类） |
| 成本 | `task_token_usage` | 单任务 token 用量与估算花费（附 provider / 模型 / 工具调用次数） |

**属性规范**：每个事件附 `session_id`、`timestamp`、`app_version`、`provider`、`model`、`tool_call_count`、`duration_ms`；**禁止**上报 `args` 原文、`result` 原文、Key、文件路径中的用户目录部分。

**命名规范**：`{对象}_{动作}`（如 `tool_call_failed`、`session_restored_by_code`）。前端用轻量封装 `trackEvent()`（不引入重型 SDK，避免为埋点增加依赖体积）。

**埋点自检清单（发布前必须全绿）**：
- [ ] 获客：能算出「打开 → 配 Key → 第一次工具调用」的漏斗转化率
- [ ] 激活：能算出「首次配 Key → 首次完成任务」的中位时长
- [ ] 留存：能算出 7 日内会话恢复率与恢复码使用占比
- [ ] 异常：能算出工具失败率（按 error_kind 分布）、熔断率、循环检出率、压缩触发率
- [ ] 成本：能算出单任务平均工具调用轮数与平均花费（护栏指标的原始数据来源）

## 15. 成功指标

### 15.1 北极星指标

**周有效任务完成数（Weekly Successful Task Runs, WSTR）**——定义为：**去重会话数**，其中 Agent 自主发起 ≥1 次真实工具调用、产出最终答案、且用户在同一任务内**未**通过「打断 / 从某步重跑」表达不信任。

> 为什么不选「会话数」：会话数会被「打开看看」污染。加入「未打断未重跑」的条件，使指标直接对应「Agent 真的把活干完了且用户认可」。

**目标**：上线后 4 周内 WSTR 周环比增长 > 20%。

### 15.2 护栏指标

| # | 指标 | 目标值 | 为什么是护栏 |
|---|------|--------|-------------|
| G1 | 平均工具调用轮数 | 3–8 轮 | < 3 说明 Agent 不敢动手（能力不足或工具描述不清）；> 8 说明在绕路（工具不够用或提示词退化） |
| G2 | 工具调用失败率 | < 8%，且 100% 失败有分类标签 | 失败率上升 = 工具质量或模型质量退化；分类缺失 = 可观测性缺失 |
| G3 | 熔断触发率 / 循环检出率 | < 2% / < 1% | 触发率高 = 工具不可用或提示词在诱导死循环 |
| G4 | 上下文压缩触发率 | 10%–35% | < 10% = 任务普遍过短或压缩阈值失效；> 35% = 单任务成本失控，需要更激进的 L1 瘦身 |
| G5 | 压缩后保真自检通过率 | **100%** | 低于 100% 即意味着约束可能丢失，必须当作缺陷处理 |
| G6 | 高危确认拒绝率 | 观察项（首月不设目标） | 过高 = 默认档位太严（用户疲劳）；过低 = 档位太松（风险）。首月只采集不考核 |
| G7 | 用户主动打断率 | < 15% | 打断率高 = 用户不信任过程或 Agent 目标跑偏 |
| G8 | 任务完成率（发起任务 → 产出最终答案） | > 85% | 低于 85% 说明工具能力不足或失败处理有缺陷 |
| G9 | 首 token 延迟 p95 | < 3s | 沿用 v1.0 护栏，Agent 场景对首字更敏感 |
| G10 | 单任务中位成本 | ≤ ¥0.3（以国产模型 + 8K/2K token 量级估算） | 成本失控会让 BYOK 模式失去「便宜」卖点 |
| G11 | 恢复码跨浏览器恢复成功率 | > 90% | 记忆能力是本产品核心承诺之一 |
| G12 | MCP server 连接失败导致的整任务失败率 | **0%**（单 server 失败不得导致整任务失败） | 验证「MCP 不拖累 MVP 体验」的设计目标 |

## 17. 明确不做（Out-of-Scope）

| 不做的功能 | 原因 | 何时考虑 |
|------------|------|---------|
| **可视化工作流编排画布** | 那是 Dify / n8n 的核心形态，与「对话即执行」定位冲突；工程量巨大且会稀释 Agent 自主性 | 若出现「必须精确控制每一步」的企业诉求，作为独立形态评估 |
| **代码执行 / 沙箱跑代码** | 安全面与成本远超本阶段；计算工具用受限表达式求值器覆盖 80% 需求；`exec` 类能力留给有强隔离方案的形态 | 有成熟隔离沙箱方案（容器 / microVM）后评估 |
| **浏览器自动化 / Playwright 集成** | 复杂度与安全面大；HTTP 工具 + 用户本机的 MCP Playwright server 已能覆盖部分场景 | MCP 生态侧接入，不自建 |
| **多 Agent 协作 / 子 Agent 编排** | 显著抬高循环与可视化复杂度，MVP 阶段先把**单 Agent 多轮多工具**做扎实 | 单 Agent 工具调用稳定性达 G8 目标后 |
| **可编辑执行计划面板** | RICE 1.7，工程量大；用「一句话预告 + 可随时打断」低成本替代 | 任务复杂度上升、用户需要预审步骤时（#16） |
| **账号体系 / 注册登录** | 沿用 v1.0 边界：免登录是差异化，且避免合规负担 | 跨设备同步诉求转化为真实付费需求后 |
| **云端同步 / 多设备实时同步** | 单机本地定位 | 同上 |
| **付费订阅 / 计费 / 额度体系** | BYOK 模式下平台不经手推理成本，无需付费墙；避免「执行次数计费」这种已被 n8n 用户诟病的结构 | 出现平台侧增值服务（如托管 MCP 目录）后 |
| **团队协作 / 共享工作区 / 审计报表** | 单用户定位 | 明确出现企业客户诉求后 |
| **云端托管 / 多租户 SaaS** | 本地可运行即可（已拍板） | 上线方式另行确认时 |
| **MCP 官方技能市场 / 一键安装数千技能** | 官方生态已碎片化（仅 7 个在维护），给用户一个不可信目录是负资产 | 官方目录质量与稳定性恢复后再议 |
| **远程 MCP Server（HTTP / SSE 形态）** | 远程端点等于把任意远端变成工具源，攻击面不可控；MVP 只连本机 stdio | 有成熟的 MCP 认证与网关方案后 |
| **多模型并排对比 / 成本路由优化** | 属「多模型仪表盘」形态，与单任务工作台定位弱相关 | 用户明确提出「同一任务跑多个模型投票」后 |
| **Token 缓存优化 / prompt cache 复用** | 依赖具体 provider 的缓存语义，跨 provider 差异大 | 单一 provider 成为主力用户后 |
| **自建插件市场** | 无生态规模，且与「新增工具只需注册一条定义」的低代码目标重叠 | 出现第三方贡献者后 |
| **移动端原生 App** | 沙箱文件工具与 MCP 子进程在移动端不可用，形态价值有限 | 移动端只读场景被验证有价值后（Web 版本已覆盖） |
